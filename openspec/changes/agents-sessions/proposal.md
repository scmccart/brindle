# Proposal

**Depends on:** nothing. It is independent of `agents-launch-commands`, so the two can be applied in either order or side by side.
**Next:** `agents-profiles`, once `agents-launch-commands` is also archived: it builds the agent profile, zone and chat components, and `brindle agent …`, on this change's agent sessions, transcript, client protocol 4 and fake ACP agent.

## Why

Brindle is to host ACP agents (Agent Client Protocol, agentclientprotocol.com) in a zone of their own, with chat controls. An ACP agent is long lived: it should keep working, and keep its conversation, when Brindle quits, crashes or upgrades, exactly as a terminal session does today. The terminal server already gives terminals that lifetime, so it is where an agent session belongs. This change is the server half: the terminal server learns to run an ACP agent, act as its ACP client, keep its conversation and serve it to clients. It is testable on its own, with a fake ACP agent and no GUI. The Brindle half (the agent profile, the agent zone and the chat components) is `agents-profiles`.

Vocabulary: "ACP agent" or "agent session" is the new thing; "the helper" or "the terminal server" is `brindle-remote`.

## What Changes

- **A spike comes first.** It decides whether ACP's wire types come from the official `agent-client-protocol-schema` crate, pinned exactly, or from a hand-written subset: it decodes captured output of real ACP agents (with an unknown variant in it), builds the static musl helper with the crate, and checks that the `Cargo.lock` diff only adds packages.
- **A sixth workspace crate, `brindle-transcript` (`transcript/`).** It holds only the transcript event types and their pure fold, which Brindle and the core share; it depends on `serde` and `serde_json` and has no cargo feature. The ACP reducer, the wire types, the JSON-RPC bookkeeping, the checkpoint encoding and the schema crate are pure modules of `brindle-remote-agent` (`src/acp/`), their only user, so Brindle never depends on the schema crate. The rules, docs, checks and files that count or list the crates change with it (`process R21`, `ports R1`/`R3`, `fcis R4`, `railway R2`, `docs/architecture/README.md`, `tests/architecture.rs`, `Cargo.toml`, `CLAUDE.md`, a comment in `ci.yml`, the e2e helper check); release-please's files need no change.
- **The holder gets a second spawn mode: plain pipes, no PTY** (holder protocol H1 version 3, a new `SPAWN_PIPES` message and a `STDERR_TAIL` message). ACP's stdio transport can't run on a PTY: line discipline and ConPTY would rewrite the JSON. The holder still parses nothing: stdout is stored and forwarded as a session's output and tail, as a PTY's is, stdin takes the core's input, and stderr is kept as a bounded tail sent when the program exits. On Linux the agent runs in a session of its own; on Windows it is started with redirected pipes and a job object, no pseudoconsole, and a bare name that is a batch file fails with an error that shows the `cmd /c …` form.
- **The server core is the ACP client.** It sends `initialize` (ACP v1, no `fs` and no `terminal` capability) and `session/new`, reduces what the agent sends into a conversation, answers the agent's requests, and keeps the conversation whether or not a client is attached. Permission requests are answered only by the attached client's choice; with no client attached, a request waits.
- **A conversation is a transcript log of Brindle's own events,** not raw ACP lines: user message, agent message, thought, tool call (updated by id), permission request and its outcome, notices, a queued prompt, turn state and agent state. Streaming chunks merge into one entry. The core checkpoints the log, with the JSON-RPC bookkeeping, into the holder, so a core restart or an upgrade keeps the conversation, a turn in flight and a queued prompt.
- **A queue of one prompt:** a prompt sent during a turn waits in the session's queue slot and is sent only when the turn ends normally (`end_turn`). Any other ending, a cancel or the agent stopping leaves it held in the slot, apart from the user's draft, until a client sends it again or discards it; the slot is in the transcript, so a held prompt survives detaches, core restarts and upgrades and is replayed. A third prompt is refused.
- **Client protocol version 4** adds agent sessions: start one (`SPAWN_AGENT`), send a prompt (`AGENT_PROMPT`), discard the queued or held one (`AGENT_UNQUEUE`), send a held one again (`AGENT_RESEND`), cancel the turn (`AGENT_CANCEL`), answer a permission request (`AGENT_PERMISSION`), and the core's `TRANSCRIPT` events, carried as JSON objects the protocol crate doesn't interpret. The event kinds and their values are fixed for protocol 4; a new one needs a new protocol version. Attaching an agent session replays its log, then live events follow. Clients on protocols 1–3 never see agent sessions.
- **The session list tells agent sessions from terminals** (an `agent` object on a listed session: its activity, which maps onto program status, and the agent's name), lists their layouts as terminals', their absolute working directory and no size, and `brindle-remote list` and `list --json` show them.
- **A fake ACP agent**, a separate test binary (`brindle-fake-acp-agent`) that cargo builds and nothing packages, makes the server tests hermetic on Linux and Windows and serves `agents-profiles`' e2e cases, against release builds and archives too.
- **Architecture docs change with the code:** the sixth crate's rules above, the new pure modules in `fcis`'s table and `PURE_MODULES`, and `process-architecture.md` and `docs/code-map.md` describing pipe sessions, H1 3 and client protocol 4.

Not in this change: Brindle's own client code for protocol 4 (except what a server test needs), the profile kind, the agent zone and its components, closing with confirmation, `fs` and `terminal` capabilities, modes, slash commands. Deferred to their own proposal-only changes: ACP v2 (`agents-acp-v2`), in-zone login (`agents-login`), recovery after an agent exits (`agents-session-recovery`), paging the log (`agents-log-paging`), markdown (`agents-markdown`).

## Capabilities

### New Capabilities

- `agent-sessions`: the terminal server hosting ACP agents. It covers starting an agent session over pipes, the core acting as ACP client, the transcript log and its replay, prompts and the queue of one, cancellation and permission answers, how agent sessions are listed, what an agent's exit, failure or demand for login looks like, how a broken or hostile agent is confined, and what core restarts, upgrades and older peers do to agent sessions. A capability of its own because it owns behaviour that terminal sessions don't have and that will grow (`agents-acp-v2`, `agents-session-recovery`, `agents-log-paging`); `terminal-server` keeps the parts every session shares.

### Modified Capabilities

- `terminal-server`: "A core and its holders" (a holder also owns sessions run on plain pipes), "Protocol versions" (client protocol 4 adds agent sessions, holder protocol 3 adds pipe sessions) and "Management commands" (`list` shows agent sessions and their activity).

## Impact

- **New crate `brindle-transcript` (`transcript/`):** the event types, `Transcript` and its fold, the events' JSON encoding, its fuzz tests and `v4/` event fixtures.
- **`brindle-remote-protocol`:** client protocol 4 (`client::PROTOCOLS` 1–4) with six client messages and `TRANSCRIPT`; `SessionInfo.agent?` with `AgentActivity`; H1 version 3 (`holder::PROTOCOLS` 1–3) with `SPAWN_PIPES` and `STDERR_TAIL`, and `HeldSession.mode?`; transcript fixtures and fuzz targets.
- **`brindle-remote-agent`:** depends on `brindle-transcript` and the schema crate; the pure ACP modules in `src/acp/` (`wire.rs`, `lines.rs`, `rpc.rs`, `reduce.rs`, `checkpoint.rs`); the holder's pipe sessions (`server/holder.rs`, a `piped` item set in `server/platform/{unix,windows}` and the neutral `server/platform/piped.rs`); the core's agent sessions (`server/core/`); the CLI's `list`; the `brindle-fake-acp-agent` binary; `build.rs` embedding the version resource into `brindle-remote` only; tests in `remote-agent/tests/`.
- **Dependencies:** `agent-client-protocol-schema`, pinned exactly, in `brindle-remote-agent` only, if the spike keeps it (it brings `serde_with`, `strum` 0.28 and `derive_more` 2 into `Cargo.lock`). No JSON-RPC or async runtime crate.
- **`brindle`:** depends on `brindle-transcript` (unused until `agents-profiles`); its offer pinned at protocols 1–3 by a constant of its own in `src/remote/local.rs`, since it offers `client::PROTOCOLS` today and raising that to 4 would let agent sessions into its sweep and sessions palette; its exhaustive matches on `ToClient` gain the `Transcript` arm, which a core never sends below 4.
- **Docs, checks and files:** `docs/architecture/{README,ports-and-adapters,process-architecture,functional-core-imperative-shell,railway-oriented-programming}.md`, `docs/code-map.md`, `CLAUDE.md`, `.claude/rules/`, `tests/architecture.rs`, `tests/common/server.rs`, `Cargo.toml`, `.github/workflows/ci.yml` (a comment, and archive listing checks).
- **Nothing in Brindle's GUI changes.**
