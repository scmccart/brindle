# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Brindle is a GPU-accelerated terminal emulator for Linux and Windows 11, in Rust. It is built on GPUI 0.2.2 (Zed's toolkit, from crates.io) and `alacritty_terminal` 0.26, with tabs, profiles, and tmux in two modes: classic, and control mode (`tmux -C`). See README.md for user-facing behaviour and keybindings.

## Build and test

Build dependencies are the system packages listed in README.md. Wayland, fontconfig and Vulkan are dlopen'd at runtime, so they have no `-dev` packages.

```sh
cargo build                          # deps built at opt-level 2 (Blade is unusable unoptimized)
cargo build --release                # stripped, thin LTO
cargo test --workspace               # all unit tests, including the remote agent (no GUI needed)
cargo test -p brindle tmux::layout   # one module
cargo test -p brindle collector_matches_the_spike_transcript   # one test
```

- **`Cargo.lock` was seeded from gpui 0.2.2's own lockfile.** Do not regenerate it, and avoid broad `cargo update`: a newer `libc` breaks `xattr`. Add new dependencies with care.
- **One build warning is left on purpose:** `the following packages contain code that will be rejected by a future version of Rust: num-bigint-dig v0.8.4, proc-macro-error2 v2.0.1`. `proc-macro-error2` (E0365, a private `proc_macro` re-export) is the latest release, and gpui 0.2.2 pulls it in through `stacksafe` 0.1 (`gpui` → `stacksafe` → `stacksafe-macro` → `proc-macro-error2`); `num-bigint-dig` comes in through `gpui` → `oo7`. Only a gpui upgrade removes them. Vendoring a patched copy was rejected. Brindle's own code builds with no warnings.
- The GPUI and alacritty sources to read for API questions are in `~/.cargo/registry/src/index.crates.io-*/gpui-0.2.2` and `.../alacritty_terminal-0.26.0`.
- Zed's `terminal`/`terminal_view` crates are GPL-3.0. Use them only to learn the API shape and never copy code from them: Brindle is MIT OR Apache-2.0.

### Windows

The Windows port (OpenSpec change `port-to-windows`) builds on `x86_64-pc-windows-msvc` with the MSVC toolchain and the Windows 11 SDK.
- The same `cargo build`, `cargo build --release` and `cargo test --workspace` commands work in PowerShell or Git Bash. The release build needs the SDK's `fxc.exe`: on `PATH`, in SDK 10.0.26100.0, or named by `GPUI_FXC_PATH`.
- Platform code is behind `cfg`: `target_os = "linux"` for D-Bus, Wayland and X11 captures, `unix` for `libc`, `windows` for the `windows` crate. `src/win.rs` holds small Windows helpers. Process info is in `terminal/process.rs` (the seam `port-to-macos` uses), and the primary selection is in `src/primary.rs`.
- `.gitattributes` keeps every text file LF, because `include_str!` embeds assets and shell scripts.
- The Windows icons (`assets/windows/brindle.ico` and `brindle-256.png`, for toasts) are rendered from `assets/brindle.svg` by `scripts/render-icons.sh` and committed; re-run it after changing the SVG.
- On Windows `BRINDLE_E2E=1 cargo test --test e2e` lists only the Windows cases (`tests/e2e/cases/win.rs`: the ConPTY host and fallback, passthrough, glyph widths, closing mid-output, titles, PowerShell integration, the caption hit-test, WSL tmux) plus the `remote-*` cases, which skip unless `BRINDLE_REMOTE_AGENT` names a Linux helper, and `tests/perf` runs only its self-test.
- Pitfalls found on the way:
  - `--send` turns `\t`, `\e`, `\r` and `\n` into controls, so Windows paths in steps use `/`.
  - `brindle.exe` is a GUI program: PowerShell doesn't wait for it unless its output is piped, or it is run with `Start-Process -Wait`.
  - Elevated PowerShell (as on CI) sets its own console title.
  - GPUI answers `WM_NCHITTEST` for the last mouse position, so probes send a `WM_MOUSEMOVE` to the window first. That is a message, not input.
  - Windows acts on a caption press (drag, double-click, the caption buttons) only when GPUI leaves it unhandled, and GPUI's focus transfer counts as handling it. So the tab strip occludes the focusable workspace, and the caption buttons have no handlers there.
  - The shell reads no icon through a symlink, such as WinGet's `Links\brindle.exe`, so the shortcut's icon location is the resolved exe.
  - Test processes aren't DPI-aware, so Windows scales down the window rectangles they read. Probes call `SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)` first to work in Brindle's physical pixels.
  - Pure helpers that read Windows paths and are tested on Linux can't use `Path` (it splits only on `/` there); see `cmdline::program_stem`.
  - Commit subjects must start lowercase, so not with "Windows" or "PowerShell".
  - Every GPUI main-thread wake is a posted message, and Windows hands out `WM_PAINT` and `WM_QUIT` only when none is waiting, so a task that wakes without pause freezes the window (no paint, no quit). The event loops are paced for this (`terminal/pace.rs`).
  - cmd retitles the console for every command it runs, so a loop in cmd sends a title per iteration.
- **Linux checks from a Windows machine:** push the branch, then ask the Linux machine's Claude session, reachable over Remote Control, to fetch it and run `cargo test --locked`, `cargo build --release --locked` and `scripts/with-xvfb env BRINDLE_E2E=1 cargo test --test e2e`. Its user approves each run. The Linux CI jobs run the same commands on every push.
- GUI runs on a Windows desktop (any Brindle window, `--dump-screen-after` included) steal focus as on Linux `:0`, so ask first. There is no `scripts/with-xvfb` equivalent on Windows.

## Commit messages

Commits follow Conventional Commits, checked by commitlint (`commitlint.config.mjs`):
- Subject is `type(scope)!: subject`. Types: `feat`, `fix`, `docs`, `test`, `ci`, `build`, `refactor`, `perf`, `style`, `chore`, `revert`.
- Scopes are lower-case and name the area: `tmux`, `e2e`, `settings`, `shell-integration`, `deps`.
- The subject starts lowercase, except for an acronym (`docs: README, …`). Headers are at most 100 characters.
- `!` marks a breaking change (a changed key, config or default).
- OpenSpec propose, archive and check-off commits are `docs(openspec): …`. Merges keep `Merge …`, which the linter skips.
- `git config core.hooksPath scripts/hooks` (set in this clone) runs `scripts/lint-commits --edit` as a `commit-msg` hook. `scripts/lint-commits` alone checks the commits not on `origin/main`; `scripts/lint-commits BASE` checks `BASE..HEAD`; `scripts/lint-commits --title TITLE` checks a PR title.
- PRs are squash-merged, so the PR title becomes the commit on `main` with ` (#NN)` appended. Titles follow the same rules, and are at most 93 characters to leave room for the suffix. The squash commit's body is empty (the repository's squash default is the PR title alone), so the title is what release-please sees: mark a breaking change there with `!`.
- It runs commitlint through `npx` (Node ≥ 22.12), with `COMMITLINT_VERSION` pinned in the script and moved by hand. To vet a bump, run `scripts/lint-commits 7157fba` (the root commit) over the whole history.

## Verifying GUI behaviour

**Never inject synthetic input (XTest, xdotool) on this desktop.** It goes to the user's focused window, not Brindle. Opening a window can also steal focus while the user is typing, so ask before GUI runs unless they've said they're away. Use the built-in debug hooks instead:

```sh
BRINDLE_CONFIG=/tmp/test-config.toml ./target/release/brindle -p tmux \
  --send 'echo hi\r' --action tmux_split_right --dump-screen-after 5
```

- `--send` and `--action` steps run in order, one second apart (`--step-interval S` changes that), against the active tab. Action names are listed by `--list-actions`. `--wait-for TEXT` holds the later steps until the active terminal's screen shows TEXT (`\n` joins lines), for at most 30 s; use it instead of padding when a step depends on a slow program, such as a shell's first prompt. While a palette or the settings dialog has a text input focused, `--send` types into that input (control characters dropped) instead of the terminal; use `--action` (`picker_confirm`, `text_input_left`, …) for keys. `--action` bypasses the keymap, so a select menu or list in a dialog is driven with `list_up`, `list_down`, `list_first`, `list_last` and `list_confirm`.
- `BRINDLE_NOTIFY_LOG=<file>` appends each desktop notification to the file (`source<TAB>title<TAB>body`) instead of sending it over D-Bus.
- `BRINDLE_TMUX_STATE=poll|subscribe` overrides how control-mode sessions follow pane state (see "Subscriptions or polling" below). The e2e suite passes it through, so `BRINDLE_TMUX_STATE=subscribe BRINDLE_E2E=1 cargo test --test e2e` runs the subscription path on any tmux.
- `--dump-screen-after N` prints the tab titles, the active terminal's size and `TermMode`, its grid geometry (`--- grid origin=X,Y cell=WxH scale=S`, logical window pixels), its program status records (`--- status state=… …`, root first), any multi-zone layout (`--- zones count=N active=ID` and `--- zone id=ID rect=X,Y,W,H[ active]` in `[0, 1]` coordinates when the active local tab has 2+ zones), and its screen text, then exits. An open overlay adds its `--- palette` or `--- settings` line (palette rows print as `label  detail  [shortcut]`), and a focused text input adds `--- input text=… cursor=N selection=A..B`. `--- focus terminal|palette|settings|tabs|none|other[ stop="NAME"] modality=keyboard|pointer` says where keyboard focus is (`tabs` is the tab strip, focused through the hidden `focus_tab_strip` action; left/right/home/end then switch tabs through `--key`, and enter or escape return focus to the terminal), which settings-dialog stop has it (`sections` for the section list, the first stop), and the focus-visible modality (the e2e cases use it to check that focus returns to the tab when the dialog closes, and that rings show). `--key KEYSTROKE` presses a key in-process through `Window::dispatch_keystroke` (bindings, key listeners and keystroke observers run, as for a real key, so use it rather than `--action` when a check depends on the keymap or on focus-visible), and `--modality pointer|keyboard` stands in for a pointer press, which can't be posted on Linux. A run with any of these debug options (`--send`, `--action`, `--key`, `--modality`, `--dump-screen-after`, the latency flags) never hands itself to a running Brindle: beside one it runs on its own, restoring and recording nothing.
- For pixels, run under Xwayland (`env -u WAYLAND_DISPLAY DISPLAY=:0`) and grab the window with x11rb `GetImage` (`tests/e2e/capture.rs`).
- For tmux tests, use a throwaway server (profile `tmux_args = ["-L", "brindle-e2e", "-f", "/dev/null"]`), never the user's default server or `main` session, and kill it afterwards.

### End-to-end suite

Repeatable GUI checks live in `tests/e2e/` as named cases. It's an opt-in `harness = false` test target, so plain `cargo test` skips it:

```sh
BRINDLE_E2E=1 cargo test --test e2e                  # every case (opens windows: ask first)
BRINDLE_E2E=1 cargo test --test e2e -- titles tmux-  # cases whose names contain a filter
BRINDLE_E2E=1 cargo test --test e2e -- --list        # case names; "(no display)" ones open no windows
BRINDLE_E2E=1 cargo test --test e2e -- --self-test   # the harness's own parser tests
BRINDLE_E2E=1 cargo test --test e2e -- --shard 2/4   # every 4th selected case, from the 2nd
```

- Each case starts its own throwaway tmux server (`brindle-e2e-<pid>-<n>`) and runs Brindle against it with the debug hooks. Cases compare the dump with `capture-pane`, sample colors in window captures, or read OSC 10/11 replies. `tmux-*` cases check tmux behaviour Brindle relies on, over a raw `tmux -C` client, with no display.
- Local Linux tabs run in the terminal server, so the cases that open windows need `brindle-remote`: plain `cargo build` builds it (every crate is a default member), but `cargo test --test e2e` doesn't, so the suite stops with a message when the helper beside the binary (or `BRINDLE_REMOTE_AGENT`) is missing or older than its sources. Each case gets its own `BRINDLE_SERVER_DIR`, `/tmp/brindle-e2e-<pid>-<n>` (holder socket paths under `target/` exceed the 108-byte `sun_path` limit). After the case the harness runs `brindle-remote stop`, copies the core's log to `server-core.log` in the case directory and removes the server directory; a `serve` or `hold` still running then fails the case, and is killed.
- Expected colors come from the `e2e` theme in the generated test config (`tests/e2e/brindle.rs`), not from built-in themes.
- `BRINDLE_E2E_BIN` tests another binary (default: this build's). `BRINDLE_E2E_SLOW=2` doubles every delay, Brindle's step spacing included (through `--step-interval`). `BRINDLE_E2E_DISPLAY` picks the X display (default `:0`).
- The `remote-*` cases (`tests/e2e/cases/remote.rs`) run Brindle against disposable Docker containers built from `tests/fixtures/remote` (an SSH server and tmux) and deploy the sibling `brindle-remote` helper (`cargo build -p brindle-remote-agent`). Without a Docker daemon or the helper they skip; `BRINDLE_REMOTE_E2E_REQUIRED=1` turns that into an error.
- `BRINDLE_REMOTE_DOCKER_TEST=1 cargo test -p brindle --locked remote::client` is an opt-in transport test with no GUI: `client::connect` against real `docker exec` and OpenSSH containers (deployment and reuse, exit and failure events, shell noise, orphans, floods, Ctrl-C). It runs the static helper at `target/x86_64-unknown-linux-musl/release/brindle-remote`, built with the Docker command in README.md; rebuild it after changing agent code, or the test runs a stale one.
- Each case's config, dumps, logs, captures (`.ppm`) and transcripts are kept in `target/tmp/e2e/<case>/`.
- Every run has its own `BRINDLE_STATE_DIR` (`<case>/state`), so nothing touches the real saved session. Quitting leaves local tabs detached in the server, and every launch attaches detached sessions, so when a run exits the harness hangs up the sessions it left detached; `Run::keep_detached()` (the `local-server-*` cases) keeps them for the case or the next run. `Run::command` passes `-e`, placed last.
- When a change adds a GUI check, add it as a case here instead of a one-off script.
- `scripts/with-xvfb <command>` runs it headless: a private Xvfb on a free display, openbox, lavapipe (`VK_DRIVER_FILES`), `LC_ALL=C.UTF-8` and a private session bus (`dbus-run-session`). Runs under it open no windows on the desktop, so they don't need asking first, unlike runs on `:0`. The suite needs the window manager (palette and multi-window cases). The locale keeps programs in panes consistent; tmux doesn't need it, since control clients run with `-u`.
- CI (`.github/workflows/ci.yml`, `ubuntu-26.04` runners, no containers) runs on pushes to `main` and on pull requests, except pull requests that change only docs (`**.md`, `openspec/**`, `LICENSE-*`; `paths-ignore`, safe because no CI job is a required check): `commits` (`scripts/lint-commits` from the PR's base or the push's `before`, else from `origin/main`, and a check that the `.ico` is no older than the SVG), `test` (a check that the five workspace crates share one version, `cargo test` and both harness self-tests), `release` and `windows` (the reusable `build-linux.yml` and `build-windows.yml`, which releases call too). `build-linux.yml` does the release build, the static musl helper (uploaded as `brindle-remote-linux-x86_64`) and the Linux archive (`scripts/package-linux.sh`, uploaded as `brindle-linux-x64`). `build-windows.yml` runs on `windows-latest`: `scripts/fetch-conpty.ps1`, the release build, `cargo test`, both self-tests, the exe's version resource, icon and PerMonitorV2 manifest, `--install-desktop`/`--uninstall-desktop`, and the release zip (`scripts/package-windows.ps1`, uploaded as `brindle-windows-x64`). When its `winget-validate` input is true (CI, not releases), it also writes the WinGet manifest (`scripts/winget-manifest.ps1`) and checks it with `winget validate`. `GPUI_FXC_PATH` is set from the runner's newest SDK. The called workflows set no concurrency group, since one matching the caller's would cancel it. The remaining CI jobs are `windows-e2e` (the suite's Windows cases on the runner's desktop, advisory, uploading `target/tmp/e2e/` as `e2e-windows` on failure; the runner has no WSL distribution, so `windows-wsl-tmux` skips), and `e2e` (the suite under `scripts/with-xvfb` with `BRINDLE_E2E_SLOW=2`) per tmux version in 4 shards (`--shard K/4`, round-robin after filters; the count is in the matrix, the job name and the command). Pushes and pull requests run only the latest tmux; the older one (3.6a, the polling path) runs only from a manual dispatch with the `old-tmux` input (`gh workflow run ci.yml --ref <branch> -f old-tmux=true`), since the matrix is built with `fromJSON(format(inputs.old-tmux && …))`, so both versions' entries sit in that one expression. e2e is advisory: red on failure, not a required check. A failed shard uploads `target/tmp/e2e/` as `e2e-tmux-<v>-shard-<k>`; rerun it locally with the same `--shard`. Move the pins by hand: `COMMITLINT_VERSION` in `scripts/lint-commits`, the Rust version in `rust-toolchain.toml` (the one pin for local builds and every CI job, which run `rustup toolchain install`), and the e2e matrix (a tmux version, what `tmux -V` reports, and the tarball's sha256 when it's built from source).
- `pr-title.yml` runs `scripts/lint-commits --title` on every PR's title (opened, edited, reopened, synchronized), with the script and rules taken from the base commit. It is a required check, and squash merges default to the PR title (repository settings).
- `release.yml` runs release-please (`release-please-config.json`, `.release-please-manifest.json`) on every push to `main`. It keeps a release PR, `chore(release): X.Y.Z`, open: the `rust` release type bumps all five crates and only their `Cargo.lock` entries, and writes `CHANGELOG.md` with `feat`/`fix`/`perf`/`revert` sections. Before 1.0, breaking changes bump the minor version.
  - Merging that PR tags `vX.Y.Z` and creates a draft release. The same run builds both platforms at the tag through the reusable workflows, attaches the Linux archive, the Windows zip and `SHA256SUMS`, and publishes the release. A failed build leaves the draft; rerun the failed jobs.
  - On release PRs (branches `release-please--…`), CI runs only `commits`, `test` and the title check. The builds and e2e jobs skip, since the code is unchanged and the release run builds again.
  - release-please acts as a GitHub App (secrets `RELEASE_APP_ID` and `RELEASE_APP_PRIVATE_KEY`), because PRs opened with `GITHUB_TOKEN` trigger no workflows.
  - Don't edit the crate versions or `CHANGELOG.md` by hand. Dependabot (`.github/dependabot.yml`) opens monthly PRs for the actions; Cargo gets security PRs only (its entry sets `open-pull-requests-limit: 0`), which are lockfile bumps to review against the `Cargo.lock` rule above. Both entries set `commit-message` so subjects read `chore(deps): bump …`.

### Manual checks

The suite never sends real keys, so these stay manual. Hand them to the user, with `scripts/run-throwaway` to try them on a build without touching their config, saved session or terminal server (it runs Brindle against a private config, state and server directory under `/tmp`, stops that server on exit, and takes `--config FILE`, `--keep` and `-- <brindle args>`; it opens a window, so it is theirs to run, not ours):
- ctrl-shift-d in a local tab does nothing and sends no `^D` (the `Swallow` binding; `commands-detach-beside-local` only checks the action);
- IME composition: with IBus, ctrl-shift-u `e9` space gives `é`, in a terminal and in a palette;
- wheel scrolling in local tabs and tmux panes;
- classic (`plain`) tmux profiles with the prefix keys;
- dragging tabs to reorder them;
- the palette shortcuts toggling (ctrl-shift-p, ctrl-shift-space and the `⌄` button).

## Architecture

Data flows **terminal server session (Linux) / Windows pseudoconsole / tmux → `Terminal` (model) → `TerminalView` (input) → `TerminalElement` (paint)**, with `Workspace` owning the tabs of one window.

- **`terminal/`** — the `Terminal` entity wraps an `Arc<FairMutex<alacritty Term>>` and a `Backend`:
  - `Server` (Linux): a session of the local terminal server (see `remote/` below); every local Linux tab uses it, with no in-process fallback, and the Unix side of `Pty` is gone. The connection's reader thread parses the session's output (`terminal/server.rs`'s `SessionSink`), and input, resize and close go to the connection's writer thread. `Terminal::spawn` returns at once; connecting, a reconnect or an upgrade finish in the background with input queued, and a failure (no helper, no connection) becomes that terminal's `Terminal::message`, uncached. Process info stays local, from `/proc`.
  - `Pty` (Windows only): alacritty's `EventLoop` runs on its own thread, over Brindle's pseudoconsole.
  - `Remote`: bytes are pushed in with `feed()` and input goes to a closure. Used for tmux panes and for error-message tabs (`Terminal::message`).
  - `Agent`: a remote Linux helper owns the PTY; framed output reaches `feed()`, while input, resize and process/CWD queries go back over its channel.
  - **Program status (`status.rs`):** the OSC 7501 parser and each `Terminal`'s `Records` (one per id, the root is `""`), with the lifetime rules: `end_activity` on OSC 133 `A` and process exit (drops `working`/`blocked`), `seen` on user input (drops `done`/`error`), `reset` on `ESC c`. `handle_found` applies what the scanner found in stream order and answers the `?` query with `write` (for a pane that goes through `send-keys -H`; tmux passes the OSC through raw but doesn't answer it). `TerminalEvent::Status(Option<Notice>)` carries a notice when a record became blocked/done/error with a different kind, title or message. `Workspace` keeps `Tab::status` (the max over the tab's terminals, `TmuxWindowView::status_summary` for panes) and draws it as a coloured dot beside the bell dot; `--dump-screen-after` prints the records as `--- status` lines.

  `links.rs` finds URLs in a line of chars and runs the opener (`xdg-open`, or `BRINDLE_LINK_OPENER`) on a background thread. `link_at` returns the link at a grid point: the cell's OSC 8 hyperlink, or else a URL found in the logical line, where rows are joined by `WRAPLINE`. `TerminalView` looks links up only in event handlers while ctrl is held (hover) or on a ctrl-click, never in `prepaint`, which just underlines the stored spans.
  - **Parsing and shell integration (`shell_integration.rs`, `pty.rs`):** every backend parses through Brindle's own `Parser` (vte processor + OSC 133 scanner), which lives in `brindle-term-core` with `Marks` and `Records` (`terminal::{shell_integration, status}` re-export them). For `Server`, `SessionSink` parses on the connection's reader thread in the same lock order. For `Pty` (Windows), `MarkedPty` wraps Brindle's pseudoconsole so the event loop's reader (`ParsingReader<R>`) parses under the term lock and returns `Ok(0)`; alacritty's own processor never sees bytes. Lock order is parser → term (`lock_unfair` while holding the parser) → marks. Marks are absolute lines (`base + Line`); `base` is kept by finding the row that was at `Line(0)` after each processor call (rows rotate, their cells never move), and resizes remap marks through logical lines. Synchronized-update timeouts are flushed from the GPUI side on `Wakeup`.

  - **Windows pseudoconsole (`conpty.rs`, `cmdline.rs`):** Brindle creates the pseudoconsole itself; alacritty's ConPTY backend isn't used.
    - The ConPTY functions are resolved once. They come from the packaged `conpty.dll` that `build.rs` embeds (`scripts/fetch-conpty.ps1` fetches it). It is loaded by absolute path from beside the exe, else from a copy extracted to `%LOCALAPPDATA%\brindle\conpty\<version>`, and only when the bytes there match the embedded ones. Otherwise the inbox kernel32 functions are used, with one warning. `BRINDLE_CONPTY=inbox` forces those.
    - It is created with `PSEUDOCONSOLE_GLYPH_WIDTH_WCSWIDTH` (0x10), which matches the grid's per-code-point widths; the host's grapheme default makes ❤️ two cells.
    - `PipeReader`/`PipeWriter` do blocking I/O on threads and wake the event loop with IOCP `post`s on `tty::PTY_READ_WRITE_TOKEN`. The loop polls level-triggered and registers once, so the reader posts again whenever a read leaves data behind, and the writer posts when room frees up. `ChildWatcher` uses `RegisterWaitForSingleObject`.
    - The `Pseudoconsole` is an `Arc` shared by `MarkedPty` (resizes) and the tab (`parent_console_to`, reparenting to the window's HWND). The last drop calls `ReleasePseudoConsole` (optional export), then `ClosePseudoConsole` on a short-lived thread, while the reader keeps draining to EOF. Closing never blocks a thread Brindle cares about.
    - Arguments are quoted with the MSVC rules. The environment block is merged and sorted case-insensitively, with profile entries winning.

  Alacritty events reach GPUI through an unbounded channel drained by a spawned task. It handles a batch's `Wakeup`s and title changes once each (`Batch::coalesce`), and once `pace::BURST` (4) updates in a row came less than `pace::PACE` (4 ms) apart, waits out the rest of `PACE` before the next, and each update takes ready batches for up to `pace::BUDGET` (16 ms, `pace::drain`); the remote-output and tmux event loops are paced the same way. Replies the emulator generates go through `reply()`, which drops them for `Remote` terminals, because tmux answers terminal queries itself. `keys.rs` and `mouse.rs` are pure xterm encoders with unit tests.
- **`remote/` / `brindle-remote`** — the `brindle-remote-protocol` crate (`remote-protocol/`, re-exported as `remote::protocol`) defines bounded framed stdio messages, shared by the app and the helper. The helper is the `brindle-remote-agent` crate (`remote-agent/`, binary `brindle-remote`), with its implementation in `remote-agent/src/agent.rs`. `client.rs` deploys a matching Linux helper through OpenSSH or Docker/Podman exec on a background thread, then routes PTY data, resize, exit and `/proc` process info to `Terminal::Agent`. The helper is cached by Brindle version with user-only permissions. The client's writer sends a heartbeat every 10 s, and the helper ends the session when it has read no frame for the request's `idle_limit_secs` (60). That liveness (`Liveness`) is stamped by the stdin reader thread, which drops heartbeats itself and marks itself `busy` while handing a real frame to the event queue, because the main loop can block on output and leave healthy clients' frames unread; never measure it in the main loop's event handling. Remote tmux control profiles run `tmux -C` directly through SSH/container pipes and keep using the existing `TmuxSession` collector; `SessionKey` includes the remote target.
- **Terminal server (Linux; OpenSpec change `terminal-server`)** — local Linux tabs run in sessions of a persistent server, two roles of the `brindle-remote` binary (`remote-agent/src/server/`), so sessions survive a Brindle exit, a core crash, restart or upgrade. The helper is required (`HELPER_MISSING` names `BRINDLE_REMOTE_AGENT`).
  - **Directory:** `$BRINDLE_SERVER_DIR`, else `$XDG_RUNTIME_DIR/brindle`, else `~/.cache/brindle/run` (`server_dir::resolve` in `remote-protocol`, used by both sides; mode 0700). It holds `core.lock`/`core.sock`/`core.log` and `holder-<build>-<n>.{sock,lock,log}`. Socket paths must fit `sun_path` (108 bytes), which is why e2e server directories are under `/tmp`. Peers are checked with `SO_PEERCRED`. A role starts as `<role> --ready-fd N` (`daemon.rs`: double fork, `setsid`, stdio to its log, one ready byte). Brindle (the core), the core (holders) and a holder (the core) start roles through `systemd-run --user --scope` in a `brindle-<role>-<hex>.scope` (`remote-protocol/src/scope.rs`), so stopping the desktop's app scope doesn't kill them; without `$XDG_RUNTIME_DIR/systemd/private` or `systemd-run`, or with `BRINDLE_NO_SCOPE=1` (the agent tests and e2e set it), they start directly with one log line. `systemd-run --scope` execs the program itself, so roles are run as `/proc/<own pid>/exe`, not `/proc/self/exe`.
  - **Holder (`hold`, `holder.rs`):** one thread on `event_loop.rs`'s `PollLoop` (poll(2) plus a `SIGCHLD` self-pipe, behind the `EventLoop` seam for the Windows IOCP phase). It owns many sessions' PTYs (`remote-agent/src/pty.rs`, shared with the stdio `--server` agent), is the programs' parent, and parses nothing. Per session it stores, uninterpreted, the core's last checkpoint and the raw tail since (1 MiB cap, then `truncated`). It exits when it has no sessions (10 s after start if it never had one). Its `Hangup` sends SIGHUP then SIGKILL to the process group while the group has members. With no core for 3 s (`CORE_GRACE`) it starts its own binary's `serve`, backing off 3 s to 60 s (`BRINDLE_TEST_HOLDER_CORE_ARGS` overrides the args in tests). It sets `IUTF8` on every PTY.
  - **Core (`serve`, `core.rs`, `core/{clients,holders,sessions,manage,screen}.rs`):** one thread on the same loop; takes `flock` on `core.lock` for its life (the loser of a start race waits for the winner, then exits 0), serves clients on `core.sock`, drives holders and runs an `Emulator` per session whether or not a client is attached. It accepts clients only after adopting the startup holders (≤ 5 s). Close policies: `kill` ends on `CLOSE`/`KILL`/`STOP` and when the owner (a `client_token`) is gone, after `RECONNECT_GRACE` (10 s) for sessions adopted by a new core; `detach` ends only on `KILL`/`STOP`/exit. `ATTACH` makes the client the owner; `DETACH` clears the owner and switches `kill` to `detach`, so a reconnecting client gets back only the sessions it still owns. Each session's `SessionMeta` (owner, policy, a random 128-bit hex `key`, `profile`, `started`) lives in its holder; the core sends `SET_META` on every owner or policy change to H1 v2 holders (logged and skipped for v1), so the next core sees it. Session ids restart at 1 in a fresh core; the key tells sessions apart across cores. `LIST`'s `SessionInfo` carries key, title (the emulator's), `started` and profile. It exits 5 s after the last session and client (`UNUSED_LIMIT`). Backpressure is per session: `PAUSE`/`RESUME` once a client's queue passes 1 MiB / falls under 256 KiB. Each `Term` feed runs under `catch_unwind` (`screen.rs`): a panic marks that emulator broken (replays are then `ESC c`) and the session keeps forwarding output; `BRINDLE_TEST_FEED_PANIC` (debug builds) injects it.
  - **Protocols (`remote-protocol/src/{client,holder,wire,version}.rs`):** client protocol 1 (`PROTOCOLS`) and core↔holder H1 share the stdio frame header (`type: u8, len: u32 BE, payload`) with their own message numbers and version ranges, negotiated per connection by `HELLO`/`WELCOME`. JSON fields are additive with defaults; a new message type needs a new version; transcript tests pin both. H1's `meta` is an opaque JSON blob the core owns. H1 is at version 2 (`SET_META`, message 14, replaces a session's stored meta). Large checkpoints/tails are chunked (`*_BEGIN`, 64 KiB `*_CHUNK`s, `*_END`). The stdio protocol is untouched.
  - **`brindle-term-core` (`term-core/`):** the GPUI-free state shared by Brindle and the core: `shell_integration` (`Parser`, `Marks`), `status` (`Records`), `osc` (the scanner), `replay` (`render(&mut Term, &Marks, &Records, title) -> Vec<u8>`, with its fidelity limits listed in the file) and `emulator` (`Emulator`: `Term` + `Parser` + `Marks` + `Records` + the kept title; its listener drops every event but title changes, so the server never answers queries — the attached client does). It re-exports `alacritty_terminal`. Keep the core's tracking identical to the client's, or replay drifts.
  - **Checkpoints and replay:** the replay stream (`ESC c`, scrollback and screen with SGR, OSC 133 marks, the alternate screen, modes, cursor, title, OSC 7501 reports) serves attach/reconnect (`REPLAY_START`…`REPLAY_END`) and is sent to the holder as a checkpoint after 512 KiB of output (`CHECKPOINT_AFTER`, checked after each read of the holder's output, and only past 4 MiB while more of it is waiting, because rendering costs about as much as feeding), before a step-down and on detach. `CHECKPOINT_END` carries `covers`, the tail bytes the core had fed when it rendered; the holder drops only that many from the front, since output may still be in flight. A new core feeds a fresh `Emulator` the checkpoint then the tail, and replays requested meanwhile wait for it.
  - **Upgrade, drain, supervision:** after `WELCOME`, `remote::local::upgrade::offer` decides whether Brindle's helper is newer (higher semver, or equal version with a different build id and a later mtime than `/proc/<core pid>/exe`); if so it runs `<helper> check --holder-protocols …` and, on success, sends `STEP_DOWN`. The core checkpoints every session, sends `GOODBYE { handover }` to each holder and exits; the upgrading client starts the next `serve`, which adopts the holders and `DRAIN`s any of another build (they take no new sessions and exit when empty). A holder never gets replaced while it has sessions. Other clients reconnect, waiting `START_AFTER` (5 s) before starting a core themselves.
  - **Management (`cli.rs`, `check.rs`):** `brindle-remote list | kill | status | stop | check` are protocol 1 clients that never start a core (`status --json` prints `{"running":false}` with no server).
  - **Brindle's client (`src/remote/local.rs`, `local/{connection,session,upgrade}.rs`):** `shared()` keeps one `Connection` per process with a reader thread (demultiplexes by session, parses into each `SessionSink`; during a replay it drops bells, notifications and status notices) and a writer thread (queues messages, holds them while disconnected). `Session::start` (`SPAWN`) and `Session::attach` (`ATTACH`, answered by a `REPLAY_START` carrying its `req`) return at once and do the connecting, start, upgrade and request on their own thread, so the UI thread never blocks; each request waits in `State.requests` for its answer. Closing a zone or tab ends its program, and quitting keeps it: `Closing::Keeps` (profile tabs) spawns with the `detach` policy, so a crash keeps them too, and `Closing::Ends` (`-e`) with `kill`. `Terminal::close` (an explicit close) sends `CLOSE`; dropping a `Keeps` terminal (quit) sends `DETACH`, an `Ends` one `CLOSE`. Nothing asks first and quit waits for nothing. On a lost connection the reader reconnects with the same `client_token` (a core is started after `START_AFTER`), a `LIST` after `WELCOME` finds the sessions the core no longer has, and those, or all after `RECONNECT_LIMIT` (15 s), get the red "session lost" line (`EXIT` with `lost`) while the tab stays open. `SPAWN` carries the complete environment (Brindle's with `child_env(profile)`; non-UTF-8 variables are dropped).
  - **Reattach (`src/reattach.rs`):** the instance's launch (unless `--no-restore`) lists the core's sessions once before the window opens (`running_sessions`, which never starts a core) into the `Detached` global. The state file's windows are merged into one (`session::merge_windows`), and zones whose recorded `{ id, key }` isn't detached any more are dropped (`session::drop_lost_zones`: the sibling takes the split, an empty tab goes; skipped when listing failed). Restored zones take theirs by id and key, the rest open as tabs in start order, then the launch's own request (`-p`/`-d`/`-e`/`--attach`) opens as the active tab (`Workspace::open`); `--attach ID`'s session is kept out of `Detached`. An attached terminal starts at the session's listed size, and its `SessionSink` holds the first replay until `REPLAY_END`, then feeds it at that size and resizes back under the term lock: a replay fed at another size (an inactive tab is never laid out, so it stays 80x24) misplaces the cursor. The "Attach Session…" palette (`PaletteKind::Sessions`) lists through the shared connection; `picker_kill` sends `KILL`.
  - **Tests:** `remote-agent/tests/{holder,core,upgrade,manage}.rs` run a real holder and core in a temp `BRINDLE_SERVER_DIR` with test clients (roles and start race, spawn and I/O, policies, reconnect, replay fidelity, checkpoints and truncation, upgrade/drain/refused check, management commands); `remote-protocol/src/fuzz.rs` fuzzes the decoders. The e2e `local-server-*` cases (`tests/e2e/cases/local_server.rs`) run Brindle against a private server directory and `brindle-remote stop` afterwards. `scripts/with-xvfb` runs them without a desktop.
- **`terminal_view.rs` / `terminal_element.rs`**
  - Key handling: GPUI resolves keybindings *before* `on_key_down`. `key_down` encodes special keys and modifier combos and calls `stop_propagation`. Plain text (no modifiers or shift only) instead arrives through the `EntityInputHandler` path, which is what makes IME work. That's why app shortcuts are ctrl-shift-*.
  - Painting: the element batches each row into same-style runs, shapes each batch once, and places it at its exact column. Non-ASCII glyphs and the cursor cell get their own batch. Box drawing (U+2500–U+259F) is painted as rectangles, not glyphs.
  - Mouse: listeners are registered in `paint` with hitbox checks, and move/up are tracked globally while dragging.
- **Grid geometry** — `cell_metrics()` and `fit_grid()` are the single source of cell size; anything that positions cells (tmux panes!) must use them. `fixed_size` views (tmux panes) never resize their `Terminal` and get no padding, because the container positions them.
- **`workspace.rs`** — each tab is either a local zone tree (`TabContent::Zones(Entity<ZoneTreeView>)`) or a tmux window (`TabContent::Tmux`).
  - **`zone_view.rs`** — `ZoneTreeView` owns a local tab's binary split tree (`ZoneTree`) of `Zone`s (`ZoneContent::Terminal(Entity<TerminalView>)`), normalized `[0, 1] x [0, 1]` geometry (`UnitRect`) for `FocusZone*` and `--dump-screen-after`, and conditional native GPUI chrome (1-zone tabs render the terminal directly; 2+ zones render 1px dividers and a header bar per zone with status dot, title, and split/close buttons).
  - The tab strip is the client-side-decorated title bar.
  - Tab titles are cached and refreshed on `TitleChanged` plus a 1 s poll of `/proc`.
  - Brindle has one window: nothing opens another after launch. Removing the last tab closes it, and closing it quits.
  - A tmux session is shown once, keyed by `SessionKey` (program, `tmux_args`, session name). `find_session` scans this window's sessions; picking or opening (`open_profile`: ctrl-alt-N, ctrl-shift-t) a profile whose session it shows switches to that tab.
- **`instance.rs`** — one Brindle per state directory. `main` takes `session.lock` before GPUI starts; the holder is the instance and listens on `$XDG_RUNTIME_DIR/brindle-instance-<FNV-1a of the state dir>.sock` (0600, `SO_PEERCRED` same uid; a named pipe `\\.\pipe\brindle-instance-<hash>-<user>` on Windows). A later launch without debug options sends one JSON line (`instance::Request`: `-p`, absolute `-d`, `-e`, `--attach`, its working directory, its `XDG_ACTIVATION_TOKEN`/`DESKTOP_STARTUP_ID`), retrying the connection for 5 s, and exits 0 on `ok` or 1 with the error. The listener thread lists sessions for `--attach`, hands the request to the UI thread (`take_launches`) and waits for its answer; the instance opens it with `Workspace::open` and raises the window with `activation::raise` and the forwarded token. On Windows the launcher calls `AllowSetForegroundWindow` for the pipe server's pid first.
- **`settings.rs`** — a GPUI global holding the `Config`, the resolved font (built once) and the zoom level. Live reload (`main.rs` polls the file mtime) rebuilds it, rebinds keys, and calls `Workspace::apply_config`.
- **`notify/`** — desktop notifications.
  - `osc.rs` scans output for the OSCs Brindle acts on beside alacritty, which drops OSCs it doesn't know: 9/777 notifications, 7501 program status, 133 `A` prompt starts and `ESC c` (for the status lifetimes). It keeps state across reads and returns `Found` values. ConEmu's `9;1`–`9;12` commands are not messages. The number must be written as is (`0009` isn't 9).
  - Local Linux tabs scan on the server connection's reader thread (`SessionSink`); Windows tabs scan on alacritty's I/O thread: the shell-integration reader (`pty.rs`) reads the PTY through `terminal/scan.rs`'s `ScanReader`, before parsing. What it finds travels on the terminal's event channel (`ChannelEvent::Osc`). Remote terminals scan in `feed()`. The scanner itself is `brindle-term-core`'s `osc`, which `notify/osc.rs` re-exports.
  - `TmuxWindowView` re-emits its panes' `Bell`/`Notify`, so `Workspace::on_attention` handles local and tmux tabs alike (bell dot, focus rule, settings).
  - `Notifier` (a GPUI global) rate-limits (`policy.rs`), then sends to a zbus worker on the background executor, or to the `BRINDLE_NOTIFY_LOG` file (written synchronously, since `--dump-screen-after` quits right after). It maps notification ids to window and tab for clicks.
  - A click activates the tab and raises the window. On Wayland, `activation.rs` uses the server's `ActivationToken` on GPUI's own `wl_surface` (foreign display, own event queue), because GPUI's own activation request is refused when unfocused. A later launch's forwarded token is used the same way.
- **`desktop.rs`** — `--install-desktop` / `--uninstall-desktop` register Brindle with freedesktop launchers. They write `brindle.desktop` (its `Exec` is the running binary's absolute path) and the embedded `assets/brindle.svg` icon, and they run in `main` before GPUI starts, so no display is needed. `scripts/install.sh` delegates to them. Linux icons come only from the desktop entry and the icon theme, matched through the `brindle` app_id. The icon cache is refreshed only where one already exists.
- **`actions.rs`** — one `ACTIONS` table drives config-name lookup, `--list-actions` and the command palette (an entry's label puts it in the palette). Default bindings use the key contexts `Workspace`, `ZoneTree`, `Terminal`, `TmuxWindow`, `Palette`, `SettingsDialog`, `SettingsSections`, `SettingsList` and `TextInput`, plus `UiLayer`, `UiFocusScope`, `UiList` and `UiCommand` (the last five from `brindle_ui::default_bindings()`, chained in). User bindings go in the `Terminal` context, so they win over the defaults.
  - Config names can stand for `brindle_ui` actions: `picker_up/down/confirm/cancel` are `ListUp/ListDown/ListConfirm/Dismiss` (as `settings_cancel` is `Dismiss`), so old configs and `--action` steps keep working; `palette_keys_and_picker_aliases` pins each to its key's action.
  - tmux actions (detach included) are handled only in `TmuxWindow`. ctrl-shift-d is also bound to the hidden `Swallow` action in `Workspace`, so outside tmux tabs it never reaches a shell as `^D`.
- **`picker.rs`** — `Palette`, the view behind every palette (new tab from a profile, commands, sessions, the session-ended and open-elsewhere questions) and the one-line prompt (OpenSpec change `ui-command-palette`). List mode is a `brindle_ui::Command` in `Dialog` chrome (shadcn's `CommandDialog`: no padding, no visible header, no close `X`); prompt mode is an `Input` under the prompt's label, which is the dialog title, with a pointer-only close `X`.
  - `Workspace` shows it in a modal `brindle_ui::Overlay` slot (`palette`, with `palette_kind` beside it); the settings dialog has the other slot, and opening one closes the other first, so the focus each records is the tab's. `set_ignore_outside_press` is set per kind (`ignores_outside_press`: the session-ended and open-elsewhere questions ignore a press outside, and the prompt that replaces a question in place keeps the slot's flag; a prompt opened on its own closes on one). The palette has its own tracked focus handle, and its one `FocusStops` stop is the active mode's input, so Tab stays on it; `--- focus` reports `palette`.
  - Every way of closing reaches `Workspace` as `PaletteEvent::Dismissed` (the command list's `Cancelled`, or the palette's own `Dismiss` handler in prompt mode); the palette never emits `DismissEvent`, so `palette_dismissed` (ended sessions, orphaned tabs) always runs.
  - The command palette lists the labelled actions available from the tab that had focus, snapshotted before the palette opens. It needs both `available_actions` (for global listeners) and `is_action_available` (for `no_json` actions). Running a command closes the palette, refocuses the tab and calls `window.dispatch_action` (deferred, and following focus), so it takes the keybinding's path.
  - Prompted commands (`TmuxRenameWindow`, `TmuxCommand`) are ordinary actions. Their handlers emit a prompt request that `Workspace` opens, so a keybinding and the palette behave the same. `open_prompt` turns an open palette into the prompt in place (the open-elsewhere question's "New tmux session…": one layer, one focus restore); a prompt asked for by a command run from the palette opens a palette of its own, since the palette closed to run it.
  - Keys: a list's are its command list's (`UiList`, `UiCommand`); the `Palette` context adds only ctrl-shift-delete (`PickerKill`, the sessions palette, on `Command::highlighted()`) and enter (`ListConfirm`, which submits a prompt). A sessions palette refreshed after a kill takes the new rows through `Command::set_groups`, keeping the filter text.
- **`brindle-ui` (`ui/`; OpenSpec change `add-brindle-ui`)** — the shared UI crate, modelled on shadcn/ui: tokens (`UiTheme`), overlay primitives (layers, focus scope, placement, list navigation, focus-visible), components and `TextInput`.
  - **Boundary:** it depends on `gpui` only, never on `brindle`, `brindle-term-core` or `alacritty_terminal`, so it knows nothing of terminals, config or the `ACTIONS` table. Mapping the terminal theme to tokens is the app's job.
  - Its actions are `brindle_ui::*`. `brindle_ui::default_bindings()` returns its default keys, and Brindle chains them into its own `default_bindings()`, so a config reload restores them; the crate binds no keys itself.
  - Controls activate on the enter or space **key-down** and ignore gpui's keyboard click, which fires on the key-up for whatever has focus then (an overlay confirmed with enter would otherwise reopen from its opener on the release).
  - The gallery (`cargo run -p brindle-ui --example gallery`, see `ui/README.md`) shows every component; `-- --check` drives the `ui-components` spec's scenarios from inside the app (keys through `Window::dispatch_keystroke`; key releases and pointer presses as messages posted to its own window, Windows only, skipped elsewhere) and prints `ok`/`FAIL`/`SKIP` per check. Both open a window: ask first, as for any GUI run.
- **`text_input.rs`** (in `brindle-ui`, `ui/src/text_input.rs`) — the single-line `TextInput` used by every overlay text field. `EditState` (text, selection, IME composition, UTF-16 offsets) is pure and unit-tested; the entity adds focus, the `TextInput` key context, mouse, clipboard and `EntityInputHandler`, so typed text and IME arrive through the platform input handler as in terminals.
  - The `TextInput` context binds no enter, escape, tab, up/down or ctrl-p/ctrl-n, so those reach the contexts around it: enter, up/down and ctrl-p/ctrl-n a command list's `UiList` (a palette's filter), the `Palette` (enter in a prompt) or the settings dialog's contexts, tab `UiFocusScope` (inside an overlay) and escape `UiCommand` (a palette's list) or else `UiLayer`.
  - Owners keep plain strings: they subscribe to `TextInputEvent::Changed` and call `set_text` (which emits nothing) for their own changes. The settings dialog lists its controls as `FocusStops` per section and mode, and the overlay's focus scope walks them on tab; the dump's `field=` is derived from which stop has focus.
- **`tmux/`** — control mode over plain pipes (`tmux -C`, not `-CC`):
  - **UTF-8:** clients start as `tmux -u [tmux_args] -C …`. Without `-u`, a client in a non-UTF-8 locale gets `_` for the tabs in our `-F` formats and for non-ASCII text, and no tab appears.
  - **Framing (`protocol.rs`):** `Collector` groups output into `%begin…%end/%error` responses and notifications. Responses to our commands (flags bit 0) are matched FIFO against `Io.pending`, because the `%begin` number is tmux's global counter, not a request id.
  - **Windows:** `%window-add` carries no layout and isn't followed by `%layout-change`, so window state always comes from a full `list-windows`. Its `#{pane_id}` is each window's active pane; it only fills in panes we don't know yet, and `%window-pane-changed` is authoritative after that.
  - **Never write tmux's selection back:** attaching must not change tmux's current window or active panes. tmux tabs are inserted inactive and come to the front only on `WindowActivated`. `active_window` is set before the tabs are announced, and `select_pane` sends nothing when the pane is already active or tmux hasn't reported one yet.
  - **Layout:** we render `#{window_visible_layout}`, the third field of `%layout-change`, which reflects zoom.
  - **Pane geometry:** layout cells drive dividers, but a pane can be smaller than its cell: `pane-border-status` takes a row for a title line without any `%layout-change` or change to the layout string. Each pane's `Inset` comes from tmux's reported geometry (`PANE_STATE_FORMAT` on restore, then the `brindle-geometry` subscription or poll) and carries over to new cells. A size change that arrives outside a layout change re-snapshots the pane. A report that doesn't fit its cell means the layout is stale (`rotate-window` sends no `%layout-change`), so the window list is fetched again.
  - **Title lines:** tmux draws `pane-border-status` lines only for terminal clients. Brindle follows each pane's `#{T:pane-border-format}` (already expanded, with `#[...]` style runs that `tmux/style.rs` parses) and each window's `#{pane-border-status}`, and `TmuxWindowView` paints them in the reserved rows, caching the shaped runs.
  - **Pane styles:** tmux applies `window-style`/`window-active-style` and the border styles only for terminal clients. Brindle follows them and sets each pane `Terminal`'s `default_colors`, and uses the border colors for dividers and title text. tmux's built-in border values (the active border's green) count as unset. Color reports to tmux carry each pane's effective colors, because tmux answers OSC 10/11 from them before looking at `window-style`.
  - **Pane restore:** three commands are sent back to back — `display-message` (`PANE_STATE_FORMAT`), `capture-pane -a`, `capture-pane`. `%output` for the pane is dropped until the last capture arrives, then `restore_bytes` replays the snapshot (after `ESC c` when re-snapshotting a pane). Mode 1003 is `#{mouse_all_flag}`; `mouse_any_flag` means *any* mouse mode.
  - **Input:** `send-keys -H`. Size: `refresh-client -C` from the tab's area.
  - **Color queries:** a control client has no tty, so tmux answers OSC 10/11 in panes with black unless told otherwise. Each pane's theme foreground and background are reported with `refresh-client -r` when the pane is created and again on config reload.
  - **Palette queries:** tmux 3.6 ignores OSC 4 in `refresh-client -r` reports, but passes OSC 4 queries through in `%output`, so Brindle answers them itself: the pane `Terminal` hands the reply to the session's `PaletteHandler`, which sends it with `send-keys -H`. It stays silent when tmux answers instead: the program set the index itself, `#{pane-colours[N]}` is set, or a terminal client is attached to the session (`list-clients`; tmux asks that client's terminal).
  - **Subscriptions or polling:** tmux before 3.7 can segfault when a control client with format subscriptions leaves or loses its session (`control_check_subs_timer` reads through a NULL session; 3.7 checks for it). So the session asks for `#{version}` before its first window list (`subscriptions_safe`), and on older or unrecognised tmux registers no subscriptions at all. It polls with one `list-panes -s` a second instead, built from the same `SUBSCRIPTIONS` table, and `PollState` turns each reply into the `SubscriptionChanged` notifications for values that changed, so both paths share the handlers. One poll is in flight at a time, and one is sent right after a user-typed command.
  - **Leaving a session:** with subscriptions, `release()` removes them before `detach-client`, from `detach`, `Drop` and an app-quit hook that waits for the writer to flush, and `kill_window`/`kill_pane` unsubscribe before ending the session's last window or pane. A session ended from inside tmux (the last shell exiting) can't be covered that way, which is why old tmux polls.
  - **Another Brindle's session:** `find_session` sees only this process. So a named attach first runs `list-clients` on the background executor, and spawns the client only if no other Brindle's control client is on the session (`shown_by_another_brindle`). Brindle's clients carry `BRINDLE_CONTROL_CLIENT=<brindle pid>`. A client counts when that marker equals its parent pid (from `/proc`) and isn't ours. The marker leaks into the panes of a server that such a client started, which is why the parent is checked. Windows skips the check: there is no `/proc`, and through WSL neither the marker nor the parent pid reaches the client. Otherwise the session emits `ShownByAnotherBrindle`, and `Workspace` asks in the window, without "Go to". A window left with no tabs, or with only an ended session's tabs that nothing replaces (`orphaned_sessions`), closes when that palette or its prompt is dismissed.
  - **Events:** `Failed` (tmux exited before ever attaching) is distinct from `Detached`, and `ShownByAnotherBrindle` (never attached) from both.
  - The tmux prefix can't work in control mode, so native `Tmux*` actions replace it.
- **`tmux_view.rs`** — `TmuxWindowView` mirrors one tmux window. It creates pane views and follows tmux's active pane in a session observer (`sync`), not during render, and draws the dividers.

GPUI 0.2.2 doesn't cache views by default, so any `cx.notify()` re-renders the whole window. Keep I/O, allocation-heavy work and lock contention out of `render` and `prepaint`.

## Delegation

This section is for the session the user is driving. A subagent carrying out a routed brief runs its own builds and tests inline and does not delegate further.

Delegate through the `route` skill (`/route:route`, from the route plugin): it picks the model and effort from the brief, so never give the Agent tool a model or effort the script did not choose, and never do inline what you would otherwise delegate while orchestrating. Chores whose output is large get a routing of their own even when nothing else is delegated, written as the commands to run and what to report, so they land on Haiku: `cargo build --release --locked`, full `cargo test` and e2e runs, CI log reads (`gh run view --log-failed`), `openspec archive`, and the version and `Cargo.lock` checks from `.github/workflows/ci.yml`. Do not fold them into an implementation brief. When route returns `split: true`, route the parts separately or say in the brief why they stay together.

## Specs

Behaviour is specified with OpenSpec:
- Main specs: `openspec/specs/<capability>/spec.md`.
- History and design rationale: `openspec/changes/archive/`.

Read the relevant spec before changing behaviour, and propose spec changes through an OpenSpec change with the `openspec` CLI.

# Command output

Command output here is condensed to save tokens, keeping every signal and
dropping costly noise. Treat it as the complete result: run commands
normally, and batch related commands into one call to avoid extra turns.
Truncated results state their recovery path in their own output. Re-run a
command as `rtk proxy <cmd>` only when its result is unusable: empty when
output was clearly expected, contradicting its exit code, or garbled.
