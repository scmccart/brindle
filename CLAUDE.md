# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Brindle is a GPU-accelerated terminal emulator for Linux and Windows 11, in Rust. It is built on GPUI 0.2.2 (Zed's toolkit, from crates.io) and `alacritty_terminal` 0.26, with tabs, zones and profiles. tmux is an ordinary program to it. See README.md for user-facing behaviour and keybindings.

## Build and test

Build dependencies are the system packages listed in README.md. Wayland, fontconfig and Vulkan are dlopen'd at runtime, so they have no `-dev` packages.

```sh
cargo build                          # deps built at opt-level 2 (Blade is unusable unoptimized)
cargo build --release                # stripped, thin LTO
cargo test --workspace               # all unit tests, including the remote agent (no GUI needed)
cargo clippy --locked --workspace --all-targets -- -D warnings   # what CI's clippy job runs
cargo test -p brindle terminal::keys   # one module
cargo test -p brindle ui_tokens_are_legible_for_every_builtin   # one test
```

- **`Cargo.lock` was seeded from gpui 0.2.2's own lockfile.** Do not regenerate it, and avoid broad `cargo update`: a newer `libc` breaks `xattr`. Add new dependencies with care.
- **One build warning is left on purpose:** `the following packages contain code that will be rejected by a future version of Rust: num-bigint-dig v0.8.4, proc-macro-error2 v2.0.1`. `proc-macro-error2` (E0365, a private `proc_macro` re-export) is the latest release, and gpui 0.2.2 pulls it in through `stacksafe` 0.1 (`gpui` → `stacksafe` → `stacksafe-macro` → `proc-macro-error2`); `num-bigint-dig` comes in through `gpui` → `oo7`. Only a gpui upgrade removes them. Vendoring a patched copy was rejected. Brindle's own code builds with no warnings, and clippy's `-D warnings` doesn't fail on this note, which is cargo's report on dependencies.
- **`brindle-fake-acp-agent` is a test binary.** It is `brindle-remote-agent`'s second `[[bin]]` (`remote-agent/src/fake_acp/`): a scripted ACP agent (`expect`, `send`, `respond`, `wait-file`, … steps; the parser is pure, `fake_acp/script.rs`) that the helper's real-role tests (`remote-agent/tests/agents.rs` and the agent cases of `upgrade.rs`, `manage.rs` and `relay.rs`) run in place of a real agent, through `CARGO_BIN_EXE_brindle-fake-acp-agent`. Every `cargo build` puts it in `target/<profile>/` beside `brindle-remote`, but nothing packages it, and the archives' listing checks (CI, below) fail if it slips in. Its parser's tests run with `cargo test -p brindle-remote-agent --bin brindle-fake-acp-agent`.
- The GPUI and alacritty sources to read for API questions are in `~/.cargo/registry/src/index.crates.io-*/gpui-0.2.2` and `.../alacritty_terminal-0.26.0`.
- Zed's `terminal`/`terminal_view` crates are GPL-3.0. Use them only to learn the API shape and never copy code from them: Brindle is MIT OR Apache-2.0.

### Windows

The Windows port (OpenSpec change `port-to-windows`) builds on `x86_64-pc-windows-msvc` with the MSVC toolchain and the Windows 11 SDK.
- The same `cargo build`, `cargo build --release` and `cargo test --workspace` commands work in PowerShell or Git Bash. The release build needs the SDK's `fxc.exe`: on `PATH`, in SDK 10.0.26100.0, or named by `GPUI_FXC_PATH`.
- Platform code is behind `cfg`: `target_os = "linux"` for D-Bus, Wayland and X11 captures, `unix` for `libc`, `windows` for the `windows` crate. `src/win.rs` holds small Windows helpers. Process info is in `terminal/process.rs` (the seam `port-to-macos` uses), and the primary selection is in `src/primary.rs`.
- `.gitattributes` keeps every text file LF, because `include_str!` embeds assets and shell scripts.
- The Windows icons (`assets/windows/brindle.ico` and `brindle-256.png`, for toasts) are rendered from `assets/brindle.svg` by `scripts/render-icons.sh` and committed; re-run it after changing the SVG.
- On Windows `BRINDLE_E2E=1 cargo test --test e2e` lists only the Windows cases (`tests/e2e/cases/win.rs`: the ConPTY host and fallback, passthrough, glyph widths, closing mid-output, titles, PowerShell integration, the caption hit-test, a background tab's menu, an elevated and an unelevated instance at once, and the `windows-agent-*` cases: a turn and the close confirmation (`agent.rs`'s own cases), a batch file's `cmd /c` hint, Markdown's parts and Windows' `file:` link actions, an exited agent continued by resume in its holder's pipe session, an agent login chosen, cancelled and chosen again, a `cmd /c` profile's terminal login method withheld, a terminal login program's exit status through ConPTY (0 starting the agent again, 1 showing the methods), and `-p -` from a file, from cmd's `<` and with no standard input handle at all, which `winproc::start_without_stdin` gives through `CreateProcessW`) plus the fonts cases (`settings-fonts`, `ui-font-config`, from `cases/fonts.rs`), the link cases that print through either shell (`links-refused`, `links-opener-fails`, `links-notice-*`, from `cases/links.rs`), the `local-server-*` cases that apply to Windows and the `remote-*` cases, which skip unless `BRINDLE_REMOTE_AGENT` names a Linux helper or one is beside the binary (an unpacked zip's), and `tests/perf` runs only its self-test. Each Windows case that opens a window gets a private server directory (`target/tmp/e2e/<case>/server`) and needs `brindle-remote.exe` beside the binary (or `BRINDLE_SERVER_HELPER`), not older than its sources, or, beside a `BRINDLE_E2E_BIN` outside this build such as an unpacked zip's, of the binary's release; `windows-e2e-build` on CI builds them, the helper and with it the fake ACP agent, for `windows-e2e` and `windows-e2e-archive`.
- Pitfalls found on the way:
  - `--send` turns `\t`, `\e`, `\r` and `\n` into controls, so Windows paths in steps use `/`.
  - `brindle.exe` is a GUI program: PowerShell doesn't wait for it unless its output is piped, or it is run with `Start-Process -Wait` (which waits for the whole process tree, a server Brindle started included; wait on the `-PassThru` process with `WaitForExit()` instead).
  - Elevated PowerShell (as on CI) sets its own console title.
  - GPUI answers `WM_NCHITTEST` for the last mouse position, so probes send a `WM_MOUSEMOVE` to the window first. That is a message, not input.
  - Windows acts on a caption press (drag, double-click, the caption buttons) only when GPUI leaves it unhandled, and GPUI's focus transfer counts as handling it. So the tab strip occludes the focusable workspace, and the caption buttons have no handlers there.
  - The shell reads no icon through a symlink, such as WinGet's `Links\brindle.exe`, so the shortcut's icon location is the resolved exe.
  - Test processes aren't DPI-aware, so Windows scales down the window rectangles they read. Probes call `SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)` first to work in Brindle's physical pixels.
  - Pure helpers that read Windows paths and are tested on Linux can't use `Path` (it splits only on `/` there); see the agent's `conpty::cmdline::program_stem`.
  - Commit subjects must start lowercase, so not with "Windows" or "PowerShell".
  - Every GPUI main-thread wake is a posted message, and Windows hands out `WM_PAINT` and `WM_QUIT` only when none is waiting, so a task that wakes without pause freezes the window (no paint, no quit). The event loops are paced for this (`terminal/pace.rs`).
  - cmd retitles the console for every command it runs, so a loop in cmd sends a title per iteration.
  - GPUI destroys a dropped window in a task, which never runs once the message loop has ended, so on a quit the window's platform state outlives `App::shutdown`, and with it the input handler holding the focused `TerminalView` (and its `Terminal`): their drops never run. What a quit must do is done explicitly (`Workspace::quit`), not in a `Drop`.
- **Linux checks from a Windows machine:** push the branch, then ask the Linux machine's Claude session, reachable over Remote Control, to fetch it and run `cargo test --locked`, `cargo build --release --locked` and `scripts/with-xvfb env BRINDLE_E2E=1 cargo test --test e2e`. Its user approves each run. The Linux CI jobs run the same commands on every push.
- GUI runs on a Windows desktop (any Brindle window, `--dump-screen-after` included) steal focus as on Linux `:0`, so ask first. There is no `scripts/with-xvfb` equivalent on Windows.

## Commit messages

Commits follow Conventional Commits, checked by commitlint (`commitlint.config.mjs`):
- Subject is `type(scope)!: subject`. Types: `feat`, `fix`, `docs`, `test`, `ci`, `build`, `refactor`, `perf`, `style`, `chore`, `revert`.
- Scopes are lower-case and name the area: `e2e`, `settings`, `shell-integration`, `deps`.
- The subject starts lowercase, except for an acronym (`docs: README, …`). Headers are at most 100 characters.
- `!` marks a breaking change (a changed key, config or default).
- OpenSpec propose, archive and check-off commits are `docs(openspec): …`. Merges keep `Merge …`, which the linter skips.
- `git config core.hooksPath scripts/hooks` (set in this clone) runs `scripts/lint-commits --edit` as a `commit-msg` hook. `scripts/lint-commits` alone checks the commits not on `origin/main`; `scripts/lint-commits BASE` checks `BASE..HEAD`; `scripts/lint-commits --title TITLE` checks a PR title.
- A wrapped body line that starts with `word: ` (such as `id-token: write`) reads as a trailer, and commitlint rejects it (`footer-leading-blank`). Reword it so the line doesn't start that way.
- Fix a pushed commit with a new commit, not an amend: force-pushes are denied in `.claude/settings.json`, and the squash merge discards the branch's commits anyway.
- After `gh pr create`, wait for the checks (`gh pr checks <n> --watch`) and report them; the task isn't done while they run. Name an unrelated failure's test and message, and rerun it only with the user's go-ahead. The user merges.
- PRs are squash-merged, so the PR title becomes the commit on `main` with ` (#NN)` appended. Titles follow the same rules, and are at most 93 characters to leave room for the suffix. The squash commit's body is empty (the repository's squash default is the PR title alone), so the title is what release-please sees: mark a breaking change there with `!`.
- It runs commitlint through `npx` (Node ≥ 22.12), with `COMMITLINT_VERSION` pinned in the script and moved by hand. To vet a bump, run `scripts/lint-commits 7157fba` (the root commit) over the whole history.

## Verifying GUI behaviour

**Never inject synthetic input (XTest, xdotool) on this desktop.** It goes to the user's focused window, not Brindle. Opening a window can also steal focus while the user is typing, so ask before GUI runs unless they've said they're away. Use the built-in debug hooks instead:

```sh
BRINDLE_CONFIG=/tmp/test-config.toml ./target/release/brindle \
  --send 'echo hi\r' --action split_zone_right --dump-screen-after 5
```

- `--send` and `--action` steps run in order, one second apart (`--step-interval S` changes that), against the active tab. Action names are listed by `--list-actions`. Bad steps are usage errors at launch (status 2, before any window opens, naming the option): an option without its value, `brindle terminal -e` without a command, a removed flat option (`-p`, or `-d`/`-e` without the `terminal` subcommand), `brindle terminal NAME` naming no profile, an `--action` no action has, a `--key` that doesn't parse, a `--hover`/`--click`/`--right-click`/`--press`/`--release` that isn't `[MODS-]COL,ROW`, and a `--dump-screen-after` that isn't a number. `--press` holds the left button on a cell, so a later `--hover` drags, until `--release`. `--wait-for TEXT` holds the later steps until the active terminal's screen shows TEXT (`\n` joins lines), for at most 30 step intervals (30 s at the default one, so `--step-interval` stretches it); use it instead of padding when a step depends on a slow program, such as a shell's first prompt. While a palette or the settings dialog has a text input focused, `--send` types into that input (control characters dropped) instead of the terminal; use `--action` (`picker_confirm`, `text_input_left`, …) for keys. `--action` bypasses the keymap, so a select menu or list in a dialog is driven with `list_up`, `list_down`, `list_first`, `list_last` and `list_confirm`.
- `--dump-screen-after N` prints the tab titles, the active terminal's size and `TermMode`, its grid geometry (`--- grid origin=X,Y cell=WxH scale=S`, logical window pixels), the font families in effect, preview included (`--- fonts terminal="…" ui="…"`, right after the grid line, or after the tabs when there is no terminal), the window's config line when it shows one (`--- config "TEXT"`, escaped onto one line, right after the fonts line; none when there is no line), its program status records (`--- status state=… …`, root first), its open OSC 3008 contexts (`--- context id="…" type=NAME|none[ label="…"]`, outermost first, `label` on an `elevate`, `chpriv`, `remote`, `container` or `vm` one, or a `session` as `root`), the program's OSC 22 pointer shape on the screen the active terminal shows (`--- pointer shape=NAME screen=primary|alternate`; none while the pointer is Brindle's own), the pointer the grid's last painted frame chose (`--- grid-pointer NAME`, a CSS name, once the grid has painted), the progress bars shown (`--- progress tab=N state=normal|error|paused|indeterminate[ percent=P]` for each tab whose face has one, numbered as the tab lines, then `--- progress zone=ID state=…[ percent=P]` for each zone of the active tab with one when it has 2+ zones, the active zone first), the context badges shown (`--- badge tab=N kind=privileged|elsewhere label="…" draw=icon|text` for each tab whose face has one, then `--- badge zone=ID …` for each zone of the active tab with one when it has 2+ zones, the active zone first; a privileged badge draws as a warning icon, `draw=icon`, its label kept as data and shown only in its tooltip), any multi-zone layout (`--- zones count=N active=ID` and `--- zone id=ID rect=X,Y,W,H[ active]` in `[0, 1]` coordinates when the active local tab has 2+ zones), and its screen text, then exits. An active agent zone prints its block in place of the screen and the terminal's lines (`--- agent zone=ID state=connecting|not-started|starting|ready|login-required|logging-in|failed|exited:CODE|exited:signal|holder-lost|lost|broken[ message="…"][ name="…"] turn=idle|working|blocked|cancelling|ended:STOP|failed activity=STATE status=STATE|none link=up|reconnecting session=open|ended continue=restart|respawn|none:not-ended|no-conversation|not-offered|profile-gone`, `continue` saying what Continue conversation would do: restart the agent on its session, continue in a new session, or neither and why; then the login row while it shows, one `--- login choice method="ID" kind=agent|terminal "NAME"[ description="…"]` per method in the agent's order (a terminal one adding ` args="…" env="K=V,…"[ dropped="NAME,…"]`, what its zone runs and the variables left out, or ` withheld="…"` when the profile's command can't run it) or `--- login running method="ID" "NAME"` while one runs, the last line adding ` refusal="…"` for a refused login or a login program's exit; then `--- note "…"` for a profile note, one `--- entry N user|agent "…"`, `thought open=true|false "…"`, `tool call="…" kind=… status=… "TITLE"`, `permission[ call="…"] options=ID:"NAME"|… outcome=pending|selected:ID|cancelled "TITLE"` or `notice level=info|warn|error "…"` per entry, each agent message's and thought's entry line (which keeps its Markdown source) followed by one `--- block entry=N part=K kind=paragraph|heading:L|code|code:LANG|list|quote|table|rule "TEXT"` per rendered part (TEXT its shown text), each followed by a `--- link entry=N part=K target="URI" text="TEXT" action=open|confirm|refuse:no-scheme|refuse:scheme|refuse:other-host|refuse:no-drive` per link in it (what a ctrl-click would do on this platform), `--- queued waiting "TEXT"` or `--- queued held reason=cancelled|failed|stopped:STOP|login-required|agent-stopped|output-lost resend=yes|no "TEXT"`, `--- conversation entries=N at=end|away` and `--- prompt status=ready|submitted|streaming|disabled[ first="TEXT"][ refusal="…"]`, `first` the launch's first prompt waiting for a login, shown read-only in the input and sent once the agent is ready); `--wait-for` matches those lines without `zone=` and `at=`, and `--send` types into its prompt input (line breaks kept). The close confirmation adds `--- confirm close target=zone:ID|tab:N busy=ID:working|blocked,…` (N the tab's place), after the menu lines, and the link confirmation `--- confirm link "URI"` there. An open overlay adds its `--- palette` or `--- settings` line (the settings dialog's Fonts section's is `--- settings section=Fonts mode=form terminal=… size=… line_height=… ui=… field=… invalid=[…] can_apply=… error=…`, plus ` open=… query=… highlighted=…` while a family list is open; the Clipboard section's is `--- settings section=Clipboard mode=form copy_on_select=… right_click=… field=… can_apply=… error=…`; the Profiles list's is `--- settings section=Profiles mode=list selected=… default=… profiles=[…] agent=[…] error=…`, `agent` naming the agent profiles; a palette list's is `--- palette list query=… highlighted=N|none`, `N` the highlighted row's index among the rows printed after it, from 0, or `none`; rows print as `label  detail  [shortcut]`), or for an open menu `--- menu items=A|[B]|-|C highlighted=N` (disabled items in brackets, separators as `-`, `N` the highlighted entry counted from 0 with separators, or `none`) followed by one line per item in the palette rows' form, and a focused text input adds `--- input text=… cursor=N selection=A..B`. Each `--wait-for` step that gave up adds `--- wait-for timeout "TEXT"`, and one still waiting when the dump is taken adds `--- wait-for pending "TEXT"` (TEXT escaped onto one line; both come last, after the focus line), so a dump that shows an unexpected screen says which wait failed; a run with no `--wait-for` prints neither. `--- focus terminal|palette|settings|tabs|menu|none|other[ stop="NAME"] modality=keyboard|pointer` says where keyboard focus is (`agent stop=prompt|continue|queued:remove|queued:send-again|queued:discard|login:ID|login:cancel|permission:ENTRY:OPTION|stop` is an agent zone's stop, `login:ID` a login method's button and `login:cancel` Cancel login, `confirm stop=cancel|close` the close confirmation's button and `confirm stop=cancel|open` the link confirmation's; `tabs` is the tab strip, focused through the hidden `focus_tab_strip` action; left/right/home/end then switch tabs through `--key`, and enter or escape return focus to the terminal; `menu` is an open menu: the `⌄` profile menu, a tab's menu or a zone header's menu, opened through the hidden `open_profile_menu`, `open_tab_menu` (the active tab's) and `open_zone_menu` (the active zone's) actions and driven with `--key down`, `--key enter` and `--key escape`), which settings-dialog stop has it (`sections` for the section list, the first stop), and the focus-visible modality (the e2e cases use it to check that focus returns to the tab when the dialog closes, and that rings show). `--key KEYSTROKE` presses a key in-process through `Window::dispatch_keystroke` (bindings, key listeners and keystroke observers run, as for a real key, so use it rather than `--action` when a check depends on the keymap or on focus-visible), and `--modality pointer|keyboard` stands in for a pointer press, which can't be posted on Linux. A run with any of these debug options (`--send`, `--action`, `--key`, `--modality`, `--dump-screen-after`, the latency flags) never hands itself to a running Brindle: beside one it runs on its own, restoring and recording nothing.
- `BRINDLE_NOTIFY_LOG=<file>` appends each desktop notification to the file (`source<TAB>title<TAB>body`) instead of sending it over D-Bus. An OSC 99 line adds tab-separated flags (`i=ID`, `replaces`, `buttons=A|B`, `silent`, `urgency=low|critical`, `expiry=never|MS`, each only when it applies), and a program's `p=close` adds `close<TAB>osc99<TAB>i=ID`; OSC 99 queries are answered with the platform sink's capabilities.
- For pixels, run under Xwayland (`env -u WAYLAND_DISPLAY DISPLAY=:0`) and grab the window with x11rb `GetImage` (`tests/e2e/capture.rs`).

### End-to-end suite

Repeatable GUI checks live in `tests/e2e/` as named cases. It's an opt-in `harness = false` test target, so plain `cargo test` skips it:

```sh
BRINDLE_E2E=1 cargo test --test e2e                  # every case (opens windows: ask first)
BRINDLE_E2E=1 cargo test --test e2e -- titles palette  # cases whose names contain a filter
BRINDLE_E2E=1 cargo test --test e2e -- --list        # case names; "(no display)" ones open no windows
BRINDLE_E2E=1 cargo test --test e2e -- --self-test   # the harness's own parser tests
BRINDLE_E2E=1 cargo test --test e2e -- --shard 2/3   # every 3rd selected case, from the 2nd
```

- Cases run Brindle with the debug hooks and compare its dump with the expected screen text, sample colors in window captures, or read OSC 10/11 replies.
- Local Linux tabs run in the terminal server, so the cases that open windows need `brindle-remote`: plain `cargo build` builds it (every crate is a default member), but `cargo test --test e2e` doesn't, so the suite stops with a message when the helper beside the binary (or `BRINDLE_REMOTE_AGENT`) is missing or older than its sources (for a `BRINDLE_E2E_BIN` outside this build, of another release than the binary's). Each case gets its own `BRINDLE_SERVER_DIR`, `/tmp/brindle-e2e-<pid>-<n>` (holder socket paths under `target/` exceed the 108-byte `sun_path` limit). After the case the harness runs `brindle-remote stop`, copies the core's log to `server-core.log` in the case directory and removes the server directory; a `serve` or `hold` still running then fails the case, and is killed, and so does one that ran in a systemd scope (`brindle-serve-…`/`brindle-hold-….scope`, read from `/proc/<pid>/cgroup` before the stop), the sign of a launch that missed the isolation. The isolation (`isolate`: `BRINDLE_CONFIG`, `BRINDLE_STATE_DIR`, `BRINDLE_SERVER_DIR`, `BRINDLE_NO_SCOPE=1`, `DISPLAY`, no `WAYLAND_DISPLAY`), the server directories, the helper check and the stop step live in `tests/common/server.rs`, shared with the perf suite; every Brindle a case launches goes through `isolate` (`Run::run`, the `instance-*` cases' `Launcher` and the Windows cases' `run_with`), with the case's own variables after it. The Windows process queries (`winproc`) are in `tests/common/` too.
- Expected colors come from the `e2e` theme in the generated test config (`tests/e2e/brindle.rs`), not from built-in themes.
- The agent cases (`tests/e2e/cases/agent.rs`, each `Case::needs_fake_agent()`) play an agent with the fake ACP agent, from a script each writes into its case directory, gating the agent's steps on files the case creates (a Shell tab's `touch`, so they follow Brindle's steps) rather than sleeps. The harness finds it through `tests/common/fake_agent.rs`: `BRINDLE_FAKE_ACP_AGENT` when set, else `brindle-fake-acp-agent` beside the suite's own build (never beside `BRINDLE_E2E_BIN`), and stops when it is missing or older than `remote-agent/src/fake_acp/`, naming the command to build it: `cargo build -p brindle-remote-agent --bin brindle-fake-acp-agent` (with `--release` for a release build; plain `cargo build` builds it too). `agent-broken` needs the `SinkPanic` fault switch, so it skips on a release build.
- `BRINDLE_E2E_BIN` tests another binary (default: this build's), such as an installed or unpacked release: the harness finds the helper beside it as Brindle does (on Linux an archive's `brindle-remote-linux-x86_64` first, for local tabs and the `remote-*` cases, which then leave Brindle to find it), and since that helper has no sources here, it must report the binary's version instead (`common::server::check_helper`). `BRINDLE_E2E_SLOW=2` doubles every delay, Brindle's step spacing included (through `--step-interval`). `BRINDLE_E2E_DISPLAY` picks the X display (default `:0`).
- Every wait a case makes goes through `tests/e2e/wait.rs`'s `Scale` (`ctx.scale()`, `Copy` so a `call_at` closure can carry it: `secs`, `poll`, `eventually`, `observe_for`), so its limit stretches with `BRINDLE_E2E_SLOW` and a passing run never reaches it; a delay in a pane's shell waits for a file the case creates (`Gate` in `cases/mod.rs`) rather than sleeping. An offset measured against one of Brindle's own unscaled limits isn't a test delay: it is written unscaled, through `Run::dump_after_last_step`, with the limit named beside it.
- The `remote-*` cases (`tests/e2e/cases/remote.rs`) run Brindle against disposable Docker containers built from `tests/fixtures/remote` (an SSH server) and deploy the sibling `brindle-remote` helper (`cargo build -p brindle-remote-agent`). Without a Docker daemon or the helper they skip; `BRINDLE_REMOTE_E2E_REQUIRED=1` turns that into an error. They read the container's server with the deployed helper's `list` through `docker exec`. `remote-ssh-network` puts its container on a Docker network of its own (`brindle-e2e-net-*`, at a fixed address, removed with it) and cuts it with `docker network disconnect`, so it takes about a minute. `remote-agent-ssh` opens an agent profile over SSH, runs a turn, lets the agent exit and continues it by resume (swapping the agent's script in the container first), copying the static fake ACP agent (`target/x86_64-unknown-linux-musl/release/brindle-fake-acp-agent`, which README.md's static helper build also builds) into its container; it skips when that is missing, an error with `BRINDLE_REMOTE_E2E_REQUIRED=1`, and stops when it is older than its sources. `remote-agent-login-terminal` copies it in the same way and runs an SSH agent profile's terminal login in the container: the login program exits 0, and the agent is started again there.
- A case that sets a fault switch declares it (`Case::needs`, `tests/e2e/switches.rs`). The runner asks each binary once (`--list-fault-switches`) and skips a case whose binary lacks one, saying which binary and why (a `--release` run, or `BRINDLE_E2E_BIN` naming a release build). `BRINDLE_E2E_SWITCHES_REQUIRED=1` makes that a failure, and `Run::env` refuses an undeclared `BRINDLE_TEST_*` variable.
- `BRINDLE_REMOTE_DOCKER_TEST=1 cargo test -p brindle --locked remote::client` is an opt-in transport test with no GUI, against real `docker exec` and OpenSSH containers (`client.rs`'s `docker` module). Remote tabs' sessions go through the relay as `Terminal::spawn` starts them (`Session::start_with` on the profile's `Host`, through `local::shared_with`), and the relay's link through the production dial (`relay::dial_with`): `docker_transport_scenarios` (sessions that exit, a missing container, a container killed under a session, a round trip with resize and the host's `PROCESS`, the login shell and the home fallback for a missing directory, a helper that isn't one, Alpine's busybox, and one root-owned helper kept), `ssh_transport_scenarios` (a round trip, Ctrl-C during a flood, a wrong key, noisy `~/.profile` and `~/.bashrc`) and `relay_launch_scenarios` (a warm SSH launch is one `ssh` process, a container's helper is deployed once and reused by root and by another user, and a directory another user made where the helper goes is refused with nothing run from it). It runs the static helper at `target/x86_64-unknown-linux-musl/release/brindle-remote`, built with the Docker command in README.md; rebuild it after changing helper code, or the test runs a stale one. The tests pass that helper to the relay's dial (`relay::dial_with`, `local::shared_with`), never through the environment, so they set no `BRINDLE_REMOTE_AGENT` and need no filter; they take turns only because two of them build and run the SSH fixture's image.
- Each case's config, dumps, logs, captures (`.ppm`) and transcripts are kept in `target/tmp/e2e/<case>/`.

### Performance suite

`tests/perf/` is a separate opt-in target that reports numbers rather than pass/fail, so it isn't part of e2e:

```sh
cargo build --release                              # it times target/release/brindle
BRINDLE_PERF=1 cargo test --test perf              # every case (opens windows: ask first)
BRINDLE_PERF=1 cargo test --test perf -- --self-test
BRINDLE_PERF=1 cargo test --test perf -- --list --shard 1/2  # every 2nd selected case, from the 1st
```

- Cases: `latency-shell` (`--latency-bench`), `throughput-brindle` (vtebench at a pinned commit, fetched into `target/perf-tools/vtebench`) and `agent-markdown-stream` (`tests/perf/agent.rs`: the fake ACP agent, found through `tests/common/fake_agent.rs` beside the release build, holds a 64 KiB Markdown reply with a 1,500-line fence behind a gate the case opens once the agent has the prompt, then sends it in 2,048 32-byte `agent_message_chunk`s, and in a second run as one chunk; each time runs from the gate to Brindle's exit, a `--wait-for` of the reply's last line then `--action quit`, so both include one step interval (1 s); `summary.toml`'s `[stream]` table keeps both times and their difference. The agent writes its chunks back to back, so Brindle's pacing merges them into a few absorbs: it measures a burst, not a reply trickling in over seconds. It skips without the fake agent, and stops its terminal server between the runs, keeping each run's server log in `streamed/` and `whole/`).
- Under `scripts/with-xvfb`, which sets `BRINDLE_PERF_DISPLAY` to its display, the cases open no windows on the desktop.
- Each run goes to `target/tmp/perf/<UTC time>/` with a `summary.toml`. `BRINDLE_PERF_BASELINE=<run dir>` prints changes against an earlier run.

The suite needs `brindle-remote` beside the release binary (`cargo build --release` builds it) and stops when it is missing or older than its sources. The run notes say `server = "private per case"`, which tells runs from before this apart (they used the user's server).
- Filters, `--list` and `--shard K/N` (round-robin after the filters) select cases as in e2e.
- `tests/common/` holds what both suites share (`Result`, `ensure!`, the case selection `Selection` with `parse_shard`/`take_shard` and their self-test, and `server.rs`: the isolation, server directories, helper check and stop step; `winproc.rs` on Windows).

## Architecture rules

`docs/architecture/` holds the normative rules, which review cites by short name and number (`fcis R2`, `process R5`). Its `README.md` has the dependency rule, a "read by layer" table and the exceptions in force. Read the **Rules** section of the docs for the layer you are changing before any non-trivial change. The "Architecture" section below describes how the code works today; those docs say what a change must keep true.

Dependency rule: `brindle` and `brindle-remote-agent` → `brindle-ui`, `brindle-term-core`, `brindle-remote-protocol`, `brindle-transcript` (the helper never names `brindle-ui`, and alone names `agent-client-protocol-schema`, in `src/acp/` only). The two binaries never reference each other, the shared crates never reference each other, and each crate below the app has a closed dependency list. `tests/architecture.rs` checks this and a few source rules as part of plain `cargo test` (alone: `cargo test -p brindle --test architecture`). When it fails, change the code, or change the rule in its doc and the test in the same commit; never loosen the test alone.

- `functional-core-imperative-shell.md` (`fcis`): decisions are pure functions and GPUI-free models; entities, threads and loops only gather, call and apply.
- `railway-oriented-programming.md` (`railway`): expected failures are values, shown on the tab or endpoint that failed; decoders never panic.
- `illegal-states-unrepresentable.md` (`types`): closed enums, stable identities, units kept apart, parsing at the boundary.
- `ports-and-adapters.md` (`ports`): the crate boundaries, and one seam per platform concern.
- `process-architecture.md` (`process`): holder and core, versioned protocols, readiness loops, upgrades, the UI thread.
- `testing-architecture.md` (`testing`): which layer a test belongs in, hermetic runs, how flakes are fixed.

The rules broken most often:
- A decision written inside a view, a thread or a loop handler, or pure code that reads the clock or the environment (`fcis R1`–`R3`). Put it in a pure function or model that takes `now` and the values as arguments, with unit tests in the same file.
- A `cfg(windows)`, `cfg(unix)` or `cfg(target_os)` outside the seam that owns the concern, or a platform type in the server core or holder (`ports R4`, `R5`). `tests/architecture.rs` (`platform_cfgs_stay_in_their_seams`) rejects such a `cfg` in production code outside the seams and the files on `docs/architecture/README.md`'s `ports R4` row; test code may pair platforms.
- A wire change that isn't additive, or a new message without a new negotiated version and transcript tests (`process R4`–`R6`).
- A `_ =>` arm on one of Brindle's own enums, or a panic on bytes from outside the process (`railway R3`, `R5`).
- Work on the UI thread, or IO in `render` or `prepaint` (`process R13`, `R14`).
- A sleep, retry or longer timeout to make a test pass, or a GUI check as a one-off script (`testing R9`, `R13`). `tests/architecture.rs` rejects `std::thread::sleep` in `remote-agent/tests/**` (outside `support/wait.rs`) and `tests/e2e/cases/**`, and a process-wide `set_var` or `remove_var` in any test (`testing R7`, `ports R10`); a sleep in a `src/` unit test is review's.

`.claude/rules/` holds a short path-scoped reminder per layer, and `openspec/config.yaml` carries the design and task rules that follow from these docs. Use the `architecture-review` skill to check a diff or a design against them.

## Architecture

Data flows **terminal server session → `Terminal` (model) → `TerminalView` (input) → `TerminalElement` (paint)**, with `Workspace` owning the tabs of one window.

`docs/code-map.md` describes how each area works today: read its entry before changing that area, and update it in the same change. Its entries, in order: `terminal/` (backends, program status, links, parsing and shell integration, the notice line, Windows programs, the event channel and pacing), `remote/` and the relay, the terminal server (directories, pipes and access, detached starts, per-build copies, the platform layer, holder, ConPTY, core, protocols, checkpoints and replay, upgrades, management, relay, tests), Brindle's client (reattach, sessions palette), `terminal_view.rs`/`terminal_element.rs`, grid geometry, `workspace.rs` (models, zones, tab strip), `instance.rs`, `settings.rs` (config line, transient notices, the settings dialog and its sections), `theme.rs`, `find_bar.rs`, `notify/`, `desktop.rs`, `actions.rs`, `picker.rs`, `brindle-ui` and `text_input.rs`.

GPUI 0.2.2 doesn't cache views by default, so any `cx.notify()` re-renders the whole window. Keep I/O, allocation-heavy work and lock contention out of `render` and `prepaint`.

## Delegation

This section is for the session the user is driving. A subagent carrying out a routed brief runs its own builds and tests inline and does not delegate further.

When the `route` skill (`/route:route`, from the route plugin) is enabled, delegate through it. It picks the model and effort from the brief, so never give the Agent tool a model or effort it did not choose, and while orchestrating, never do inline what you would otherwise delegate. When route returns `split: true`, route the parts separately or say in the brief why they stay together. When route is off, the delegation decisions are yours; do a task of a few tool calls inline.

Either way, chores whose output is large get a brief of their own, written as the commands to run and what to report: `cargo build --release --locked`, full `cargo test` and e2e runs, `openspec archive`, and the version and `Cargo.lock` checks from `.github/workflows/ci.yml`. Don't fold them into an implementation brief. A CI log read (`gh run view --log-failed`) is such a chore unless you filter it to the failure first (`grep -E '\.\.\. FAILED|panicked at|##\[error\]'`).
