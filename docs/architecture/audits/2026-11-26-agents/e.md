## Findings

### E-1: A pointer press on anything in an agent zone that isn't a focusable control moves keyboard focus to the zone tree, off the prompt
- Severity: high
- Confidence: confirmed (every hop read; the manual check "a pointer press into an inactive agent zone focusing it" would contradict this if it was seen to pass, so it is worth re-running with the dump's focus line)
- Category: correctness (focus, accessibility)
- Where: `src/zone_view.rs:2220` (`ZoneTreeView` root `.track_focus(&self.focus_handle)`), `src/zone_view.rs:2055-2065` (agent zone's capture handler), `ui/src/components/reasoning.rs:86`, `ui/src/components/tool.rs:162` (div `on_click`, no `prevent_default`), `src/agent/view.rs:977-987` (message copy `Button` without a focus handle), `src/agent/view.rs:848-856` (Earlier row), `ui/src/components/message_scroller.rs:393-403` (scroll-to-end button); gpui `elements/div.rs:2025-2037`.
- Scenario: gpui's tracked-focus listener focuses the element's handle on any bubble-phase mouse down over its hitbox that nobody `prevent_default`ed. The innermost focus-tracking ancestor of an agent zone's conversation is `ZoneTreeView`'s root, whose handle is not the zone's (`ZoneTreeView::focus_handle` returns the active zone's, but the tracked one is the tree's own). So a press on message text, a thought's "Thought" trigger, a tool row's line, a message's copy button, the Earlier row or the scroll-to-end button focuses the tree's handle. In an inactive zone the capture handler first focuses the prompt (`focus_zone`), then the bubble takes it away again. Afterwards: typing goes nowhere, escape (`agent_cancel`), tab (the zone's `UiFocusScope`), shift-pageup and the `AgentZone` actions are not on the dispatch path (the tree's node is above `AgentView`), until the user clicks the prompt. The code already knows the pitfall: `CodeBlock` and `Diff` copy buttons and the header's `inert` wrappers prevent the default for exactly this reason (`zone_view.rs:2122-2135`), but the conversation's own controls and text don't. No test presses into an agent zone inside a `ZoneTreeView` (`view/tests.rs:741` clicks a copy button in a bare `AgentView`).
- Fix: one rule at `AgentView`'s root: a bubble-phase left `on_mouse_down` that, when the press wasn't taken (`!window.default_prevented()`), calls `brindle_ui::focus_from_pointer(prompt_handle)` (which prevents the default, so the tree doesn't take it). That also covers the inactive-zone case, so the capture handler only needs to make the zone active. Add a `VisualTestContext` test in `zone_view.rs` pressing a thought trigger and message text and asserting the prompt keeps focus (`process R14` unaffected; restores the spec's "Keyboard focus SHALL go to the prompt input when the zone is focused").

### E-2: While scrolled away, splicing the item at the top of the view resets its offset to 0: the view jumps to that item's start (streaming parts, thoughts, tool output, and every config reload)
- Severity: high
- Confidence: confirmed
- Category: correctness
- Where: `ui/src/components/message_scroller.rs:237-248` (`splice` passes straight to `ListState::splice`); gpui `elements/list.rs` `splice_focusable` (`if old_range.contains(item_ix) { *item_ix = old_range.start; *offset_in_item = px(0.) }`); triggers `src/agent/model.rs:1820-1827` (an agent message's changed tail), `:2135-2145` (a thought is one item, spliced on every chunk), `:1846-1863` (an open tool row's growing last run); `src/agent/view.rs:487-498` (`set_profile` splices `0..count`), called for every zone by `ZoneTreeView::restyle` (`zone_view.rs:1467-1476`) from `Workspace::apply_config` (every config reload), `set_profile_preview`/`set_theme_preview` (every settings-dialog preview step) and `end_previews` (closing any overlay after a preview).
- Scenario: a long reply streams a 1,500-line fence (one part, about 3,000 px). The user scrolls up 600 px to read it while it streams (`Follow::Away`, `logical_scroll_top = (k, 2,400 px)`). The next paced absorb splices `k..k+1`; gpui sets the top to `(k, 0)` and the view jumps 2,400 px to the fence's first line. The same happens reading a long thought while it streams (every chunk re-splices the whole thought), or the open output of a running command. Separately, with the view anywhere above the end, any config reload or settings preview splices `0..count` and the view jumps to the first held entry. The spec's "Reading back: the lines in view stay put" is broken. `refresh_top_row` already works round exactly this reset for item 0 (`message_scroller.rs:219-223`), so the behaviour was known for the top row but not generalised; `a_growing_last_item_stays_in_view` only covers `AtEnd`.
- Fix: in `MessageScroller::splice`, when `follow == Away` and the top item lies in the spliced range and `count > 0`, restore `ListOffset { item_ix: top.item_ix.min(start + count - 1), offset_in_item: top.offset_in_item }` after the splice (a growing item keeps its offset; gpui's layout tolerates an offset past a shrunk item's end). In `AgentView::set_profile`, splice only when the size changed (colours don't change a measure). Test: a scroller test where the top item grows while away and an item 10 px into view keeps its bounds, plus `set_profile` with an unchanged size leaving `scroll_top()` alone.

### E-3: A focused permission button that is off-screen isn't drawn, so the zone's keys stop working
- Severity: medium
- Confidence: confirmed
- Category: correctness (accessibility)
- Where: `src/agent/view.rs:305-320` (`FocusStops` includes the pending permissions' handles), `:507-513` (splices without focus handles), `ui/src/components/message_scroller.rs:240`; gpui `list.rs` `layout_items` (an off-screen focused item is drawn only when its `ListItem` carries a focus handle, i.e. `splice_focusable`), `window.rs:3982-3990` (a focus id not in the rendered frame dispatches from the root).
- Scenario: the user is scrolled up reading (`Away`) when a permission request arrives below the view, or tabs to a permission's reject button and then wheels up. Tab from the prompt focuses the off-screen button (`FocusScope::step`), and nothing scrolls it into view. The list doesn't draw it, so the next frame's dispatch path is the window root's: enter, tab (the zone's `UiFocusScope`), escape (`agent_cancel`) and the `AgentZone` page keys do nothing, and focus never returns (no focus-lost listener, `sync` only moves focus when a stop disappears). The spec's keyboard path requirement fails exactly when attention matters.
- Fix: when focus lands on a permission (or login) stop, reveal its block: `AgentView` records each permission block's index and calls a new `MessageScroller::reveal(ix)` (gpui's `scroll_to_reveal_item`) from an `on_focus_in` on each handle; alternatively splice permission blocks with `splice_focusable` and a handle that contains the buttons. Test: tab to a permission while away, and its buttons are drawn and enter answers it.

### E-4: A zone that last drew its Earlier row in view keeps fetching pages while it is hidden, loading the whole log
- Severity: medium
- Confidence: confirmed (the precondition, a held page shorter than the zone while following its end, is the usual short-newest-page case)
- Category: performance / memory
- Where: `src/agent/view.rs:400-414` (`follow_earlier` asks `fetch_if_due(true, true)` whenever `top_row_in_view()`), `ui/src/components/message_scroller.rs:237-248` (`top_in_view` is cleared on a prepend only when `Away` and the row is the top item), `:360-381` (only a drawn frame updates it), `src/agent/model.rs:1569-1576`.
- Scenario: the restored zone follows its end and holds a newest page shorter than the zone, so the Earlier row shows and a fetch goes out. The user switches tab. The page arrives; the reply's notify runs `sync` → `follow_earlier`; `Earlier` is `Available` again and `top_row_in_view()` is still the last drawn frame's `true` (a hidden tab draws no frame), so another fetch goes out, and again on each reply, until the server's log start (up to the 16 MiB `LOG_LIMIT`), each page's Markdown rendered on the UI thread and kept. While visible, the next frame would have stopped it once the view filled.
- Fix: clear `top_in_view` on every splice that inserts at the owner's start (not only the anchored one), so a fresh frame must say the row is still in view before the next fetch. Test in `message_scroller.rs`: prepend while `AtEnd` with the row in view and `top_row_in_view()` is false until the next draw.

### E-5: A top-level block is one list item of unbounded size, rebuilt and laid out on every frame it is visible
- Severity: medium
- Confidence: plausible (the cost figure is estimated, not measured)
- Category: performance
- Where: `src/agent/markdown.rs:382-392` (tables bounded in columns only), `:366-381` (lists unbounded), `src/agent/model.rs:357-371` (one block per part), `ui/src/components/response.rs:557-641` (a list or table is one element tree), `ui/src/components/code_block.rs:41-46,97` (`shown_code` copies the whole code per render); gpui `list.rs` `layout_items` (`if visible_height < available_height || size.is_none()`: visible items are rendered and laid out on every frame; a cached size is used only off-screen).
- Scenario: virtualization stops at the part. An agent's 1,000-row, 4-column table or a 1,000-item list is one item of roughly 5,000 divs and 4,000 `StyledText`s, rebuilt and laid out by taffy on every frame it is visible: every paced absorb, every motion tick (10/s for the whole turn while the working row shows) and every hover redraw. A 64 KiB fence is copied once per frame by `shown_code` and its lines hashed by the line-layout cache. `agents-markdown` decision 6 says "the list lays out only the changed tail"; that holds for measurement of off-screen items only, so its cost model understates per-frame work for large visible blocks.
- Fix: split large blocks into continuation parts in `markdown::render` (tables and lists in runs of N rows or items, joined frames as `CodeBlock::joined`/`Diff::joined` already do for tool output), so each list item is bounded; compute the shown text once (a `shown` field on `Code`, filled by the renderer) instead of in `CodeBlock::render`. The perf suite's `agent-markdown-stream` could gain a table case.

### E-6: `AgentUpdate::Working` reads the model's length at flush time, not at emit time: a working-row removal can miss and leave ghost items
- Severity: low
- Confidence: confirmed
- Category: correctness
- Where: `src/agent/view.rs:514-522`; `src/agent/mod.rs:668-697` (a chunk's events are applied in one `update`, so emitted events reach the view after all of them), `:747-759`.
- Scenario: in one drained chunk, absorb 1 ends the turn (emits `Splices` then `Working(None)`) and absorb 2 adds a block (emits `Splices [L..L, +1]`). The view handles `Working(None)` with `len = L+1` (final) while the scroller holds `L + 1` items, so `working_splice` removes `L+1..L+2`, past the end: nothing goes. The scroller ends with one item more than the model's blocks; that trailing index renders an empty div. Each such chunk adds another zero-height ghost; the page keys' `below` and `last_bottom` then use a ghost as the last item.
- Fix: carry the length with the event (`AgentUpdate::Working { row, len }`, the model's `blocks().len()` when absorbed), or fold the working row into the model's own splices so the view applies one ordered list.

### E-7: Every modifier change re-renders the whole window while an agent zone has focus
- Severity: low
- Confidence: confirmed
- Category: performance
- Where: `src/agent/view.rs:1179`.
- Scenario: typing a capital letter in the prompt sends shift down and up; each `ModifiersChangedEvent` calls `cx.notify()` on the view, a whole-window render (gpui 0.2.2 caches no views), doubling or tripling the renders while typing in a long conversation. The redraw is only needed when `control` (the link gesture) changes.
- Fix: keep the last `control` state in the view and notify only when it flips (or only when the pointer is over the zone).

### E-8: The remeasure policy is inverted: a reload remeasures every item for no change, a zoom remeasures nothing
- Severity: low
- Confidence: confirmed
- Category: correctness
- Where: `src/agent/view.rs:487-505`; `src/workspace.rs:2908-2911` (`change_font_size` only refreshes windows; the view's Settings observer runs `sync`, which doesn't splice).
- Scenario: an agent zone without a profile font size follows the terminal size in effect (`text_size`), zoom included. After ctrl-+, visible items are re-laid out, but every off-screen item keeps its old cached height, so a scroll's position, the leading overdraw and the page keys' "hidden above" work from stale heights and the view jumps as items come into view; an away view's `offset_in_item` now points at another line. Meanwhile every config reload remeasures everything (and, by E-2, jumps).
- Fix: have the view remember the size it measured at and splice all (with E-2's anchoring) from its Settings observer when `text_size` changed, and not from `set_profile` otherwise.

### E-9: An agent's "needs permission" notification shares the tab's OSC token bucket, and is dropped silently when it is empty
- Severity: low
- Confidence: confirmed
- Category: correctness
- Where: `src/notify/policy.rs:150-164` (`(tab, is_bell)` bucket, `OSC_PER_TAB` 3 per 2 s), `src/notify/mod.rs:413`.
- Scenario: since `zones-mixed-tabs`, one tab can hold a terminal whose build emits OSC 9/777 notifications and one or more agents. Three terminal notifications within two seconds empty the bucket, and an agent's blocked notification in that window is never sent or retried, though the agent now waits on the user. Not an agent acting unseen (it is blocked), hence low.
- Fix: give `Source::Agent` its own bucket (key `(tab, Source class)`), or exempt `State::Blocked` from the per-tab limit, keeping the global cap.

## Structural observations
- **Scroll anchoring belongs wholly in `MessageScroller`.** E-2, E-4 and E-8 are the same gap: the owner splices blindly and the scroller passes gpui's splice through, special-casing only the top row. One `splice` that preserves the top item and offset when away, clears `top_in_view` on any prepend, and a `remeasure_all()` that does both, would fix all three in the crate that owns the list (`ui/` stays app-agnostic).
- **Make the working row part of the model's list.** The model owns `blocks`, the view owns a trailing extra item and patches it with `working_splice` from a length read at the wrong time (E-6). If `ChatModel` emitted the working row as its last `Block` kind (or emitted the working splice in its `Splices`), the view would apply one ordered stream and `working_splice`/`self.working` would go.
- **A pointer-focus rule per zone body, not per control.** Focus behaviour on presses is spread over `zone_view.rs`'s capture handler and `inert` wrappers, `CodeBlock`/`Diff`'s `prevent_default`, and `focus_from_pointer` in components; the conversation's own controls were missed (E-1). One bubble handler at `AgentView`'s root ("a press nobody took focuses the prompt") makes it hold for every future control.
- **`workspace.rs` (5,029 lines) should lose the conversations palette.** `ConversationsPalette`, `open_conversations`, `conversations_lister_changed`/`listed`/`confirmed`, `show_conversations`, `take_conversations`, `close_palette_chooser`, `open_here`, `open_placed` (about 300 lines, `workspace.rs:391-405, 1493-1780`) are one responsibility with its own state and lifetime rule (the chooser must be closed on every exit path); `workspace/` already holds `launch.rs`, `notices.rs`, `overlays.rs`, so a `workspace/conversations.rs` fits. Similarly `zone_view.rs`'s terminal-login orchestration (`on_login_zone`, `login_zone_of`, `open_login_zone`, `end_login`, the `login_for` field) is agent-specific and could be `zone_view/login.rs`; the `ZoneContent` closed enum itself is the right seam and its exhaustive arms read well.
- **Per-absorb view work scales with the conversation.** `AgentView::sync` runs on every agent notify (every paced absorb while streaming): `pending_permissions()` scans all blocks, `stops()` runs twice, `prompt_state` asks `Agent::offer`, which looks the profile up in the config. Each is small, but with the model's own `refresh_facts`/`refresh_rows` (all entries per absorb, reviewer D's area) it is O(N) UI-thread work per frame of streaming; the model could keep the pending permissions as a set updated on change.
- **`markdown.rs` is clean.** Parse is linear, bounded in depth and columns, panic-free on input, and `link_action` is the single pure decision for links; nothing opens without the ctrl gesture (`link_press` → `wants_links`), and the confirmation path plans again before opening. Its only gap is size per part (E-5).
