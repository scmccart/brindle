## Violations

1. `remote-agent/tests/support/mod.rs:408,410,437,447,457,464,512,514,1038,1044,1051,1169,1186` (13 cfg attributes, plus `:20` gating `pub mod relay`) — ports R4, MUST — "A platform concern MUST have one seam, and code outside it MUST NOT carry a `cfg` for that concern." The test seam is `support/unix.rs` and `support/windows.rs`. `mod.rs` also carries cfg pairs for the program to run, the environment and the hang-up exit code, e.g. `#[cfg(unix)] pub fn shell(...) { spawn(session, "/bin/sh", &["-c", script]) }` / `#[cfg(windows)] pub fn shell(...) { spawn(session, "cmd.exe", ...) }`, and `#[cfg(unix)] assert_eq!(code, None, ...)` in `assert_hung_up`. `remote-agent/tests/support/` is not named in the ports R4 exception, so no tag. Fix: move these per-platform items into `unix.rs`/`windows.rs` (same names, as the module doc already says) and leave `mod.rs` cfg-free. Caveat: testing-architecture's "Platform pairs" idiom prescribes `#[cfg(unix)]` pairs in tests, so the two docs pull against each other here.

2. `remote-agent/tests/support/programs.rs:11,13,17,22,30,35,41,46,52,57` (10 cfg attributes) — ports R4, MUST — same words. Each helper (`ENTER`, `echoer`, `echo_of`, `exits_after_a_line`, `sleeps`) is a cfg pair choosing the program per platform, outside `unix.rs`/`windows.rs`, e.g. `#[cfg(unix)] pub fn sleeps() -> Spawn { client_spawn("sleep", &["1000"]) }`. No exception covers it. Fix: define the per-platform program table in `unix.rs`/`windows.rs` and re-export through `programs.rs`. Same caveat as 1.

3. `remote-agent/tests/upgrade.rs:10,16,25,31,63,69,80,82,173,185,210,342,344,399,406,467` (16 cfg attributes) — ports R4, MUST — same words. Examples: `#[cfg(unix)] let image = fs::read_link(format!("/proc/{pid}/exe")).unwrap();` against `#[cfg(windows)] ... win::image_path_of(pid)` in `runs_the_built_binary`; `other_build_copy`, `exits_at_startup` and `printed` as cfg pairs; `#![cfg(any(target_os = "linux", windows))]` at line 10. A test file outside any seam and not named in the exception. Fix: a seam-style `support` item per platform (`process_image(pid)`, `other_build_copy`, `printed`) so the test body is cfg-free; the Linux-only relay tests (`:399`, `:406`, `:467`) are the one case where a cfg is a feature gate rather than a pair. Same caveat as 1.

4. `remote-agent/tests/upgrade.rs:366-381` — testing R8, MUST — "A test MUST assert the rule, not a number that depends on timing or machine speed." `assert!(stepped_down.elapsed() < Duration::from_secs(10), "a core came back after {:?}", ...)` asserts a wall-clock bound measured from `Instant::now()`, next to an `eventually(Duration::from_secs(20), ...)`. The rule under test is that the holder starts its own core after the core grace and backoff; the 10 s figure depends on machine load. Fix: drop the elapsed assertion (the `eventually` already proves a core came back), or assert on the holder's own log line for its supervision start rather than on elapsed time.

5. `remote-agent/tests/support/mod.rs:47`, `remote-agent/tests/upgrade.rs:368,378` — testing R7, MUST — "To wait, poll for the condition within a scaled limit." The limits are fixed constants: `pub const TIMEOUT: Duration = Duration::from_secs(30);` (the comment says "Long enough for a loaded CI machine"), plus the hard-coded 20 s and 10 s in `a_next_core_that_wont_start_is_replaced_by_the_holders_own`. Nothing scales them (`BRINDLE_E2E_SLOW` reaches only the e2e harness). Fix: make `TIMEOUT` the one place a factor is applied (read once, e.g. a `BRINDLE_TEST_SLOW` factor passed through a `OnceLock`) and use it in `upgrade.rs`. Confidence: moderate; the rule's wording names scaling, and the real-process tests have no scaling mechanism at all.

## Design smells

- `support/mod.rs:1-5` says `unix` and `windows` export "the same items", but they don't: `stays_blocked`, `signal_set`, `program_of`, `context_switches`, `pass_fd_as`, `send_exec_error_down_fd_3`, `start_with` exist only in `unix.rs`; `working_set_kib`, `Window`, `CONSOLE_WINDOW`, `cmd_title`, `inherited_env` only on Windows. Fine while the users are cfg-gated, but the module doc overstates it.
- `support/unix.rs:138-146` and `support/relay.rs:60-71` repeat the same `ExecutableFileBusy` retry loop; one helper would keep the documented cause in one place.
- `support/windows.rs:203-226` `connect` retries `ERROR_PIPE_BUSY` in an unbounded `loop` (each `WaitNamedPipeW` is 5 s), so a pipe that stays busy hangs the test instead of failing at `TIMEOUT`.
- `upgrade.rs:29-32,72` (Windows) `QUIET = 1 s` decides when "the session has printed everything" by waiting for silence (`output_until_quiet`); `support/unix.rs:293-325` `stays_blocked` does the same with `BLOCKED_FOR = 250 ms`. Both are time-based quiet windows, not conditions; the unix one documents why it isn't a fixed sleep, the Windows one doesn't.
- `support/relay.rs:21-29` `IDLE = 1500 ms` / `HEARTBEAT = 300 ms` make the liveness tests (in `tests/relay.rs`, outside this batch) depend on real-time ratios under load.
- `support/windows.rs:394-419` finds server processes by parsing `core[pid]`/`holder[pid]` out of log text, so a log format change silently makes `TempDir::drop` leak roles on Windows.
- `support/windows.rs:599-603` `printed_window` and `support/mod.rs:1062-1089` (`numbered_line`, `check_lines`) are small parsers/checkers with no tests of their own; they are test support, so fcis R8 doesn't strictly reach them.
- `support/mod.rs:976-977` `attach_until` sleeps 50 ms between attach attempts; it is bounded by `TIMEOUT` and is a poll, so not a violation, but each try attaches and detaches a real session.
- `upgrade.rs:462-463` a string literal contains a literal line break instead of `\n` (`"no {entry:?} in` newline `{logs}"`); harmless, inconsistent with the other asserts.
- `support/mod.rs:1054` and `windows.rs` `inherited_env` read the test process's environment into spawns (read only, not a violation of ports R10).
