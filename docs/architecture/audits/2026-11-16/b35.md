## Violations

1. tests/e2e/main.rs:25, 126, 128, 138, 156, 208, 223, 298, 315, 340, 342, 345, 352, 376, 393, 434, 453, 455 — ports R4 (MUST) — "A platform concern MUST have one seam, and code outside it MUST NOT carry a `cfg` for that concern" — `#[cfg(target_os = "linux")] let has_display = x11rb::connect(...)`, `#[cfg(unix)] ... Command::new("kill")` / `#[cfg(windows)] winproc::kill(pid)`, the two `server_processes` bodies, `cfg!(windows)` in `server_dir`, `stop_server`, `save_logs` and `end_roles`, and the `#[cfg(windows)]` self-test entries. 18 sites, all in the harness's `main.rs`, which is not in the seam list. The file is NOT named in the ports R4 exception, so none is tagged. Smallest fix: move the per-platform pieces (display probe, process kill, `server_processes`, server-dir choice) into one `tests/e2e/platform/{unix,windows}.rs` module pair with the same item names, and let `main.rs` call them with no cfg. Or have the doc name the harness as a seam. The `server_processes` pair already has the same name and signature on both platforms, so that part is a seam in all but location.

2. tests/e2e/cases/status.rs:93 — testing R5 (MUST) — "Every delay scales with one factor (`BRINDLE_E2E_SLOW`), the app's own step interval included" — `let report = r"sleep 3; printf '\033]7501;state=blocked:kind=auth:app=brew\033\\'; sleep 30\r";`. The case needs the report to fire after the `new_tab` step. That step comes one step interval later, which `Run` stretches by `ctx.secs`, but the 3 s in the shell command is fixed. At `BRINDLE_E2E_SLOW` of 3 or more (a 3 s step interval or longer) the report fires before the second tab opens, and the case's outcome changes. Smallest fix: build the sleep from `ctx.secs(3.0)`, or drive the order with `--wait-for` and a second step.

3. tests/e2e/cases/status.rs:38 — testing R5 (MUST) — same rule — `read -rs -t 3 -d '\\' r` in the OSC 7501 query line: a fixed 3 s wait for the reply, not scaled. `query.rs` scales its equivalent (`{T}`). Smallest fix: format the 3 from `ctx.secs(3.0)`.

4. tests/e2e/cases/win.rs:495-502 — testing R5 (MUST) — same rule — `Start-Sleep -Milliseconds 500` before reading the OSC 11 reply in `passthrough`. It is a fixed delay and a padding wait (`--wait-for` is the rule's replacement). Smallest fix: loop on `[Console]::KeyAvailable` up to a limit built from `ctx.secs`.

5. tests/e2e/cases/win.rs:539-541 — testing R5 (MUST) — same rule — `ping -n 8 127.0.0.1` (about 7 s of real time) checked at `dump_at 4.0`, which stretches with SLOW. At SLOW of 2 or more the dump (8 s or later) can come after ping has exited, and `title == "PING"` fails. The program's duration is fixed while the dump time scales. Smallest fix: compute the ping count from `ctx.secs(dump_at)`, or run something that waits for a condition (a `--wait-for` prompt state) instead of a timed program.

6. tests/e2e/cases/win.rs:765 and 777 — testing R8 (MUST) — "A test MUST assert the rule, not a number that depends on timing or machine speed" — `ensure!(took < ctx.secs(6.0) + 5.0, "took {took:.1} s");` (in `close_mid_output` and `flood_responsive`). The rule is "the window stays responsive", but the check is a wall-clock bound, which depends on runner speed (the 5 s margin is a magic number). The dump line itself arriving is the real signal: `run` already fails when Brindle "didn't exit" past `dump_at + 30`. Smallest fix: drop the extra bound and rely on the run's own deadline, or assert a rule-based fact in the dump (for example, the flood tab's `--wait-for` text appearing).

7. tests/e2e/cases/tabs.rs:132-141 — testing R9 (MUST) — "A flake not yet diagnosed is filed as an issue" — the comment on `face_top` says the device row of the face edge "varied by one between runs ... the exact cause was not chased" and the band was moved down 1 px after "two of seven runs" misread. The mitigation is labelled honestly (R11), but the comment cites no issue for the undiagnosed cause, and shows no before and after loop numbers (R10). Smallest fix: file the issue and cite it in the comment (or find the cause in the logical to device pixel derivation of the strip origin).

## Design smells
- tests/e2e/cases/win.rs:206-210: `tab_menu_background` gates its probe on `start.elapsed() < ctx.secs(4.0)` from the harness spawn. `Probe`'s own doc (win.rs:299-304) says the harness's clock and Brindle's differ by seconds on a cold start, so a time gate is the unreliable thing it warns against. It is a padding wait, not a poll on a condition (testing R7's wording, though R7 names unit and real-process tests).
- tests/e2e/main.rs:75-77: `Ctx::sleep` is a fixed-sleep helper (scaled). Its callers in other files (`restore.rs`, `multi_window.rs`) are outside this batch. The testing doc lists "sleep before an assertion" as an anti-pattern.
- tests/e2e/main.rs:287, 296, 301 and win.rs:115, 360, 712: fixed, unscaled limits (5 s, 2 s, +30 s, 120 s) on the server stop, role wait and zoom wait. They are limits, not delays, so not counted under testing R5, but under SLOW on a loaded runner they are the first to flake.
- Fixed `dump_at` and `capture_at` times (for example settings.rs:37, 121, 173 with 11.7, 13.3 and 17.3 s; zones.rs; shell.rs) are scaled by `Run`, but they are padding against step counts, not `--wait-for` conditions. The `step_time` helper is copied into five case files (`mod.rs:196`, `tab_menu.rs:12`, `zone_menu.rs:12`, `tabs.rs:70`, plus `palette.rs` and `profile_menu.rs` outside this batch). One shared helper would remove the drift risk.
- tests/e2e/cases/win.rs:80, 179, 387-390: probes return strings ("no window", "no holder", "waiting", "clicked") that callers then match with `==` or `contains`. They are stringly-typed outcomes (railway R1 and types R7 spirit), but they are test-harness polling values, so not counted.
- tests/e2e/main.rs:81, 314, 319 and status.rs:9, win.rs:381, 407, 513: `.ok()` and `unwrap_or_default()` on file reads and writes. A missing artifact or log becomes an empty value. Later assertions fail anyway, but a failed `ctx.save` is invisible. Not counted: these are test helpers.
- tests/e2e/main.rs:111: unknown `--flags` are silently ignored (needed for cargo's libtest args), so a typo such as `--shrad 2/3` runs every case without a message.
- Pure helpers with no unit test in the self-test: `tabs.rs` `measure_plus`, `distance` and `Strip::rect`; `settings.rs` `with_shell_profile_theme` and `shown_section`; `win.rs` `count`, `under`-like helpers (only `under` is self-tested). They are test code, so fcis R8 (own-file unit tests for pure functions) and testing R1 are not counted as violations. The harness's own parsers (`parse_shard`, `take_shard`, `query::replies`, `palette_reply`) are self-tested.
- tests/e2e/cases/win.rs CONFIG sets `[notifications] when = "always"` but only `passthrough` sets `BRINDLE_NOTIFY_LOG`. Any other case that causes a notification would reach the real desktop (testing R4's "touches nothing of the user's"). No case here does today.
- tests/e2e/cases/win.rs:100-134, 182-188 send `WM_*` messages to Brindle's own window with `SendMessageW`. This is allowed by CLAUDE.md and does not touch other windows, but it sits close to testing R2's "synthetic OS input" line, so keep it limited to the message set it uses.
- Every case function returns `Result<Outcome, String>` (the shared `Result` alias). It is covered by the railway R4 exception in spirit, but the tests do not compare error text, so nothing is tagged or counted.
