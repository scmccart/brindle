## Violations

1. `ui/src/components/select.rs:379-380` (and `select.rs:110`, `:115`, `:311`) — types R3 (MUST) — "An identity MUST be the value that stays stable, never a position... An index is valid only within the render or the call that computed it." — `Select` keeps its selection as a position across a refresh of its options: `set_options` runs `let selected = self.selection.selected().filter(|&ix| ix < self.options.len()); self.selection.set(selected);`. After the options are replaced, the same index names a different option, and `SelectEvent::Changed(usize)` reports a position the owner must resolve against options that may have changed since. Smallest fix: key the selection by a stable value (the option's label or a caller-supplied id), or have `set_options` take the new selection and clear it otherwise.

2. `ui/src/components/dropdown_menu.rs:102-104` with `ui/src/components/menu.rs:157` — types R3 (MUST) — same rule — `DropdownMenu::set_entries` says "an open menu keeps its own" entries, while `entries()` returns the new ones. `MenuEvent::Selected(usize)` is then an index into the open menu's old entries, delivered later (through `forward_selection`), after the owner may have replaced the list. The owner (`src/workspace.rs:368,374`) resolves it against entries that can differ. Smallest fix: make `set_entries` a no-op or an error while open, or put the chosen `MenuEntry`/item label in the event.

3. `ui/src/components/menu.rs:123-125` — types R7 (MUST) — "No sentinels: no `-1`, no `0` id, no empty string for 'none'." — `pub fn label(&self) -> &str { self.item().map_or("", |item| item.label.as_ref()) }` returns `""` for a separator. `type_char` collects these into `labels` for typeahead, so the empty string stands for "no label". Smallest fix: return `Option<&str>`, or filter separators out before `Typeahead::find`.

4. `ui/src/components/mod.rs:100-102` — fcis R8 (MUST) — "Every pure function and model MUST ship with unit tests in its own file's `#[cfg(test)] mod tests`" — `interaction` is a pure function and `mod.rs`'s test module covers only `key_activation` and `accepts_click`. It is tested in `button.rs:210-216` and `toggle.rs:220-222`, not in `mod.rs`. Smallest fix: add a small test to `mod.rs`'s `tests`, or move `interaction` next to those tests.

5. `ui/src/components/menu.rs:453-457` — fcis R10 (SHOULD) — "A new conditional in a view... handler SHOULD be questioned... it moves into the model or a pure function" — `Menu::key_down` decides inside the entity that `pageup` means `MenuNav::first` and `pagedown` means `MenuNav::last` (`"pageup" if !keystroke.modifiers.modified() => Some(MenuNav::first)`). Typeahead and space already go through the pure, tested `typed_key`, and nothing tests this mapping. Smallest fix: a pure `page_key(key, modifiers) -> Option<Step>` with a unit test.

6. `ui/src/components/menu.rs:491-495` — fcis R10 (SHOULD) — same rule — `Menu::release` builds `ReleaseOver` in the view from `item_at` and `inside`: `Some(ix) if inside => ReleaseOver::Option(ix), _ if inside => ReleaseOver::Menu, _ => ReleaseOver::Outside`. This is a three-way classification of where a release landed, untested. Smallest fix: a pure `release_over(item: Option<usize>, inside: bool) -> ReleaseOver` with a test.

## Design smells
- `ui/src/components/dropdown_menu.rs:132`, `ui/src/components/popover.rs:274`, `ui/src/components/select.rs:615`: an unmeasured trigger (`None`) becomes `Bounds::default()`, a zero rect at the window origin, and the menu is placed against that on the first frame (`select.rs:441` does the same with `px(0.)`). The `Option` is handled by defaulting rather than by a distinct case.
- `ui/src/components/menu.rs:379`: `Menu::bounds` reads "not painted yet" as `width <= 0`. It is turned into an `Option` there, which is fine, but it leans on a zero-width sentinel from `ScrollHandle`.
- `ui/src/components/select.rs:698` and `:739`: `SelectMenu` re-checks `!self.options[ix].disabled` before emitting `Picked`, although `ReleaseOver::Option` is documented as "an enabled option" and only enabled rows carry the handler. Two places decide "enabled".
- `ui/src/components/select.rs:222-226`: `(false, _) => Open` on `Activation` is a wildcard in a tuple pattern. It is not a `_ =>` arm, but a new `Activation` variant would silently open.
- `ui/src/components/select.rs:664-690`, `:792`: `SelectMenu` copies `options` and `selected` as snapshots at open. They are fixed for the menu's life, so this is safe, but they duplicate `Select`'s state with no refresh rule written beside them.
- `ui/src/components/select.rs:444` and `menu.rs:46-50`: the private `select::MenuEvent` shares a name with `menu::MenuEvent`, and `menu.rs` imports `MenuRelease`/`ReleaseOver` from `select.rs`, so `menu` depends on `select`'s pure types. The shared pointer-release model could live in its own module.
- `ui/src/components/mod.rs:130-156`: `FocusRing` mixes pure geometry (in `style::ring_geometry`, tested elsewhere) with drawing. It is fine, but the drawing half has no test here.
