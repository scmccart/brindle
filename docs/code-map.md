# Code map

How the code works today, area by area: entities, threads, protocols, files and the names to search for. It is descriptive and read on demand: the normative rules are in `docs/architecture/`, and behaviour is specified in `openspec/specs/`. Keep it current in the change that alters what it describes.

Data flows **terminal server session → `Terminal` (model) → `TerminalView` (input) → `TerminalElement` (paint)**, with `Workspace` owning the tabs of one window.

- **`terminal/`** — the `Terminal` entity wraps an `Arc<FairMutex<alacritty Term>>` and a `Backend`:
  - `Server` (Linux and Windows): a session of a terminal server, this machine's or a remote endpoint's (the terminal's `Host`, see `remote/` below); every tab with a program uses it, local or remote, with no in-process fallback: Brindle runs no PTY or pseudoconsole of its own, and alacritty's `tty` and `EventLoop` are unused. The connection's reader thread parses the session's output (`terminal/server.rs`'s `SessionSink`, with the path style from `Host::path_style`: `PathStyle::Posix` for a remote endpoint, and `process::LOCAL_PATH_STYLE` here), and input, resize and close go to the connection's writer thread. `Terminal::spawn` returns at once; connecting, a reconnect or an upgrade finish in the background with input queued, and a failure (no helper, no connection) becomes that terminal's `Terminal::message`, uncached. A local session's process info stays local, from its pid: `/proc` on Linux, and on Windows the newest descendant of the program in a Toolhelp snapshot, for the name and that process's pid (`process::newest_descendant`; the title tick's look runs off the UI thread, see `workspace.rs`), with the directory from OSC 7 and 9;9 (`process::LOCAL_DIRECTORY` says which). A reported directory is a path the program chose, so no check of it runs on the UI thread: `dir_check.rs`'s `DirCheck` (GPUI-free) keeps what is known of it, the terminal runs the check it asks for on the background executor on `Wakeup` (one at a time, the latest report last, a repeat not checked again), and `Terminal::working_directory` only reads the model; a new tab's or split's directory is named by `spawn_request` and checked on the session's own thread (`Session::start` calls the request there, `with_checked_dir` takes the answer). Restore still probes on the UI thread (`session::resolve_tab`), but only a recorded directory that is absolute in this machine's path style. `shell_integration::is_absolute_path(path, style)` (term-core) is that one rule for a path that came from a program, which `reported_dir`, the restore check and `links::plan` all call: POSIX, it starts with `/`; Windows, it is `X:\` or `X:/` and then has no `:`, no `"` and no control character, so never a UNC, device or rooted path, a stream of a file, or anything a later reader takes for more than a name. A remote session's comes from its host's `PROCESS` reports (`Session::foreground`), with OSC 7 winning for the directory; every arm that assumes the program runs here (the pid lookups, a directory checked on disk, `parent_console_to`) is gated on `Host::Local`.
  - `Remote`: a read-only message with no program (`Terminal::message`), whose text is pushed in with `feed()`; input goes nowhere. Used for error-message tabs.
  - **Program status (`status.rs`):** the OSC 7501 parser and each `Terminal`'s `Records` (one per id, the root is `""`), with the lifetime rules: `end_activity` on OSC 133 `A` and process exit (drops `working`/`blocked`), `seen` on user input (drops `done`/`error`), `reset` on `ESC c`. `handle_found` applies what the scanner found in stream order and answers the `?` query with `write`. `TerminalEvent::Status(Option<Notice>)` carries a notice when a record became blocked/done/error with a different kind, title or message. `Workspace` keeps `Tab::status` (the max over the tab's terminals) and draws it as a coloured dot before the tab's title (`TabTrigger::leading`), followed by the bell dot; `--dump-screen-after` prints the records as `--- status` lines.
  - **Progress (OSC 9;4, `brindle-term-core`'s `progress.rs`):** each `Terminal` keeps `progress: Option<Progress>` (`Normal(Percent)`, `Error`/`Paused(Option<Percent>)`, `Indeterminate`). `handle_found` sets it with `Found::progress_after` (a `Found::Progress` report through `progress::apply`, which keeps the previous percent for an error or a pause without one; `PromptStart` and `Reset` drop it), the same rule the core's `Emulator` follows; `end` (exit, loss, failure) drops it too, and the event-overload reset clears it with the records. Any change emits `TerminalEvent::Status(None)`, and the handlers that refresh the status dot refresh the bar: `Zone::progress` in `ZoneTreeView`, and `Tab::progress` (`ZoneTreeView::progress_summary`, `progress::most_pressing` over the zones: error, paused, the lowest normal, indeterminate) in `Workspace::refresh_status`. `render_tab_bar` and the zone header draw it from those cached values as a `brindle_ui::EdgeBar` (`TabTrigger::edge_bar`, `CardHeader::edge_bar`), its length and colour from `Theme::progress_bar` on the chrome theme (muted, red, yellow, muted at 40% across the width). `--dump-screen-after` prints `--- progress tab=N …` and, in a split tab, `--- progress zone=ID …` lines.
  - **Contexts (OSC 3008, UAPI.15, `brindle-term-core`'s `context.rs`):** each `Terminal` keeps `contexts: Contexts` (a `Vec` of `(ContextId, Fields)`, outermost first, the last active: a new start nests under the active one, a known id's start replaces its fields and truncates after it, an end truncates at it, an unknown end and a start past `MAX_DEPTH` (32) are ignored) and a cached `badge: Option<Badge>` (`Contexts::notable`: the innermost `elevate`/`chpriv` (`BadgeKind::Privileged`, labelled with the target user, else `elevated`) or `session` whose `targetuser` is exactly `root` (Privileged, labelled `root`: real `run0` sends that and never ends it), `remote`, `container` or `vm` (`Elsewhere`, by host or name), cut to 24 characters), recomputed in `handle_found` when `apply` reports a change, which emits `TerminalEvent::Status(None)`. `context::parse` decodes `\xHH` in ids (1–64 bytes in 0x20–0x7E, else the sequence is dropped) and values (≤ 255 bytes, UTF-8, no control character, else the field is dropped) and keeps only `type`, `user`, `hostname`, `targetuser`, `targethost`, `container`, `vm`, `cwd` and `comm`; an unknown `type` is no type. Resets and prompts leave the stack: `end` (exit, loss, failure) clears it, and so does `ChannelEvent::Replay(true)`, since the replay carries the session's stack and its `ESC c` ends nothing, and the event-overload reset (a dropped message leaves it stale). `Zone::badge` (refreshed on `Status`) is drawn in its header (`CardHeader::badge`), and `Tab::badge`, the active zone's (`ZoneTreeView::active_badge`, refreshed on `Status` and on the tree's `TitleChanged`, which a change of active zone sends), on its face (`TabTrigger::badge`), both as the `brindle_ui::Badge` that `zone_view::ui_badge` makes in `Theme::badge_color` of the tab's theme: `BadgeDraw::of` draws a privileged one as `Icon::TriangleAlert` alone in ANSI 3 (made legible on the background at 3:1), its tooltip "Running as <user>", and an `Elsewhere` one as its label in `card_muted_foreground`. The title is cut first, down to its first 8 characters, then a label badge (`brindle_ui::badge::title_and_badge`; an icon badge isn't cut). `--dump-screen-after` prints the active terminal's `--- context …` lines and `--- badge tab=N …` / `--- badge zone=ID …` lines (`describe_badge`, ending in `draw=icon|text`).
  - **Pointer shapes (OSC 22, `brindle-term-core`'s `pointer.rs`, `terminal/pointer.rs`):** each `Terminal` keeps `pointer: pointer::Stacks`, one stack of up to `STACK_DEPTH` (16) entries per screen, each a `Shape` or `None` ("no shape", which an empty set leaves and which reads as Brindle's own). The rules are kitty's (`set_pointer_shape` in `kitty/window.py`): `pointer::parse` reads a set (`=` or none: only the last name Brindle shows counts, since each replaces the top; an empty name is `None`), a push (`>`: each name Brindle shows, at most the last 16), a pop (`<`) or a query (`?`: one `Ask` per item); a set or push with no name Brindle shows parses to `None`, so it is no find. `Shape` is the 22 CSS names GPUI has a pointer for (`Shape::name`/`from_name`, one table). The reader tags each op with the screen active where it sat (`ChannelEvent::Pointer(Screen, Op)`, see "Parsing" below; `Found::Pointer` alone is `Kind::Ignored`), `Terminal::apply_pointer` applies it and writes a query's reply (`Stacks::apply` returns the whole `ESC ] 22 ; … ESC \`) with `write`. `Found::Reset`, `end` (exit, loss, failure), `ChannelEvent::Replay(true)` and the event-overload reset clear both stacks; the server keeps none (`Emulator::feed` ignores the find), so an attach starts with Brindle's own. `terminal/pointer.rs` maps each `Shape` to a `gpui::CursorStyle` (`cursor_style`; `no-drop` shares `not-allowed`'s) and picks the grid's pointer (`choose`, see `terminal_element.rs`). `--dump-screen-after` prints `--- pointer shape=NAME screen=primary|alternate` (`Stacks::describe`) while the active screen's top is a shape.

  `links.rs` finds URLs in a line of chars, decides what a click does and runs the opener (`xdg-open`, or `BRINDLE_LINK_OPENER`) on a background thread. `links::plan(uri, this_host, windows)` is the pure decision, for detected and OSC 8 links alike: `Open` (the link with `"` and whitespace percent-encoded) only for a scheme in `SCHEMES`, the list `find_url` detects; a `file:` link only with no host, `localhost` or this machine's name; on Windows `Reveal(path)` for a `file:` link, which shows it selected in Explorer (`explorer.exe /select,`, or `explore` on a directory) and never opens it, and only for a path that passes `is_absolute_path` as Windows will read it (percent-decoded, every `/` a `\`): a network path (`\\host\…`) is refused as another host, and any other as `NoDrive` (a device or rooted path, `file:shell:…`, no drive, `C:x`, a stream, a `"` or a control character), since Explorer reads more than paths and the path goes inside one pair of quotes on its command line; else `Refuse(Refusal::{NoScheme, Scheme, OtherHost, NoDrive})`. `plan_here(uri)` is `plan` with this machine's name and `cfg!(windows)`, what `open` acts on; agent zones plan their links with it before deciding (see `agent/`). `wants_links(modifiers)` (ctrl without alt) is the link gesture, shared by `TerminalView` and `AgentView`. `failure_text` words a refusal or an opener's failure; `open_reporting(uri)` opens now and later answers the failure's text (logged), and `TerminalView::open_link` emits it as `LinkFailed` (at once for a refusal, later from the opener's thread for a failure) instead of writing into the terminal: `ZoneTreeView` passes it on from any tab, and `Workspace` shows it as a transient notice on the config line (see `settings.rs`). `link_at` returns the link at a grid point: the cell's OSC 8 hyperlink, or else a URL found in the logical line, where rows are joined by `WRAPLINE`. `TerminalView` looks links up only in event handlers while ctrl is held (hover) or on a ctrl-click, never in `prepaint`, which just underlines the stored spans.
  - **Parsing and shell integration (`shell_integration.rs`, `server.rs`):** every backend parses through Brindle's own `Parser` (vte processor + OSC 133 scanner), which lives in `brindle-term-core` with `Marks` and `Records` (`terminal::{shell_integration, status}` re-export them); alacritty's own processor never sees bytes. For `Server`, `SessionSink` parses on the connection's reader thread under the term lock; `feed()` does the same for a `Remote` message. `Sink::write` scans with `scan_positions`: a chunk with no `Found::Pointer` sends its finds and then parses in one go; one with a pointer op is parsed in pieces under one hold of the locks, every find sent where it sits and each op sent as `ChannelEvent::Pointer` tagged with the screen (`ALT_SCREEN`) the parse reached, so finds keep their stream order (a push then `ESC c` leaves the stacks empty). A held replay's pointer ops are dropped (a replay holds none). Lock order is parser → term (`lock_unfair` while holding the parser) → marks. Marks are absolute lines (`base + Line`); `base` is kept by finding the row that was at `Line(0)` after each processor call (rows rotate, their cells never move), and resizes remap marks through logical lines. Synchronized-update timeouts are flushed from the GPUI side on `Wakeup`. VS Code's OSC 633 is read in the same pass: `parse_mark` takes `133` or `633` for `A`–`D`, `633;P;Cwd=` is one more `reported_dir` form (its `\\`/`\xHH` escapes decoded by `decode_vscode`, then the usual `is_absolute_path`), and `633;E;<line>[;nonce]` (or a `C` mark's `cmdline_url=`, which fish 4 writes) becomes `Split::CommandLine`, applied as `Marks::set_line` on the latest command while it has no output mark. `Command::line` is copied only, never run; the nonce is ignored. `Marks::last_command_line` returns a `LineSource` (the reported line, or the `B`..`C` span), which `Terminal::last_command_line_text` reads under the term lock for `TerminalView::copy_last_command`. `Marks::prompt_seen` is a sticky flag set by any `A` mark (kept by a clear, a prune and the alternate screen); `last_command_line_text` returns `None` until it is set, and `Workspace::open_command_palette` passes it (`Terminal::has_prompt_marks`) to `actions::palette_lists` as `PaletteFacts`, which hides Copy Last Command Line until then.

  - **Elevation (Windows: `process.rs`, `context.rs`):** `process::newest_descendant` returns the foreground process's pid with its name, so the title and the elevation name the same process. `process::elevation(pid)` opens the process (`PROCESS_QUERY_LIMITED_INFORMATION`) and its token (`TOKEN_QUERY`) and reads `TokenElevation`. It answers `Elevated` or `Standard` only from a token it read; any failure, a denial included, is `Unknown`, never inferred. Off Windows it is always `Unknown`. `process::detect(roots, &mut ElevationCache)` takes one `Snapshot` and reads the token of each foreground pid the cache doesn't hold. The cache keeps only what was read (`Standard` or `Elevated`) and is pruned to the snapshot's pids, so a reused pid is read again. The title tick runs `detect` on the background executor and applies it with `Terminal::set_detected` (see `workspace.rs`). `Terminal`'s `Notable` keeps `contexts`, `elevation` and the cached `badge`, recomputed as `context::badge(contexts.notable(), elevation)` whenever either changes: `Elevated` is `Privileged`, labelled `Administrator`, whatever the program announced; `Standard` and `Unknown` leave the announced context's badge. The pure rule and its tests are in `brindle-term-core`'s `context.rs` (`Elevation`, `badge`).
  - **Line ends (`terminal/mod.rs`, `process::LOCAL_LINE_END`):** grid copies (Copy, `copy_on_select`, Copy Last Command Output and Line) pass through `copied_text(text, LineEnd)`, which joins lines with `\r\n` where `LOCAL_LINE_END` is `CrLf` (Windows) and with `\n` elsewhere, without doubling a `\r\n`. OSC 52 text and a link's address are written as they are.
  - **Mouse clipboard feedback (`terminal/feedback.rs`, pure, in `PURE_MODULES`):** `Feedback { kind: FeedbackKind::{Copied, Pasted, NothingToPaste}, at, shown }` and `phase(now)` give `Phase::{Shown, Fading(opacity), Gone}`: shown for `SHOWN_FOR` (800 ms), then faded over `FADE_FOR` (200 ms). A new feedback replaces the old, so two never stack. `TerminalView` holds it in a `FeedbackSlot` and sets it on a mouse-up for which `finish_selection` reports a clipboard write (`Copied`), and on a right press that `right_press` says is `Paste` (`Pasted`, or `NothingToPaste` when the clipboard has no text). Keys and palette actions never set it. `TerminalView::render_feedback` draws it with no focus handle and no mouse handler: a brindle-ui tooltip surface with `Icon::Copy`, `Icon::ClipboardPaste` or `Icon::Ban` and `FeedbackKind::label` ("Copied", "Pasted", "Nothing to paste"), anchored 12 px right of and below the pointer and kept inside the grid's bounds (`Anchored::within`). Its timer task notifies the view every `FADE_FRAME` (16 ms) only while the feedback isn't `Gone`, then ends. The dump line `--- feedback kind=…` is `TerminalView::describe_feedback`.
  - **Notice line (`terminal/tab_note.rs`):** a failure that belongs to a running tab and doesn't end its session is one dim line in its terminal, as the "connection lost" line is. `tab_note::line(text)` drops every C0 and C1 control (so text from a server or a relay can't move the cursor or end the dim style) and joins lines with `; `; `NoteGate` refuses a repeat until the session prints again. `Terminal::note` writes it on the UI thread, holding it in `held_notes` while an attached session's first replay is still to come and writing it after the replay, or after a `Lost` or `Failed` line; `SessionSink::note` writes it from the connection's reader thread through the sink's gate and its held-replay path. Callers: a server `ERROR` about a shown session and a message that can't be encoded (`Connection`) and a restored tab whose profile is gone. A profile shortcut past the last profile opens a message tab. A launch's unknown profile (`brindle terminal wrk`) opens nothing: `workspace::profile_for`, one rule for the first launch and a forwarded one, refuses it as a usage error (`LaunchRefusal`). A link that isn't opened is the window's, not the tab's: it goes to the config line, never into the terminal. A relay link's lost line carries its first line of cause (`lost_line`), and the local server's give-up line its last error (`reconnect_gave_up`).
  - **Windows programs (`cmdline.rs`):** pure helpers, tested everywhere, for what Brindle asks the server to run: the default program (`windows_default_program`), the config editor's command, the merged environment (`merge_environment`) and console-default titles. Sessions' pseudoconsoles and command lines are the holder's (see "ConPTY in the holder" below).

  Alacritty events, and what the sink finds, reach GPUI through an unbounded channel drained by a spawned task, each passing the terminal's `EventGate` (`terminal/events.rs`, `Listener::send`) on its producer's thread first, which is what bounds the channel (`process R9`). `Wakeup`s, title changes, foreground reports and clipboard writes are merged at the source: at most one marker per kind waits, its latest value in the gate's slot. Life events (replay markers, exit, loss, failure, `Broken`, `InputRefused`) are always queued. Side events (bells, notifications, status reports, replies to the program's queries) are dropped from 2048 waiting until under 512 (`EVENT_MARKS`); the task then logs how many at `warn` and, if status, progress or context reports were among them, resets the terminal's `Records`, progress and contexts. The gate's mutex is a leaf lock, taken last (under the parser and term locks when alacritty sends mid-parse) with nothing taken under it. The task tells the gate once per chunk what it took (`EventGate::took`), then applies the chunk in order. Once `pace::BURST` (4) updates in a row came less than `pace::PACE` (4 ms) apart, it waits out the rest of `PACE` before the next, and each update takes ready chunks for up to `pace::BUDGET` (16 ms, `pace::drain`). Replies the emulator generates go through `reply()`, which drops them for read-only `Remote` terminals. Pointer shape ops (`ChannelEvent::Pointer`) are side events that count as status for the overload reset, which clears the pointer stacks too. `keys.rs` and `mouse.rs` are pure xterm encoders with unit tests.
- **`remote/` / `brindle-remote`** — the `brindle-remote-protocol` crate (`remote-protocol/`, re-exported as `remote::protocol`) defines the bounded frame header, the frame marker and the terminal server's protocols, shared by the app and the helper. The helper is the `brindle-remote-agent` crate (`remote-agent/`, binary `brindle-remote`): the terminal server's roles, the relay and the management commands (below). `Host` (`remote/host.rs`) is the server a session runs in: `Local`, or `Remote(RemoteTarget)`, equal when the targets name the same endpoint; each tab records its own, and its splits stay on it whatever the profile targets later. A remote profile's tabs run on `Backend::Server` like local ones, in the endpoint's own terminal server, through one connection per endpoint (`remote::local::shared(host)`, `Connection::relay`; see "Brindle's client" and "Relay" below). `client.rs` deploys a matching Linux helper and launches the relay through OpenSSH or Docker/Podman exec (`remote_command`). An endpoint keeps the helper cached by version and digest: an SSH host in the user's `~/.cache/brindle/<version>-<digest>/` (user-only), a container in root's `/tmp/brindle-helper-<version>-<digest>/` for all its users (root makes the directory, takes the copied file over, renames it into place and removes other builds' directories; a directory someone else made there is refused by name and left alone; nothing is removed when a connection ends). `client::launch` starts an endpoint's relay for `local::relay::dial_with`: one command, a script that execs the cached helper's `relay` or exits 97 (in a container, as the profile's user, when the directory or the helper isn't root's own or is a symbolic link); only on 97 is the helper deployed and the launch run once more, and ssh's own 255 is a connection error. The link (`local/{link,relay}.rs`) is the relay process's stdin and stdout from its frame marker on (`skip_preamble` drops what the shell printed first), and its stderr is kept for errors: `RELAY_HOST` first, then client protocol 2, whose `HELLO` asks for `linger_secs` (300) and `process_info`, so a remote tab's sessions outlive a dropped link and its title and directory come from `PROCESS`. The program's environment (`local/endpoint_env.rs`, pure, OpenSpec change `remote-login-environment`): the SSH launch runs `relay --login-environment`, so `RELAY_HOST` carries the endpoint's SSH-session environment (`env`, passwd basics filled in) and the login shell's (`login`: `Captured` or `Failed`; absent for a container, whose relay isn't asked). The connection keeps an `EndpointEnv` (`exec`, `Login::{NotAsked, Captured, Failed}`) per link, and its writer's `encode` re-encodes each start (`start_of`: `SPAWN`, `SPAWN_AGENT`, `AGENT_RESTART`; every other message goes as it is) with `merged`'s environment, the request's over the endpoint's: a `SPAWN` with no command runs the login shell (`Start::LoginShell`), which reads its own startup files, so it gets `exec`; a program (`Start::Program`: a command, an agent, a restart) gets the captured login environment, or `exec` with a `Fallback` when the capture failed. A fallback's line ("the login shell's environment on … wasn't read (…), so this program has the SSH session's environment") is recorded by request (`State::fallbacks`) when the start is written, and told through `SessionSink::endpoint_note` before the reply: on `SPAWNED`, a terminal writes it as a dim line before the program's output; on a restart's `OK`, or a new agent's `SPAWNED`, an agent zone keeps it as its endpoint note (`AgentEvent::EndpointNote`, `ChatModel::set_endpoint_note`), shown under a restore's note, each its own `--- note` dump line. Nothing logs a `RELAY_HOST` or a start's environment. Each side sends `RELAY_HEARTBEAT` after 10 s without a write; Brindle ends a link that read nothing for 30 s (`Timings::dead`), the relay one that read nothing for 60 s. The relay's liveness (`Liveness`, `remote-agent/src/liveness.rs`, the relay's alone) is stamped by its stdin reader thread, which drops heartbeats itself and marks itself `busy` while handing a real frame to the core, because copying output to a slow client can block and leave healthy clients' frames unread; never measure it where output is copied. A dropped link reconnects with backoff and no time limit, writing a dim "connection to … lost; reconnecting…" line into the endpoint's tabs, and a connection that isn't eager closes 5 s after it was last in use (`Timings::idle`).
- **Terminal server (OpenSpec changes `terminal-server` and `terminal-server-windows`)** — local tabs run in sessions of a persistent server, two roles of the `brindle-remote` binary (`remote-agent/src/server/`, built on Linux and Windows; `main.rs` adds the Windows-only `launch` trampoline and the Linux-only hidden `login-env` role the relay's login shell `exec`s), so sessions survive a Brindle exit, a core crash, restart or upgrade. The helper is required (`HELPER_MISSING` names `BRINDLE_SERVER_HELPER`, which `remote::find_server_helper` honours first; then Linux tries `BRINDLE_REMOTE_AGENT` and the helper beside the exe, while Windows looks only for `brindle-remote.exe` beside `brindle.exe`, since there `BRINDLE_REMOTE_AGENT` keeps naming the Linux helper for remote profiles).
  - **Directory (Linux):** `$BRINDLE_SERVER_DIR`, else `$XDG_RUNTIME_DIR/brindle`, else `~/.cache/brindle/run` (`server_dir::resolve` in `remote-protocol`, used by both sides; mode 0700). It holds `core.lock`/`core.sock`/`core.log` and `holder-<build>-<n>.{sock,lock,log}`. Socket paths must fit `sun_path` (108 bytes), which is why e2e server directories are under `/tmp`. Peers are checked with `SO_PEERCRED`. A role starts as `<role> --ready-fd N` (`platform/unix/daemon.rs`: double fork, `setsid`, stdio to its log, one ready byte). It closes the ready pipe right after that byte, and a Linux starter reads the pipe to its end and counts the role as ready only if the pipe held exactly that byte (`remote-protocol/src/ready.rs`): passing the pipe as fd 3 can replace the pipe through which `Command` reports a failed exec, and that error's 8 bytes then arrive in the ready pipe. Brindle (the core), the core (holders) and a holder (the core) start roles through `systemd-run --user --scope` in a `brindle-<role>-<hex>.scope` (`remote-protocol/src/scope.rs`), so stopping the desktop's app scope doesn't kill them; without `$XDG_RUNTIME_DIR/systemd/private` or `systemd-run`, or with `BRINDLE_NO_SCOPE=1` (the helper's tests and e2e set it), they start directly with one log line. `systemd-run --scope` execs the program itself, so roles are run as `/proc/<own pid>/exe`, not `/proc/self/exe`.
  - **Directory, pipes and access (Windows):** `$BRINDLE_SERVER_DIR`, else `%LOCALAPPDATA%\brindle\run`, or `run-elevated` for an elevated process so elevated and unelevated never share a server (`server_dir::resolve_windows`), created with a protected DACL for the user and SYSTEM (`platform/windows/dir.rs`). It holds `core.lock`/`core.log` and `holder-<build>-<n>.{lock,log}`. The pipes aren't in it but named from it (`remote-protocol/src/{server_dir,endpoint}.rs`): `\\.\pipe\brindle-server-<h>-core` and `…-holder-<build>-<n>`, where `<h>` is the FNV-1a hash of the directory's canonical path plus the user's SID string (so the directory must exist; no length limit), and the core finds holders by their lock files. The locks are `LockFileEx` (exclusive, fail immediately), released when the process dies. Every pipe (`remote-protocol/src/{access,win}.rs`) gets the SDDL `D:P(A;;GA;;;<user SID>)(A;;GA;;;SY)` plus a no-write-up mandatory label at the creator's own integrity, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` on a name's first instance, so a squatted name fails the bind (error 5 or 231, read as `AddrInUse`). Before reading anything the server checks the client (`GetNamedPipeClientProcessId`, then that process's `TokenUser` and `TokenIntegrityLevel`; `ImpersonateNamedPipeClient` fails until a read) and closes one with another SID, a lower integrity or an unreadable token. Clients (the CLI, a holder dialling its core, and Brindle's client) check the server before writing (`GetNamedPipeServerProcessId`, `win::check_server`) and refuse another SID or any other integrity, so no process uses a server at another integrity level.
  - **Detached start (Windows, `platform/windows/daemon.rs`):** the starter runs `<helper> launch <role> --ready-handle N` (std passes the ready pipe's write end, inheritable, as handle `N`), and the `launch` trampoline `CreateProcessW`s `<role> --ready-handle N` from its own image and exits at once, like the double fork, so no role's parent is a live process and `taskkill /T` or "End process tree" on Brindle doesn't reach it. The role is created with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB | CREATE_UNICODE_ENVIRONMENT` and a `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (the ready pipe and the trampoline's stdout/stderr). A job that forbids breakaway fails that with `ERROR_ACCESS_DENIED`; the trampoline then retries without the breakaway flag and says so in one stderr line, its starter's log (a `KILL_ON_JOB_CLOSE` job then still ends the role). The role writes one ready byte once listening, then points stdout/stderr at its log (`daemonize`). `brindle-remote.exe` stays a console program for its CLI; the flags keep roles from opening a console.
  - **Per-build copies (Windows):** Windows locks a running image, and a holder runs for days, so roles never run from the installed helper: `win::ensure_helper_copy` (for Brindle's client, group 7) copies it to `<copies>\<build id>\brindle-remote.exe` (`server_dir::helper_copies`: `bin` in `BRINDLE_SERVER_DIR` when set, else `%LOCALAPPDATA%\brindle\server`), through a temporary name and a rename, keeping the last-write time; a rename another process won is used once its build id checks out. Cores and holders start roles from their own image (`win::own_image_path`, `GetModuleFileNameW`), which is the copy. At its start the core removes other builds' copies (`prune_copies` → `win::prune_helper_copies`); one still running can't be deleted and stays.
  - **Platform layer (`server/platform/{unix,windows}`):** the core and the holder name no platform type. What they need from the system is in one set of modules per platform with the same items: `event_loop` (`Loop`, `Source`, `Waker`), `conn` (the `Stream` under the shared framed `Conn`), `listen` (`Listener` with the peer check, `connect`; on Windows its paths are pipe names), `lock`, `daemon` (`ready_from_args`, `start_role`, `ReadyPipe`), `pty` (`Pty`, `Program`, `Group`), `piped` (`Piped`, its three streams' sources, `PipeCommand`, `spawn_piped`, sharing `pty`'s `Program` and `Group`. Linux: three `pipe2(O_CLOEXEC)` pairs, the holder's ends non-blocking, the program `setsid` with default signals (`pty::default_signals`) in `pty::start_directory` and exactly the request's environment. Windows: three pipes from `pty::pipe` (`server_dir::pty_pipe` names), the program's ends inheritable and the whole `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, its job given with `PROC_THREAD_ATTRIBUTE_JOB_LIST` (`Job`, `KILL_ON_JOB_CLOSE`), so a pipe session's `Program` and `Group` hold `Ends::Job` where a PTY session's hold `Ends::Console`; the module is private in each seam and its items are re-exported at `platform::`'s top, since `platform::piped` is the neutral module: `CREATION_FLAGS` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT`), `STARTUP_FLAGS`, `JOB_LIMITS` (`KILL_ON_JOB_CLOSE`), `ChildEnds::handle_list`, `launch` (the spawn's exact environment, the program resolved in its `PATH` by `conpty::cmdline::resolve_program`, `launch_line`), `batch_hint` ("npx is a batch file (C:\…\npx.cmd); run it as `cmd /c npx …`", the first `.bat`/`.cmd` in `PATH` order, with the arguments quoted) and `HangUp` (`CloseInput` at once, `EndGroup` after `pty::GRACEFUL_SHUTDOWN`, `KillRemaining` after another)), `dir` and `sys`. Handlers read and write through a source's owner, never through what the `Source` wraps, so the Windows loop can do the I/O itself. The decisions sit in neutral modules beside the seams, pure and tested on every platform, which the seams gather for, call and apply: `server/platform/{ready_arg,ensure_dir,pipe_state,wait,piped}.rs`, `conpty/{cmdline,choice,hosts}.rs`, `pty/{program,stat}.rs`, and in `brindle-remote-protocol` `access` (`admit_client`, `Dacl`), `server_dir` (pipe names, holder sockets, helper copies) and `hresult`.
    - **Windows loop (`event_loop.rs`, `pipe.rs`):** one IOCP with a readiness facade. Each pipe source keeps one overlapped read in flight into a buffer it owns and is readable while that holds bytes or hit the end; writes copy into an owned buffer and go out overlapped, writable while under `WRITE_MARK` (1 MiB); a listener keeps one overlapped `ConnectNamedPipe` pending and is readable once a client connected. A wait takes queued packets, then checks every source, and blocks only when none is ready, so readiness stays level-triggered as with poll(2). `Conn::input_waiting` is the buffered count plus `PeekNamedPipe`. The waker posts a packet (`PostQueuedCompletionStatus`); there is no `SIGCHLD`, so the holder watches each program with `Waker::wake_on_exit` (`RegisterWaitForSingleObject`). Deregistering and dropping cancel I/O with `CancelIoEx` and take the packets before buffers are freed. A pipe has no half-close: `shutdown_write` closes the handle once the pipe has taken everything written.
  - **Holder (`hold`, `holder.rs`):** one thread on the platform's `Loop` (Linux: `PollLoop`, poll(2) plus a `SIGCHLD` self-pipe; Windows: the IOCP loop). It owns many sessions' PTYs (Linux: `remote-agent/src/pty/unix.rs`; Windows: ConPTY, below), is the programs' parent, and parses nothing. Per session it stores, uninterpreted, the core's last checkpoint and the raw tail since (1 MiB cap, then `truncated`). H1 3's `CHECKPOINT_APPEND` (OpenSpec change `agents-log-paging`) opens a blob like `CHECKPOINT_BEGIN`, marked in `Core.appends`, and at its `END` adds the bytes to the stored checkpoint instead of replacing it, covering the tail as a whole one does; `policy::append_open_refusal` refuses it below H1 3 and `policy::append_refusal` onto an empty checkpoint or past `MAX_CHECKPOINT_LEN`, each an `ERROR` for the session that leaves the stored checkpoint and tail as they were (length checks only: the holder still parses nothing). An adoption gets the base and its segments back as one blob. It exits when it has no sessions (10 s after start if it never had one). On Linux its `Hangup` sends SIGHUP to the process group before it closes the PTY (closing first let a program blocked reading the terminal exit on the failed read), then SIGKILL while the group has members, and its programs start with every signal's default action and an empty signal mask (`pre_exec` in `pty/unix.rs`), whatever the holder inherited (under `nohup`, an ignored SIGHUP). When a write to its core fails, it still handles what that core had sent (up to 16 MiB) before it drops the core. It stops reading PTYs once 8 MiB is queued to its core (`CORE_QUEUE_HIGH`) and resumes under 2 MiB (`CORE_QUEUE_LOW`), through the pure `core_backlog` and `read_limit`; input past 4 MiB waiting for one session is dropped with an `ERROR` (lossy by design, behind Brindle's input budget of the same size). Each message from its core is handled under `catch_unwind` (`Holder::guarded`): a failure is answered for its unit (`unit_of`), `SPAWN_FAILED` for a `SPAWN` (hanging up a session it had made), an `ERROR` for that session (abandoning a checkpoint it was assembling) or for the holder, and the sessions and connection carry on; `BRINDLE_TEST_HOLDER_PANIC` (debug builds, `server/fault.rs`) injects one through a marker in a `SPAWN`'s arguments or an `INPUT`'s bytes. A connection whose first message isn't `HELLO`, or whose `HELLO` shares no version, gets an `ERROR` and a graceful close (`Conn::close_for`, within `REFUSAL_CLOSE_LIMIT`, 1 s), as the core does for a client, so the peer reads the error and then the end, not a reset. With no core for 3 s (`CORE_GRACE`) it starts its own binary's `serve`, backing off 3 s to 60 s (`BRINDLE_TEST_HOLDER_CORE_ARGS` overrides the args in tests). On Linux it sets `IUTF8` on every PTY. Pipe sessions (H1 version 3's `SPAWN_PIPES`, `platform::spawn_piped`; a session's streams are `Io::{Pty, Pipes}`): stdout is the session's output exactly as a PTY's is (tail, `OUTPUT`, `PAUSE`, `covers`), stdin takes `INPUT` under the same cap on a token of its own (`Source::Stdin`), and stderr (`Source::Stderr`) is read always into a 16 KiB ring (`StderrRing`), sent once as `STDERR_TAIL` just before `EXITED`, or right after the session's `TAIL_END` in an adoption when it ended with no core (logged as "ended with no core to tell; kept for the next one"); the session ends once stdout and stderr have both ended or been quiet (`streams`, then `policy::drained`). A hang-up is `platform::piped::HangUp`'s steps (`hang_ups`): stdin closes at once while stdout and stderr are still read, the group (Linux `SIGHUP`) or job (Windows `TerminateJobObject`) ends a grace later, and what remains is killed after another. `RESIZE` and `REPARENT` for one get an `ERROR` ("session N is on pipes and has no size" / "… no console window"). A core that negotiated H1 below 3 isn't shown them (`policy::shown`): not in `WELCOME`, no `OUTPUT` (their output only grows the tail), no `EXITED`, so a finished one waits for a core that speaks 3. A failed spawn is `SPAWN_FAILED` "cannot run <command>: <error>" (on Windows, a bare name that is a batch file gets `batch_hint`'s text). `tests/holder.rs` covers them on both platforms (`a_pipe_*`, `an_older_core_isnt_shown_a_pipe_session…`).
  - **ConPTY in the holder (Windows, `remote-agent/src/conpty/`, `platform/windows/pty.rs`):** the `Api` resolution, `Pseudoconsole` and the launch-line quoting (`cmdline::launch_line`) live in the agent, and `remote-agent/build.rs` embeds the packaged ConPTY (`scripts/fetch-conpty.ps1` fetches it; Brindle's own exe embeds none). `conpty.dll` is loaded by absolute path from beside the helper, else from a copy extracted to `%LOCALAPPDATA%\brindle\conpty\<version>`, and only when the bytes there match the embedded ones; otherwise the inbox kernel32 functions are used, with one log line. `SPAWN`'s command is never empty on Windows (Brindle resolves a profile without one itself: `cmdline::windows_default_program`); the holder quotes it with `launch_line` and passes the environment as given. `BRINDLE_CONPTY=inbox` is read from the session's `SPAWN` environment, not the holder's, and each `Api` is resolved lazily and cached. Each session has two one-way pipes, input then output (`server_dir::pty_pipe`: `\\.\pipe\brindle-pty-<holder pid>-<n>`, consecutive `n`, first instance, the server pipes' security); the host gets synchronous ends, the holder's overlapped ends make one `Source`. Pseudoconsoles are created with `PSEUDOCONSOLE_GLYPH_WIDTH_WCSWIDTH` (0x10), which matches the grid's per-code-point widths; the host's grapheme default makes ❤️ two cells.
    - **Exit:** the exit wait wakes the loop; the holder releases (`ReleasePseudoConsole` when exported) and closes the pseudoconsole on a short-lived thread, since `ClosePseudoConsole` can block until output drains, keeps reading output to EOF, and sends `EXITED` after the last output with `GetExitCodeProcess`'s code.
    - **Hangup (`CLOSE`, `KILL`, `STOP`, a `kill` session's owner gone):** the host sends `CTRL_CLOSE_EVENT` once, only to processes connected then, so the close thread first waits up to `CONNECT_LIMIT` (`pty::GRACEFUL_SHUTDOWN`, 1 s) for the root to be on the console, keeping a copy of the input end open until then (the input ending is a close too), then closes. After the same grace `Group::kill_remaining` calls `TerminateProcess` on the root if alive and on every process still on the session's console host (`conpty::console_host`, through the undocumented `NtQueryInformationProcess` class 49; if that fails, only the root). Programs that left the console (a GUI app) keep running; there is no per-session job object.
    - **`REPARENT`:** the Windows core forwards a client's `REPARENT { session, hwnd }` (protocol 1 message 13) to the session's holder (H1 message 11), which calls `ConptyReparentPseudoConsole` so the console window, and programs' dialogs, are owned by that window; it is advisory (no reply). The inbox ConPTY has no such export, which is logged once. A Linux core refuses it with an error. The owner is never cleared, and the core doesn't keep the HWND across restarts: a client re-sends it after reconnecting. Brindle sends it from `Terminal::parent_console_to` (when a terminal's view is made in the window): `Session::reparent` holds the HWND until the session has started or attached, and `Connection` keeps it per session (in its `State.sessions` entry) and sends it again after every later `REPLAY_END`, which is a reconnect's.
  - **Core (`serve`, `core.rs`, `core/{agents,clients,holders,sessions,manage,policy,process,screen}.rs`):** one thread on the same loop; takes `core.lock` for its life (`flock`; `LockFileEx` on Windows; the loser of a start race waits for the winner, then exits 0), serves clients on `core.sock` (Windows: the core pipe), drives holders and runs an `Emulator` per session whether or not a client is attached. Its decisions are pure, in `core/policy.rs`: the `Lifecycle` (when it accepts clients, the reconnect grace, the idle exit) and the session, client and holder policies the handlers call. For agent sessions (`agents-sessions`) it also holds `agent_checkpoint_due` (every reducer `Moment`, a step-down, a detach, else past `CHECKPOINT_AFTER`), with `agents-log-paging` how a due one is written (`Stored::{Unknown, Known { base, appended, seq }}`, `agent_appendable` and `agent_checkpoint_form`: whole for an unknown store, a step-down, a trim since the last, segments that would outgrow the base or pass 64 MiB, a segment too large, a draining holder of another build; appended otherwise), a page's budget (`page_budget`, `ATTACH.page` or `AGENT_FETCH.max_bytes` clamped to `PAGE_BYTES`, 256 KiB) and the `AGENT_FETCH` refusals (`agent_fetch_refusal`: below protocol 4, no session, a terminal one, not attached here, replay pending), `placement`'s `SpawnMode` (pipe spawns go only to a holder of the core's build that negotiated H1 3, `PIPES_PROTOCOL`), and what a client below protocol 4 (`AGENT_PROTOCOL`) meets: `shown` by `SessionKind`, `attach_refusal` ("session N is an agent session, which needs client protocol 4", before anything else about the session), `returning` without agent sessions, `agent_request_refusal` ("AGENT_PROMPT needs client protocol 4") for the agent messages, `LIST` leaving agent sessions out, and `agent_spawn_refusal` ("an agent session needs a command"). A session's `Content` is a terminal's `Screen` or an agent's `Agent` (`core/agents.rs`, the shell around `acp::reduce`): `SPAWN_AGENT` resolves the absolute directory (`platform::agent_directory`, deciding through `platform::piped::agent_dir`: the request's, `~` expanded, else the home, else the core's), which is the `SPAWN_PIPES` `cwd`, the meta's `cwd` and `session/new`'s, and queues a `SpawnRequest::Agent` (placed with `SpawnMode::Pipes`). Every input (`SPAWNED`, stdout, the stderr tail kept for `EXITED`, a lost holder, the attached client's `AGENT_*` commands, a due `Output::wake` from `tick`) is stepped under `catch_unwind` (a panic becomes `Input::Fault`, the command answered "session N: the terminal server's ACP handling failed"; `BRINDLE_TEST_ACP_PANIC` injects one), and its `Output` applied in order: the events as `TRANSCRIPT` to the attached client unless its replay waits, a checkpoint when `agent_checkpoint_due` says (`covers` from `Lines::covers`), the stdin as `INPUT` while the program is live, the hang-up; then the reply (`OK`, or `ERROR` "session N: …"; none for a taken cancel). An agent session is listed at 0×0 with `SessionInfo.agent` (the log's `Activity` mapped one to one, and the name from `initialize`: its readable `agentInfo.title` when given, else `agentInfo.name`), its `ATTACH` (or a reconnect) replays the newest page of the log, `Transcript::page(policy::page_budget(attach.page))` (`agents-log-paging`; the whole `replay()` when it fits, else a `Window` over the earlier entries), as `TRANSCRIPT` between `REPLAY_START` and `REPLAY_END` with the size ignored (a pending replay keeps its budget in `PendingReplay.page`), the attached client's `AGENT_FETCH` gets the whole entries before `before` as `AGENT_PAGE` frames (`Core::client_agent_fetch`, `Transcript::fetch` packed by `client::pack_page`, the last frame's `last.more` saying whether more are earlier; nothing stepped or checkpointed, whatever the agent's phase), and `RESIZE`, `DATA` and `REPARENT` are refused naming it. Each `Agent` keeps `stored` (what its holder stores, `policy::Stored`) and `unsaved` (the events applied since its last checkpoint), and `agent_checkpoint(id, at)` writes whole (`ToHolder::checkpoint`) or appends a segment of `unsaved` (`ToHolder::checkpoint_append`) as `policy::agent_checkpoint_form` says, for the holder's `Holder::adoption`; `stored` starts again `Unknown` on an adoption, a restart (`Agent::restarted`) and any holder `ERROR` naming the session (`Agent::forget_stored`). `Content::Agent` is boxed, as a screen is. On adoption its holder's checkpoint is kept until the tail, then `acp::checkpoint::adopt` rebuilds it and the tail is fed as stdout. Agent sessions are left out of the `PROCESS` look. **Ended agent sessions** (`agents-session-recovery`): an agent that exits, or whose holder is lost (`Input::Lost`, "its holder ended"), is kept as `Life::AgentEnded { code }` when `Agent::continuable` (the reducer's `continuable()`: it ended, and `initialize` offered `session/resume` or `session/load`) and a client has the session or may return, as the pure `policy::end_fate` says (`EndFate::{Keep, KeepForOwner, Report}`; terminal sessions keep `exit_fate`). It has no program and no holder, lives in this core's memory only (a core restart or upgrade loses it, and the zone then starts a new session), is listed (`Life::is_listed`, pid 0) but not counted in `STATUS` (`is_held`), and gets no `EXIT`; a `DETACH` (`policy::detach_ends`), `CLOSE`, `KILL` or `STOP` ends it with `EXIT { code, lost: None }`, and its client's leaving does too unless it lingers (`ended_gone_fate`). `AGENT_RESTART` (`client_agent_restart`) is refused below protocol 4, from a client without the session, while the core stops ("the server is stopping; try again"), and as `policy::restart_refusal` says ("session N: the agent hasn't ended", "… can't continue this conversation", "… AGENT_RESTART needs a command"); otherwise it steps `Input::Restart` (the `RESTARTED` notice, `Starting`), updates the meta's command and queues a `SpawnRequest::Restart`, a `SPAWN_PIPES` under the same session id in the conversation's `cwd` on any H1 3 holder of the core's build, answered `OK` at once and never `SPAWNED`. Its `SPAWN_FAILED`, or a hang-up, `STOP` or takeover before it is placed (`abandon_restart`), steps `Exited { None, message }` back to ended (`restart_failed`); a holder lost before its `SPAWNED` places it again. A `SPAWN_AGENT` naming a `conversation` runs in that `cwd` as `Agent::continuing` (`AgentSession::continuing`, a fresh log). A continuing spawn or restart is checkpointed right after its `SPAWN_PIPES`, and `checkpoint::adopt` steps `Input::Spawned` into a checkpoint still `Spawning`, so a core killed before `SPAWNED` continues it. At `initialize`'s answer the reducer's `choose` picks `session/resume` (preferred for a kept log), `session/load` (its replay muted into one notice for a kept log, shown after `REPLAY_SHOWN` for a fresh one) or neither (`CANT_CONTINUE`: `Failed` and the session ends; never `session/new`). **Logging in** (`agents-login`): `AGENT_LOGIN` (`AgentCommand::login`) is stepped as `Command::Login` like the other agent commands (attached client, protocol 4; `OK`, or `ERROR` "session N: the agent offers no login method \"x\"", "… login method \"x\" runs in a terminal, which Brindle opens", "… the agent isn't waiting for a login", "… a login is already running"), and `AGENT_CANCEL` while logging in cancels the login as the reducer says. `AGENT_RESTART` is also taken for a running agent that needs a login (`Agent::needs_login`, `restart_refusal`'s `needs_login`): its step hangs the agent up (`Phase::Restarting`, the `RESTARTED_AFTER_LOGIN` notice, `Starting`), the request is kept on the `Agent` (`login_restart`, in memory), and at the holder's `EXITED` `session_exited` asks `login_restart_due` (a client attached, the core not stopping) and `restart_after_login` steps `Input::Restart` again and queues it as an ended agent's restart (no `Exited` in the log, no `EXIT`), in the conversation's directory or else the session's. Any later `hang_up` drops the kept restart, and the exit then ends the agent as any. **The queue of one:** each agent session has one prompt slot, `Transcript::slot()` (`Slot::{Empty, Waiting, Held}`), set by the reducer and sent as `Queue { slot }` (live, and in every replay while not empty), so it lives in the log, the checkpoint and the replay, never only in a client. An `AGENT_PROMPT` during a turn waits, and is sent only after the turn ends `Ended { EndTurn }`; any other ending, a cancel, `-32000`, the agent failing or exiting, or lost output holds it with its `HoldReason`. `AGENT_RESEND` sends a held prompt (queued again while a turn runs, refused while the agent isn't ready) and `AGENT_UNQUEUE` discards a waiting or held one; a prompt while the slot is taken and a turn runs is refused ("a prompt is already queued"), and with no turn running a new prompt is sent with a held one left as it is. The slot never changes the listed activity. A session's state is a `Life` (starting, running, hung up, exited with the exit kept for its owner, or an agent ended and kept for its conversation) and an `Ownership` (attached, lingering, awaiting its owner after an adoption, or detached, each with since when), with its owner an `Option<ClientToken>`. It accepts clients only after adopting the startup holders (≤ 5 s). Close policies: `kill` ends on `CLOSE`/`KILL`/`STOP` and when the owner (a `client_token`) is gone, after `RECONNECT_GRACE` (10 s) for sessions adopted by a new core; `detach` ends only on `KILL`/`STOP`/exit. A client may ask in its `HELLO` for `linger_secs` (capped at `MAX_LINGER`, 600 s): its `kill` sessions then outlive its connection that long (`Ownership::Lingering`, kept only in this core; an exit meanwhile is kept for it, as for an adopted session) and are hung up only when it hasn't come back by then; `replay` clears it. A `HELLO` with the token of a client that is still connected replaces it (`take_over`): the stale connection (a link that died silently) is closed without `client_gone`, its sessions lose their client but keep their owner and go to the new one with replays, its spawns not yet sent to a holder fail and its sessions still starting are hung up (`reattach` never gives back one still starting). `ATTACH` makes the client the owner; `DETACH` clears the owner and switches `kill` to `detach`, so a reconnecting client gets back only the sessions it still owns. A `DETACH`'s or `SET_LAYOUT`'s `layout` (Brindle's record of the session's tab, opaque to the core; `SET_LAYOUT` stores only a change) goes into the session's meta, unless its JSON is over `MAX_LAYOUT` (64 KiB; logged and dropped, the detach still applies), so it survives core restarts and upgrades through `SET_META`; `LIST` reports it while the session is detached, and `ATTACH` clears it (OpenSpec change `session-layout-in-server`). Each session's `SessionMeta` (owner, policy, a random 128-bit hex `key`, `profile`, `started`, `layout`) lives in its holder; the core sends `SET_META` on every owner or policy change to H1 v2 holders (logged and skipped for v1), so the next core sees it. A stored meta the next core can't read whole (`SessionMeta::from_value`'s `MetaFault`: a field of the wrong type, or not an object; a missing field is just its default) is adopted detached with no owner, keeping what was well formed and getting a fresh key if its key was malformed (`adopt_meta`); `core.log` names the session and the fields, and the repaired meta is stored back with `SET_META`. A replay waits until the session's last `SET_META` is in its holder's connection (`Session::storing`, a count of bytes written to it; each turn flushes holders before clients, then sends those replays), so a client that has its `REPLAY_START` gets the session back even from a core killed right then. Session ids restart at 1 in a fresh core; the key tells sessions apart across cores. `LIST`'s `SessionInfo` carries key, title (the emulator's), `started`, profile, `owned` (an owner is set and no client attached: it may come back) and `detached_secs` (since its last client left; from the adoption for an adopted session). Clients that negotiated protocol 2 and set `HELLO`'s `process_info` get `PROCESS` (`process.rs`): the foreground program's `comm` and `cwd` (Linux: `tpgid` from `/proc/<pid>/stat`, through `platform::pty::foreground`; a Windows core sends none), once after a spawn or attach, then on change. The core looks once a second (`PROCESS_LOOK`) and only at sessions with output or input since its last look; activity younger than 250 ms at a look keeps the flag for the next, since a keystroke's echo comes before the shell makes the program it starts the foreground. It exits 5 s after the last session and client (`UNUSED_LIMIT`). Backpressure is per session: `PAUSE`/`RESUME` once a client's queue passes 1 MiB / falls under 256 KiB. A client found gone by a failed write is dropped only once the frames it had sent are handled (up to `DEAD_CLIENT_READ_LIMIT`, 16 MiB, as a holder does for its core; nothing is sent back), so the `DETACH`es Brindle sends as it quits count even when the core has output queued for it. Each `Term` feed runs under `catch_unwind` (`screen.rs`): a panic marks that emulator broken (replays are then `ESC c`) and the session keeps forwarding output; `BRINDLE_TEST_FEED_PANIC` (debug builds) injects it.
  - **Protocols (`remote-protocol/src/{client,holder,wire,version}.rs`):** client protocols 1–4 (`PROTOCOLS`) and core↔holder H1 share the frame header (`type: u8, len: u32 BE, payload`) with their own message numbers and version ranges, negotiated per connection by `HELLO`/`WELCOME`. JSON fields are additive with defaults; a new message type needs a new version; transcript tests pin both. Client protocol 2 adds only `PROCESS` (message 41), sent only on connections that negotiated 2 and asked, so a 1–2 client and a 1-only core agree on 1. Client protocol 3 adds only `SET_LAYOUT` (message 14, client → core: the layout of a session the client has attached, refused with an `ERROR` below 3 or from a client without it attached; transcript `client-set-layout`), so a 1–3 client and a 1–2 core agree on 2 and Brindle sends its layouts only on quit. `HELLO`'s `linger_secs` and `process_info`, `SessionInfo`'s `owned`, `detached_secs` and `layout`, and `DETACH`'s `layout` (`client::Detach`, no longer a `SessionRef`) are additive fields; `client-layout` and `holder-set-meta-layout` are their transcripts, and the older fixtures stay byte for byte. They offer the whole client range, so a protocol 4 core lists them agent sessions: `list_line` (pure, unit-tested) puts `agent: <activity>` in the title column, and `--json` prints `SessionInfo` as the core sent it, its `agent` object included; `kill` and `stop` need nothing of their own for agent sessions.
  - **Relay (`relay`, `relay.rs`; Linux only (`target_os = "linux"`); other platforms, macOS included, refuse it):** a client of its host's core that pipes the client protocol to its stdio for a Brindle on another machine (over `ssh` or `docker exec`). It writes the frame marker, resolves and creates the server directory, connects or starts the core from `/proc/<own pid>/exe` (stdout to `/dev/null`, since its own carries frames; ready pipe through `start_role_as`/`ReadyPipe::wait`), then sends `RELAY_HOST` (version, build, its environment with `HOME`, `USER`, `LOGNAME` and `SHELL` filled in from passwd where unset or empty (`login_env::with_basics`), shell from `SHELL` else passwd, home, server dir, core pid, and `login` when asked) or `RELAY_ERROR` (the problem and `core.log`'s path) and exits. **Login environment (OpenSpec change `remote-login-environment`):** `relay --login-environment` (the SSH launch passes it, a container's doesn't; any other argument is a usage error) starts a thread after the marker that runs the user's login shell as `login_env::invocation` says (`$SHELL -l -i -c 'exec "$0" login-env' HELPER` for the POSIX shells, `busybox sh …`, fish with the path in its quotes; csh, tcsh, nu and other shells are `Unsupported`), with stdin and stdout on `/dev/null`, stderr on a pipe whose last 4 KiB are kept, fd 63 on a dump pipe (not a low one: an interactive login bash marks 3 to 19 close-on-exec), `setsid`, the home directory and the filled environment. The shell `exec`s the hidden `login-env` role (`relay::login_env_role`, declared in `main.rs` under Linux, not in the usage text), which writes `NAME=VALUE\0` records and an empty one to fd 63. The relay polls the dump, stderr and an exit pipe its reaper thread closes, reads the dump up to its terminator (never to EOF, since an `ssh-agent` a startup file left may hold it; at most 256 KiB and 4096 variables, `login_env::parse_dump`), takes `_`, `SHLVL`, `PWD` and `OLDPWD` from its own environment (`captured`), and after 10 s (`BRINDLE_TEST_RELAY_LOGIN_ENV_MS`, a timing honoured by release builds too) sends `SIGKILL` to the shell's group. `reach()` joins it after the probe and upgrade and before the client's core connection opens, so it overlaps reaching the core and spends nothing of the core's 5 s `HELLO` limit. The outcome is `RELAY_HOST.login` (`Captured`, or `Failed` with `LoginEnvFailure::text()`), and a failure gets one `relay[pid]:` line in `core.log` with no values. The client's core connection is open once `HOST` is sent, so its `HELLO` must follow within the core's 5 s. Then whole frames are copied both ways by header; the client's relay frames are dropped, so no core sees a `RELAY_HEARTBEAT`. Scope: a scope only when `/var/lib/systemd/linger/<passwd name>` exists and `scope::current_outcome()` finds a user manager (`decide_scope`); otherwise plain, with `BRINDLE_NO_SCOPE=1` in the core's environment (its holders too) and one `core.log` line saying why. That line warns that the sessions "may not outlive the login" only when a user manager is reachable (`scope::Outcome::user_manager`: the user doesn't linger, or `systemd-run` is missing); with no user manager (a container) or `BRINDLE_NO_SCOPE=1` it is the plain "without a scope" line. Liveness (`liveness.rs`): the stdin reader thread stamps every frame, heartbeats included, and is busy while writing one to the core; the main thread ends the relay after 60 s without a stamp; a heartbeat thread sends `RELAY_HEARTBEAT` after 10 s without a write, under the writer mutex the core→stdout copier holds per frame, so a client that stops reading blocks only those two. `BRINDLE_TEST_RELAY_IDLE_MS`/`…_HEARTBEAT_MS` shorten both for tests. It ends when either side closes. Upgrade: on its own connection (token `relay-<pid>-upgrade`) it reads `WELCOME`, compares `upgrade::is_newer` (its own exe's mtime against `/proc/<core pid>/exe`'s), checks the holders' H1 versions in-process (`check::refusal`), sends `STEP_DOWN`, waits for the old core to exit (a `serve` that loses the lock counts the exiting one as the winner), starts `serve` and connects again (up to 15 s, taking the holders' own core if its won't start); a refusal relays to the running core. Tests: `tests/relay.rs` and the relay cases in `tests/upgrade.rs` (Linux) run it on a socket pair (`tests/support/relay.rs`).
- **Brindle's client (`src/remote/local.rs`, `local/{agent,connection,session,upgrade}.rs`):** `shared()` keeps one `Connection` per endpoint (`Host`) with a reader thread (demultiplexes by session, parses into each `SessionSink`; during a replay it drops bells, notifications and status notices) and a writer thread (queues messages, holds them while disconnected). `Session::start` (`SPAWN`) and `Session::attach` (`ATTACH`, answered by a `REPLAY_START` carrying its `req`) return at once and do the connecting, start, upgrade and request on their own thread, so the UI thread never blocks; each request waits in `State.requests` for its answer. Input waits under the session's input budget (`remote/budget.rs`, `InputBudget`, owned by the `Session` across its phases and handed to its `Running`): held while the session starts and while the link is down or slow, counted until the writer has written or skipped its `DATA` (`Outgoing`'s backlog), a call taken whole while less than 4 MiB waits and refused past it until less than 1 MiB waits; `Session::input` returns a `Delivery`, and `Terminal::write` sends `ChannelEvent::InputRefused` on a crossing's first refusal, which writes one dim "input not sent" line in the tab. Control messages (resize, close, detach, layout) are never refused. Every call into a sink goes through `Connection::deliver` under `catch_unwind` (`process R3`): when Brindle's emulator panics on a session's output, that session stops being shown and is sent `DETACH` (it keeps running), its sink is told `broken` (the terminal replaces its `Term`, parser and marks, and the tab says in red that it can't show the session any more and to attach it again from Attach Session…), and the reader carries on for the endpoint's other sessions. Debug builds take `BRINDLE_TEST_SINK_PANIC=<marker>`, read once: the sink panics on output holding the marker (the e2e suite's fault switch). `brindle --list-fault-switches` lists it and `BRINDLE_TEST_LAUNCH_LISTING`, and a release build lists none. `State.sessions` holds each shown session's `Shown` entry by id: its sink, its key (`SessionKey`, decoded once from the wire's string; `None` from a core that predates keys), its window (for `REPARENT`) and its last `PROCESS`, which all go with it. A `Running` (a started session's handle) acts only while its connection shows that session by id and key (`State::shows`, `State::forget`), so a lost or exited tab's input, resizes, window, layout, detach and close never reach a session that later got its id. Closing a zone or tab ends its program, and quitting keeps it: `Closing::Keeps` (profile tabs) spawns with the `detach` policy, so a crash keeps them too, and `Closing::Ends` (`-e`) with `kill`. `Terminal::close` (an explicit close) sends `CLOSE`; quitting has every terminal leave explicitly (`Workspace::quit` → `ZoneTreeView::quit_all` → `Terminal::quit_with`, from the app's quit handler and from the window's close: the `CloseWindow` action or a close the platform asks for), a `Keeps` one with `DETACH` and an `Ends` one with `CLOSE`, recording the window first, since a zone that left no longer knows its session. Each tab's `DETACH`es carry its layout (`layout::record`: the split tree by session key, the active zone, the manual title, the tab's index and the process's id (`layout::origin_id`, made once in `main.rs` and passed to `Workspace::new`); zones without a running session are left out, and a session still starting detaches without one). While Brindle runs, `main.rs`'s once-a-second `record_session` tick also calls `Workspace::send_layouts` → `ZoneTreeView::send_layout` → `Terminal::set_layout` → `Running::set_layout`, which sends `SET_LAYOUT` only when the link negotiated protocol 3 (`State.protocol`, from each `WELCOME` in `Connection::up`) and the layout differs from the one it last sent, so a killed Brindle leaves its splits (e2e `local-server-layout-live`). A drop does the same, and a session leaves only once, but drops can't be relied on (see the Windows pitfalls). Nothing asks first, and quit waits at most `QUIT_FLUSH` (500 ms) for the connections to write the tabs' `DETACH`es and `CLOSE`s (`local::flush`, after GPUI's shutdown; a connection that is down isn't waited for): they are only queued for the writer threads, which the exit ends (on Windows at once), and a lost `DETACH` leaves the session its owner, so the next launch doesn't open it as a tab. On a lost connection the reader reconnects with the same `client_token` (a core is started after `START_AFTER`), a `LIST` after `WELCOME` finds the sessions the core no longer has with their keys (`State::keep_listed` over `ListedSession`s: a fresh core restarts ids at 1, so a session whose id it lists under another key is one it no longer has, and an attach cut off by the drop is sent again only to a session listed with its key), and those, or all after `RECONNECT_LIMIT` (15 s), get the red "session lost" line (`EXIT` with `lost`) while the tab stays open. A relay link's reason for ending (the log line, `LinkState::Offline` and the failed requests share it) names its cause (`relay_link_ended`): `nothing read from <name> for <limit>` when the watchdog ended it (it marks the link's `Stamp` expired first, so a killed process's status isn't mistaken for the cause), else the relay process's own account (`Wire::why`: `ssh exited with 255: <cause>`, the cause the last line it wrote to stderr), else `the relay closed the connection`; only the local core's socket or pipe says `the terminal server closed the connection`. A failed launch's first line names its cause the same way (`client::split_cause`: the last non-empty stderr line, the other lines below it). `SPAWN` carries the complete environment (Brindle's with `child_env(profile)`; non-UTF-8 variables are dropped; on Windows names are merged case-insensitively with the profile's entry winning, `cmdline::merge_environment`). A relay connection stays in use (`State::in_use`) while a request, a session, a listing hook or an unwritten `CLOSE` needs it, but a `CLOSE` only for `Timings::close_limit` (5 min) after the oldest was queued: with no link up by then, the closes are given up, never written, and their programs left running (logged as `not ending session <ids> on <endpoint>: …`, which is also the end's reason if nothing else uses it). A core that refuses this Brindle (`Refused`) ends a connection that isn't eager; an eager one reports the endpoint offline with the refusal, fails new tabs' requests with it and retries at most `Timings::eager_cap` apart.
  - **Agent sessions (OpenSpec change `agents-profiles`, section 4):** `remote::agent_link` (`src/remote/mod.rs`, the platform-neutral seam `src/agent/` uses) starts an agent session (`AgentStart::Spawn` → `Session::start_agent`, `SPAWN_AGENT` with the `detach` policy) or attaches one (`AgentStart::Attach`, at 0×0) and gives an `AgentLink` over the `Session`. The writer checks `agent::model::agent_start` on the link's negotiated protocol just before it writes `SPAWN_AGENT`: below 4 nothing is sent and the spawn fails with `StartFailure::TooOld`; the session's thread turns a connect failure into `StartFailure::NoServer` and a refused spawn into `StartFailure::Refused`, and the sink's `failed` downcasts it. A connection remembers the client protocols its `HELLO` offered (`Connected::offer`, `connect_offering`, `hello_offering`) and offers them again on reconnects and upgrades; Brindle's own is `BRINDLE_PROTOCOLS`, `client::PROTOCOLS` (1–4) since task 6.5. `Session::{prompt, resend, unqueue, answer}` (`AGENT_PROMPT`, `AGENT_RESEND`, `AGENT_UNQUEUE`, `AGENT_PERMISSION`) go only while the session runs and the connection shows it, each registered as `Waiting::Agent` in `State.requests` and its id returned; otherwise each returns why nothing was sent, `Err(NotSent)` (`agent::model::NotSent`, OpenSpec change `agents-client-state-fixes`): `Starting` while the session's thread hasn't installed `Phase::Running`, `Gone` once it was let go, never started or the connection no longer shows it. The `OK` or `ERROR` reaches the sink's `reply` under that id as `Ok` or `Err(ReplyError::Failed)`, and so does any failure before it was written; one written when the link drops is `Err(ReplyError::Unanswered)`, since the core may have taken it. `State::link_lost` returns `LinkLost { unanswered, unsent }`: the written requests (attaches carried, as before), and the queued `Waiting::Agent`s whose `carry` is `Carry::Never` (a fetch), which fail with the link's text; every other queued request (`Carry::NextLink`) goes out on the next link. Once `run` has set `Phase::Running` it drops the phase lock and calls the sink's `running` (`SessionSink::running`, a no-op for a terminal), so the zone hears the session runs only once a request can go; `BRINDLE_TEST_SESSION_START_DELAY` (debug builds, `SESSION_START_DELAY` in `src/remote/mod.rs`) sleeps between the core's answer and that step, the fault switch the `agent-*-before-the-session-runs` e2e cases use. `Session::cancel` sends `AGENT_CANCEL`, which nothing answers (`Result<(), NotSent>`). `Session::restart` sends `AGENT_RESTART` the same way (`agents-session-recovery`), and `SPAWN_AGENT` carries `AgentSpawnRequest.conversation` for a continue in a new session. `TRANSCRIPT` frames go by session id to the sink's `transcript` through `Connection::deliver`; a terminal's sink logs and drops one. An `Err` from it (an event that didn't decode or fold) or a panic goes to `Connection::break_session`: the session stops being shown, is sent `DETACH` (it keeps running, still listed) and the sink is told `broken`. A dropped link tells every shown sink `link_down`. `Session::fetch` (`AgentLink::fetch(before, max_bytes)`, OpenSpec change `agents-log-paging`) sends `AGENT_FETCH` as a `Waiting::Agent` request (`Carry::Never`) while the link is up; while it is down nothing is sent and it returns `Err(NotSent::LinkDown)`, one still queued when the link drops fails with `LINK_DOWN` ("the connection to the terminal server is down"), and one written then is unanswered, as any agent request. Its `AGENT_PAGE` frames go to the sink's `page(req, events, last)` while the fetch waits (a page for no waiting fetch is dropped); the frame with `last` ends the wait, and its `OK` reaches `reply` after the sink folded the page, or an `Err` from `page` breaks the session. The agent's sink is `agent::sink::Sink` (`local/agent.rs` implements `SessionSink` for it): it folds into the `AgentShared` it shares with its zone's `Feed` and sends `AgentEvent`s through an `EventGate` (`Changed` merged, the rest life events), and in debug builds panics on an event holding `BRINDLE_TEST_SINK_PANIC`'s marker. The client tests run scripted protocol 4 cores (`session.rs`'s `MiniAgent`) and, ignored unless `BRINDLE_TEST_SERVER_HELPER` and `BRINDLE_FAKE_ACP_AGENT` name built helpers, a real core with `brindle-fake-acp-agent`.

- **`agent/` (OpenSpec change `agents-profiles`)** — an agent zone: an ACP agent session in the terminal server (the core is the ACP client), shown as a conversation. Data flows **the connection's reader → `AgentShared` → `ChatModel` → `AgentView`**:
  - **Reader → `AgentShared`:** `sink.rs`'s `Sink` is the session's `SessionSink` (through `remote/local/agent.rs`); on the reader thread it decodes each `TRANSCRIPT` value with `Event::from_value` and folds it into `shared.rs`'s `AgentShared` (`Arc<Mutex<_>>`, a leaf lock): the `Transcript` and its `Changes` (`added_from`, `changed` with `Dirty::{Appended, Replaced}`, `trimmed_through`, `slot_changed`, `turn_or_agent`, `reset` on a replay's start, `status_from`, `prepended`). `status_from: StatusFrom::{Unchanged, Replay, Live}` says where the newest `Turn` or `Agent` event of the batch was folded (a replay's start sets `Replay`), so a live event after a replay in one batch still raises its notice or sends the first prompt (`agents-client-state-fixes` decision 8). A fetch's `AGENT_PAGE` frames are buffered by request id until the last, then folded in front through `AgentShared::prepend` (`Transcript::prepend`, recording `prepended: Some(count)`, `status_from` untouched; a page that doesn't decode or fit leaves the transcript as it was and breaks the session); a replay's start drops the frames buffered so far and the rest of those fetches' frames, and a fetch's reply clears what it left. It tells the zone through an `EventGate`: one merged `AgentEvent::Changed`, and life events (`Replay`, `LinkDown`, `SessionRunning` from the session's thread, `Exited`, `Lost`, `Failed(StartFailure)`, `Broken`, `Reply { request, outcome: Result<(), ReplyError> }`, `Note`). An event that doesn't decode or fold, or a panic, breaks the session (detached, still running).
  - **`AgentShared` → `ChatModel` (`mod.rs`'s `Agent` entity):** `Agent::spawn` (the request built by `spawn.rs`'s pure `agent_spawn_request` on the session's thread; the directory by `spawn::directory`) or `Agent::attach` calls `remote::agent_link` and keeps the `AgentLink` behind the `Requests` trait (a test's fake implements it too). Its task drains the gate's channel in chunks paced by `terminal/pace.rs` (`Pace`, `pace::drain`), tells the gate what it took (`Feed::split`'s `Taker`), and on `Changed` takes the changes under the lock and calls `ChatModel::absorb`; life events call `session_running`, `not_started`, `ended`, `lost`, `broken`, `set_link`, `replied`. It checks a terminal launch's profile against its own config (`forwarded_launch` → `profile_for`). The answer is `ok`, `error: TEXT` or `usage: TEXT` (`instance::Answer`); the launch exits 0, 1 with the error, or 2 with the usage error (an unknown profile), which it prints; on Windows a launch with no console whose stderr goes nowhere (a Start Menu launch) also shows it in a message box (`win::show_unprinted`).   - **kitty's OSC 99 (`kitty.rs`, pure; `brindle-term-core`'s `kitty.rs` parses one chunk):** each `Terminal` keeps a `kitty::Assembly` (at most 8 incomplete notifications, oldest dropped; 2048 bytes each of title, body and button labels; base64 decoded as a stream, an unfinished quad carried to the next chunk; metadata merged, a later chunk's value winning; no title means the body is the title). `Terminal::handle_kitty` drops chunks during a replay and with `notifications.osc99` off, answers `p=?` at once with `reply_query` (from `Notifier::caps`: the platform sink's `Caps`, `dbus::CAPS` or `toast::CAPS`, the log sink answering as its platform's, D-Bus's `buttons` updated by `Reply::Capabilities`), and emits shows, closes and alives as one event kind (`TerminalEvent::Notify99`, `Request99`), so they reach `Notifier` in stream order through `Workspace`. `Notifier` keeps a `kitty::Open<EntityId>` table: `(terminal, id)` to a sent key or a sink id, oldest first, for replacement (an update before its first is shown is sent as new and the first closed once shown, as kitty does), `p=close` (`close_program`, which writes the close report itself when `c=1`) and `p=alive` (`answer_alive`). A `Target` carries the `ProgramNotice` (a `WeakEntity<Terminal>` and the `Program`), so a click goes through `kitty::activation` (body: raise unless `-focus`, report with `report`; buttons `1`–`4`: report with `report`, never raise) and a close through `kitty::on_close`; reports to a closed terminal are skipped. The log sink writes OSC 99 lines with flags (`i=`, `replaces`, `buttons=`, `silent`, `urgency=`, `expiry=`) and `close<TAB>osc99<TAB>i=ID` for a program's close.
  - A click activates the tab and raises the window. On Wayland, `activation.rs` uses the server's `ActivationToken` on GPUI's own `wl_surface` (foreign display, own event queue), because GPUI's own activation request is refused when unfocused. A later launch's forwarded token is used the same way. The attachment to GPUI's display (the registry round trip and the `xdg_activation_v1` bind) is made once, on the background executor, as soon as the window opens (`activation::prepare`, called by the launch task after `open_window`); a raise with a token that arrives before then waits for it in a task (`Attachment::Pending`, `policy::raise_plan`), and one after a failed attachment raises plainly.

- **`picker.rs`** — `Palette`, the view behind every palette (new tab from a profile, commands, sessions) and the one-line prompt (OpenSpec change `ui-command-palette`).   - The command palette lists the labelled actions available from the tab that had focus, snapshotted before the palette opens. It needs both `available_actions` (for global listeners) and `is_action_available` (for `no_json` actions). Running a command closes the palette, refocuses the tab and calls `window.dispatch_action` (deferred, and following focus), so it takes the keybinding's path.
  - Prompted commands (`RenameTab`) are ordinary actions. Their handlers emit a prompt request that `Workspace` opens, so a keybinding and the palette behave the same. A prompt asked for by a command run from the palette opens a palette of its own, since the palette closed to run it.
  - Keys: a list's are its command list's (`UiList`, `UiCommand`); the `Palette` context adds only ctrl-shift-delete (`PickerKill`, the sessions palette, on `Command::highlighted()`) and enter (`ListConfirm`, which submits a prompt). A sessions palette refreshed after a kill or an answer takes the new rows through `Command::set_groups`, keeping the filter text and, by `keep`, the highlighted row.
  - **Sessions palette state (`picker::SessionsModel`):** pure, in `PaletteKind::Sessions { model }`. It holds each endpoint's `Listing` (`Pending` until it answers) with its round, the killed sessions, each endpoint's failed kill and the highlighted row's `RowKey` (a session's endpoint, id and key, an endpoint, an endpoint's failed kill, or the note). This machine's failure to list is `Listing::Unlisted` (a remote endpoint's is `Offline`, `listing sessions on <name>: …`), a disabled `this machine  could not list sessions: <why>` row. `answer` applies one endpoint's listing as it arrives, with the outcome of the kill made before it (`list_sessions` returns `Listed { sessions, kill }`), and drops one from an earlier round, except a failed kill: that brings the session's row back and adds a disabled `<name>  could not end session N: <why>` row after the endpoint's, kept until the endpoint's next answer. `view` builds the groups and the index to keep: the highlighted row if it is still listed, else the row now at its place (a kill), else the last, skipping rows that do nothing. `Workspace::refresh_sessions_palette` spawns one listing per endpoint (`palette_endpoints`: this machine, then `Hosts`; `listing_from` decides what each gives) and applies each answer through `sessions_answered`, with no `join_all`. The palette opens when every endpoint has answered or after `OPEN_GRACE` (250 ms), whichever comes first, so a slow one is a disabled `<name>  listing sessions…` row until it answers or gives up (`LIST_LIMIT`). The "No detached sessions" note is a row after every endpoint's, shown only once nothing is pending or unlisted (e2e `local-server-palette-unlisted`).
