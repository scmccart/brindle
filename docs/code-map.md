# Code map

How the code works today, area by area: entities, threads, protocols, files and the names to search for. It is descriptive and read on demand: the normative rules are in `docs/architecture/`, and behaviour is specified in `openspec/specs/`. Keep it current in the change that alters what it describes.

Data flows **terminal server session → `Terminal` (model) → `TerminalView` (input) → `TerminalElement` (paint)**, with `Workspace` owning the tabs of one window.

- **`terminal/`** — the `Terminal` entity wraps an `Arc<FairMutex<alacritty Term>>` and a `Backend`:
  - `Server` (Linux and Windows): a session of a terminal server, this machine's or a remote endpoint's (the terminal's `Host`, see `remote/` below); every tab with a program uses it, local or remote, with no in-process fallback: Brindle runs no PTY or pseudoconsole of its own, and alacritty's `tty` and `EventLoop` are unused. The connection's reader thread parses the session's output (`terminal/server.rs`'s `SessionSink`, with the path style from `Host::path_style`: `PathStyle::Posix` for a remote endpoint, and `process::LOCAL_PATH_STYLE` here), and input, resize and close go to the connection's writer thread. `Terminal::spawn` returns at once; connecting, a reconnect or an upgrade finish in the background with input queued, and a failure (no helper, no connection) becomes that terminal's `Terminal::message`, uncached. A local session's process info stays local, from its pid: `/proc` on Linux, and on Windows the newest descendant of the program in a Toolhelp snapshot, for the name and that process's pid (`process::newest_descendant`; the title tick's look runs off the UI thread, see `workspace.rs`), with the directory from OSC 7 and 9;9 (`process::LOCAL_DIRECTORY` says which). A reported directory is a path the program chose, so no check of it runs on the UI thread: `dir_check.rs`'s `DirCheck` (GPUI-free) keeps what is known of it, the terminal runs the check it asks for on the background executor on `Wakeup` (one at a time, the latest report last, a repeat not checked again), and `Terminal::working_directory` only reads the model; a new tab's or split's directory is named by `spawn_request` and checked on the session's own thread (`Session::start` calls the request there, `with_checked_dir` takes the answer). Restore still probes on the UI thread (`session::resolve_tab`), but only a recorded directory that is absolute in this machine's path style. `shell_integration::is_absolute_path(path, style)` (term-core) is that one rule for a path that came from a program, which `reported_dir`, the restore check and `links::plan` all call: POSIX, it starts with `/`; Windows, it is `X:\` or `X:/` and then has no `:`, no `"` and no control character, so never a UNC, device or rooted path, a stream of a file, or anything a later reader takes for more than a name. A remote session's comes from its host's `PROCESS` reports (`Session::foreground`), with OSC 7 winning for the directory; every arm that assumes the program runs here (the pid lookups, a directory checked on disk, `parent_console_to`) is gated on `Host::Local`.
  - `Remote`: a read-only message with no program (`Terminal::message`), whose text is pushed in with `feed()`; input goes nowhere. Used for error-message tabs.
  - **Program status (`status.rs`):** the OSC 7501 parser and each `Terminal`'s `Records` (one per id, the root is `""`), with the lifetime rules: `end_activity` on OSC 133 `A` and process exit (drops `working`/`blocked`), `seen` on user input (drops `done`/`error`), `reset` on `ESC c`. `handle_found` applies what the scanner found in stream order and answers the `?` query with `write`. `TerminalEvent::Status(Option<Notice>)` carries a notice when a record became blocked/done/error with a different kind, title or message. `Workspace` keeps `Tab::status` (the max over the tab's terminals) and draws it as a coloured dot before the tab's title (`TabTrigger::leading`), followed by the bell dot; `--dump-screen-after` prints the records as `--- status` lines.
  - **Progress (OSC 9;4, `brindle-term-core`'s `progress.rs`):** each `Terminal` keeps `progress: Option<Progress>` (`Normal(Percent)`, `Error`/`Paused(Option<Percent>)`, `Indeterminate`). `handle_found` sets it with `Found::progress_after` (a `Found::Progress` report through `progress::apply`, which keeps the previous percent for an error or a pause without one; `PromptStart` and `Reset` drop it), the same rule the core's `Emulator` follows; `end` (exit, loss, failure) drops it too, and the event-overload reset clears it with the records. Any change emits `TerminalEvent::Status(None)`, and the handlers that refresh the status dot refresh the bar: `Zone::progress` in `ZoneTreeView`, and `Tab::progress` (`ZoneTreeView::progress_summary`, `progress::most_pressing` over the zones: error, paused, the lowest normal, indeterminate) in `Workspace::refresh_status`. `render_tab_bar` and the zone header draw it from those cached values as a `brindle_ui::EdgeBar` (`TabTrigger::edge_bar`, `CardHeader::edge_bar`), its length and colour from `Theme::progress_bar` on the chrome theme (muted, red, yellow, muted at 40% across the width). `--dump-screen-after` prints `--- progress tab=N …` and, in a split tab, `--- progress zone=ID …` lines.
  - **Contexts (OSC 3008, UAPI.15, `brindle-term-core`'s `context.rs`):** each `Terminal` keeps `contexts: Contexts` (a `Vec` of `(ContextId, Fields)`, outermost first, the last active: a new start nests under the active one, a known id's start replaces its fields and truncates after it, an end truncates at it, an unknown end and a start past `MAX_DEPTH` (32) are ignored) and a cached `badge: Option<Badge>` (`Contexts::notable`: the innermost `elevate`/`chpriv` (`BadgeKind::Privileged`, labelled with the target user, else `elevated`) or `session` whose `targetuser` is exactly `root` (Privileged, labelled `root`: real `run0` sends that and never ends it), `remote`, `container` or `vm` (`Elsewhere`, by host or name), cut to 24 characters), recomputed in `handle_found` when `apply` reports a change, which emits `TerminalEvent::Status(None)`. `context::parse` decodes `\xHH` in ids (1–64 bytes in 0x20–0x7E, else the sequence is dropped) and values (≤ 255 bytes, UTF-8, no control character, else the field is dropped) and keeps only `type`, `user`, `hostname`, `targetuser`, `targethost`, `container`, `vm`, `cwd` and `comm`; an unknown `type` is no type. Resets and prompts leave the stack: `end` (exit, loss, failure) clears it, and so does `ChannelEvent::Replay(true)`, since the replay carries the session's stack and its `ESC c` ends nothing, and the event-overload reset (a dropped message leaves it stale). `Zone::badge` (refreshed on `Status`) is drawn in its header (`CardHeader::badge`), and `Tab::badge`, the active zone's (`ZoneTreeView::active_badge`, refreshed on `Status` and on the tree's `TitleChanged`, which a change of active zone sends), on its face (`TabTrigger::badge`), both as the `brindle_ui::Badge` that `zone_view::ui_badge` makes in `Theme::badge_color` of the tab's theme: `BadgeDraw::of` draws a privileged one as `Icon::TriangleAlert` alone in ANSI 3 (made legible on the background at 3:1), its tooltip "Running as <user>", and an `Elsewhere` one as its label in `card_muted_foreground`. The title is cut first, down to its first 8 characters, then a label badge (`brindle_ui::badge::title_and_badge`; an icon badge isn't cut). `--dump-screen-after` prints the active terminal's `--- context …` lines and `--- badge tab=N …` / `--- badge zone=ID …` lines (`describe_badge`, ending in `draw=icon|text`).
  - **Pointer shapes (OSC 22, `brindle-term-core`'s `pointer.rs`, `terminal/pointer.rs`):** each `Terminal` keeps `pointer: pointer::Stacks`, one stack of up to `STACK_DEPTH` (16) entries per screen, each a `Shape` or `None` ("no shape", which an empty set leaves and which reads as Brindle's own). The rules are kitty's (`set_pointer_shape` in `kitty/window.py`): `pointer::parse` reads a set (`=` or none: only the last name Brindle shows counts, since each replaces the top; an empty name is `None`), a push (`>`: each name Brindle shows, at most the last 16), a pop (`<`) or a query (`?`: one `Ask` per item); a set or push with no name Brindle shows parses to `None`, so it is no find. `Shape` is the 22 CSS names GPUI has a pointer for (`Shape::name`/`from_name`, one table). The reader tags each op with the screen active where it sat (`ChannelEvent::Pointer(Screen, Op)`, see "Parsing" below; `Found::Pointer` alone is `Kind::Ignored`), `Terminal::apply_pointer` applies it and writes a query's reply (`Stacks::apply` returns the whole `ESC ] 22 ; … ESC \`) with `write`. `Found::Reset`, `end` (exit, loss, failure), `ChannelEvent::Replay(true)` and the event-overload reset clear both stacks; the server keeps none (`Emulator::feed` ignores the find), so an attach starts with Brindle's own. `terminal/pointer.rs` maps each `Shape` to a `gpui::CursorStyle` (`cursor_style`; `no-drop` shares `not-allowed`'s) and picks the grid's pointer (`choose`, see `terminal_element.rs`). `--dump-screen-after` prints `--- pointer shape=NAME screen=primary|alternate` (`Stacks::describe`) while the active screen's top is a shape.

  `links.rs` finds URLs in a line of chars, decides what a click does and runs the opener (`xdg-open`, or `BRINDLE_LINK_OPENER`) on a background thread. `links::plan(uri, this_host, windows)` is the pure decision, for detected and OSC 8 links alike: `Open` (the link with `"` and whitespace percent-encoded) only for a scheme in `SCHEMES`, the list `find_url` detects; a `file:` link only with no host, `localhost` or this machine's name; on Windows `Reveal(path)` for a `file:` link, which shows it selected in Explorer (`explorer.exe /select,`, or `explore` on a directory) and never opens it, and only for a path that passes `is_absolute_path` as Windows will read it (percent-decoded, every `/` a `\`): a network path (`\\host\…`) is refused as another host, and any other as `NoDrive` (a device or rooted path, `file:shell:…`, no drive, `C:x`, a stream, a `"` or a control character), since Explorer reads more than paths and the path goes inside one pair of quotes on its command line; else `Refuse(Refusal::{NoScheme, Scheme, OtherHost, NoDrive})`. `failure_text` words a refusal or an opener's failure, and `TerminalView::open_link` emits it as `LinkFailed` (at once for a refusal, later from the opener's thread for a failure) instead of writing into the terminal: `ZoneTreeView` passes it on from any tab, and `Workspace` shows it as a transient notice on the config line (see `settings.rs`). `link_at` returns the link at a grid point: the cell's OSC 8 hyperlink, or else a URL found in the logical line, where rows are joined by `WRAPLINE`. `TerminalView` looks links up only in event handlers while ctrl is held (hover) or on a ctrl-click, never in `prepaint`, which just underlines the stored spans.
  - **Parsing and shell integration (`shell_integration.rs`, `server.rs`):** every backend parses through Brindle's own `Parser` (vte processor + OSC 133 scanner), which lives in `brindle-term-core` with `Marks` and `Records` (`terminal::{shell_integration, status}` re-export them); alacritty's own processor never sees bytes. For `Server`, `SessionSink` parses on the connection's reader thread under the term lock; `feed()` does the same for a `Remote` message. `Sink::write` scans with `scan_positions`: a chunk with no `Found::Pointer` sends its finds and then parses in one go; one with a pointer op is parsed in pieces under one hold of the locks, every find sent where it sits and each op sent as `ChannelEvent::Pointer` tagged with the screen (`ALT_SCREEN`) the parse reached, so finds keep their stream order (a push then `ESC c` leaves the stacks empty). A held replay's pointer ops are dropped (a replay holds none). Lock order is parser → term (`lock_unfair` while holding the parser) → marks. Marks are absolute lines (`base + Line`); `base` is kept by finding the row that was at `Line(0)` after each processor call (rows rotate, their cells never move), and resizes remap marks through logical lines. Synchronized-update timeouts are flushed from the GPUI side on `Wakeup`. VS Code's OSC 633 is read in the same pass: `parse_mark` takes `133` or `633` for `A`–`D`, `633;P;Cwd=` is one more `reported_dir` form (its `\\`/`\xHH` escapes decoded by `decode_vscode`, then the usual `is_absolute_path`), and `633;E;<line>[;nonce]` (or a `C` mark's `cmdline_url=`, which fish 4 writes) becomes `Split::CommandLine`, applied as `Marks::set_line` on the latest command while it has no output mark. `Command::line` is copied only, never run; the nonce is ignored. `Marks::last_command_line` returns a `LineSource` (the reported line, or the `B`..`C` span), which `Terminal::last_command_line_text` reads under the term lock for `TerminalView::copy_last_command`. `Marks::prompt_seen` is a sticky flag set by any `A` mark (kept by a clear, a prune and the alternate screen); `last_command_line_text` returns `None` until it is set, and `Workspace::open_command_palette` passes it (`Terminal::has_prompt_marks`) to `actions::palette_lists` as `PaletteFacts`, which hides Copy Last Command Line until then.

  - **Elevation (Windows: `process.rs`, `context.rs`):** `process::newest_descendant` returns the foreground process's pid with its name, so the title and the elevation name the same process. `process::elevation(pid)` opens the process (`PROCESS_QUERY_LIMITED_INFORMATION`) and its token (`TOKEN_QUERY`) and reads `TokenElevation`. It answers `Elevated` or `Standard` only from a token it read; any failure, a denial included, is `Unknown`, never inferred. Off Windows it is always `Unknown`. `process::detect(roots, &mut ElevationCache)` takes one `Snapshot` and reads the token of each foreground pid the cache doesn't hold. The cache keeps only what was read (`Standard` or `Elevated`) and is pruned to the snapshot's pids, so a reused pid is read again. The title tick runs `detect` on the background executor and applies it with `Terminal::set_detected` (see `workspace.rs`). `Terminal`'s `Notable` keeps `contexts`, `elevation` and the cached `badge`, recomputed as `context::badge(contexts.notable(), elevation)` whenever either changes: `Elevated` is `Privileged`, labelled `Administrator`, whatever the program announced; `Standard` and `Unknown` leave the announced context's badge. The pure rule and its tests are in `brindle-term-core`'s `context.rs` (`Elevation`, `badge`).
  - **Line ends (`terminal/mod.rs`, `process::LOCAL_LINE_END`):** grid copies (Copy, `copy_on_select`, Copy Last Command Output and Line) pass through `copied_text(text, LineEnd)`, which joins lines with `\r\n` where `LOCAL_LINE_END` is `CrLf` (Windows) and with `\n` elsewhere, without doubling a `\r\n`. OSC 52 text and a link's address are written as they are.
  - **Mouse clipboard feedback (`terminal/feedback.rs`, pure, in `PURE_MODULES`):** `Feedback { kind: FeedbackKind::{Copied, Pasted, NothingToPaste}, at, shown }` and `phase(now)` give `Phase::{Shown, Fading(opacity), Gone}`: shown for `SHOWN_FOR` (800 ms), then faded over `FADE_FOR` (200 ms). A new feedback replaces the old, so two never stack. `TerminalView` holds it in a `FeedbackSlot` and sets it on a mouse-up for which `finish_selection` reports a clipboard write (`Copied`), and on a right press that `right_press` says is `Paste` (`Pasted`, or `NothingToPaste` when the clipboard has no text). Keys and palette actions never set it. `TerminalView::render_feedback` draws it with no focus handle and no mouse handler: a brindle-ui tooltip surface with `Icon::Copy`, `Icon::ClipboardPaste` or `Icon::Ban` and `FeedbackKind::label` ("Copied", "Pasted", "Nothing to paste"), anchored 12 px right of and below the pointer and kept inside the grid's bounds (`Anchored::within`). Its timer task notifies the view every `FADE_FRAME` (16 ms) only while the feedback isn't `Gone`, then ends. The dump line `--- feedback kind=…` is `TerminalView::describe_feedback`.
  - **Notice line (`terminal/tab_note.rs`):** a failure that belongs to a running tab and doesn't end its session is one dim line in its terminal, as the "connection lost" line is. `tab_note::line(text)` drops every C0 and C1 control (so text from a server or a relay can't move the cursor or end the dim style) and joins lines with `; `; `NoteGate` refuses a repeat until the session prints again. `Terminal::note` writes it on the UI thread, holding it in `held_notes` while an attached session's first replay is still to come and writing it after the replay, or after a `Lost` or `Failed` line; `SessionSink::note` writes it from the connection's reader thread through the sink's gate and its held-replay path. Callers: a server `ERROR` about a shown session and a message that can't be encoded (`Connection`) and a restored tab whose profile is gone. A profile shortcut past the last profile opens a message tab. A launch's unknown profile (`brindle terminal wrk`) opens nothing: `workspace::profile_for`, one rule for the first launch and a forwarded one, refuses it as a usage error (`LaunchRefusal`). A link that isn't opened is the window's, not the tab's: it goes to the config line, never into the terminal. A relay link's lost line carries its first line of cause (`lost_line`), and the local server's give-up line its last error (`reconnect_gave_up`).
  - **Windows programs (`cmdline.rs`):** pure helpers, tested everywhere, for what Brindle asks the server to run: the default program (`windows_default_program`), the config editor's command, the merged environment (`merge_environment`) and console-default titles. Sessions' pseudoconsoles and command lines are the holder's (see "ConPTY in the holder" below).

  Alacritty events, and what the sink finds, reach GPUI through an unbounded channel drained by a spawned task, each passing the terminal's `EventGate` (`terminal/events.rs`, `Listener::send`) on its producer's thread first, which is what bounds the channel (`process R9`). `Wakeup`s, title changes, foreground reports and clipboard writes are merged at the source: at most one marker per kind waits, its latest value in the gate's slot. Life events (replay markers, exit, loss, failure, `Broken`, `InputRefused`) are always queued. Side events (bells, notifications, status reports, replies to the program's queries) are dropped from 2048 waiting until under 512 (`EVENT_MARKS`); the task then logs how many at `warn` and, if status, progress or context reports were among them, resets the terminal's `Records`, progress and contexts. The gate's mutex is a leaf lock, taken last (under the parser and term locks when alacritty sends mid-parse) with nothing taken under it. The task tells the gate once per chunk what it took (`EventGate::took`), then applies the chunk in order. Once `pace::BURST` (4) updates in a row came less than `pace::PACE` (4 ms) apart, it waits out the rest of `PACE` before the next, and each update takes ready chunks for up to `pace::BUDGET` (16 ms, `pace::drain`). Replies the emulator generates go through `reply()`, which drops them for read-only `Remote` terminals. Pointer shape ops (`ChannelEvent::Pointer`) are side events that count as status for the overload reset, which clears the pointer stacks too. `keys.rs` and `mouse.rs` are pure xterm encoders with unit tests.
- **`remote/` / `brindle-remote`** — the `brindle-remote-protocol` crate (`remote-protocol/`, re-exported as `remote::protocol`) defines the bounded frame header, the frame marker and the terminal server's protocols, shared by the app and the helper. The helper is the `brindle-remote-agent` crate (`remote-agent/`, binary `brindle-remote`): the terminal server's roles, the relay and the management commands (below). `Host` (`remote/host.rs`) is the server a session runs in: `Local`, or `Remote(RemoteTarget)`, equal when the targets name the same endpoint; each tab records its own, and its splits stay on it whatever the profile targets later. A remote profile's tabs run on `Backend::Server` like local ones, in the endpoint's own terminal server, through one connection per endpoint (`remote::local::shared(host)`, `Connection::relay`; see "Brindle's client" and "Relay" below). `client.rs` deploys a matching Linux helper and launches the relay through OpenSSH or Docker/Podman exec (`remote_command`). An endpoint keeps the helper cached by version and digest: an SSH host in the user's `~/.cache/brindle/<version>-<digest>/` (user-only), a container in root's `/tmp/brindle-helper-<version>-<digest>/` for all its users (root makes the directory, takes the copied file over, renames it into place and removes other builds' directories; a directory someone else made there is refused by name and left alone; nothing is removed when a connection ends). `client::launch` starts an endpoint's relay for `local::relay::dial_with`: one command, a script that execs the cached helper's `relay` or exits 97 (in a container, as the profile's user, when the directory or the helper isn't root's own or is a symbolic link); only on 97 is the helper deployed and the launch run once more, and ssh's own 255 is a connection error. The link (`local/{link,relay}.rs`) is the relay process's stdin and stdout from its frame marker on (`skip_preamble` drops what the shell printed first), and its stderr is kept for errors: `RELAY_HOST` first, then client protocol 2, whose `HELLO` asks for `linger_secs` (300) and `process_info`, so a remote tab's sessions outlive a dropped link and its title and directory come from `PROCESS`. A remote `SPAWN` carries the relay's environment with the profile's over it (`relay_env`, `SpawnRequest::remote`). Each side sends `RELAY_HEARTBEAT` after 10 s without a write; Brindle ends a link that read nothing for 30 s (`Timings::dead`), the relay one that read nothing for 60 s. The relay's liveness (`Liveness`, `remote-agent/src/liveness.rs`, the relay's alone) is stamped by its stdin reader thread, which drops heartbeats itself and marks itself `busy` while handing a real frame to the core, because copying output to a slow client can block and leave healthy clients' frames unread; never measure it where output is copied. A dropped link reconnects with backoff and no time limit, writing a dim "connection to … lost; reconnecting…" line into the endpoint's tabs, and a connection that isn't eager closes 5 s after it was last in use (`Timings::idle`).
- **Terminal server (OpenSpec changes `terminal-server` and `terminal-server-windows`)** — local tabs run in sessions of a persistent server, two roles of the `brindle-remote` binary (`remote-agent/src/server/`, built on Linux and Windows; `main.rs` adds the Windows-only `launch` trampoline), so sessions survive a Brindle exit, a core crash, restart or upgrade. The helper is required (`HELPER_MISSING` names `BRINDLE_SERVER_HELPER`, which `remote::find_server_helper` honours first; then Linux tries `BRINDLE_REMOTE_AGENT` and the helper beside the exe, while Windows looks only for `brindle-remote.exe` beside `brindle.exe`, since there `BRINDLE_REMOTE_AGENT` keeps naming the Linux helper for remote profiles).
  - **Directory (Linux):** `$BRINDLE_SERVER_DIR`, else `$XDG_RUNTIME_DIR/brindle`, else `~/.cache/brindle/run` (`server_dir::resolve` in `remote-protocol`, used by both sides; mode 0700). It holds `core.lock`/`core.sock`/`core.log` and `holder-<build>-<n>.{sock,lock,log}`. Socket paths must fit `sun_path` (108 bytes), which is why e2e server directories are under `/tmp`. Peers are checked with `SO_PEERCRED`. A role starts as `<role> --ready-fd N` (`platform/unix/daemon.rs`: double fork, `setsid`, stdio to its log, one ready byte). It closes the ready pipe right after that byte, and a Linux starter reads the pipe to its end and counts the role as ready only if the pipe held exactly that byte (`remote-protocol/src/ready.rs`): passing the pipe as fd 3 can replace the pipe through which `Command` reports a failed exec, and that error's 8 bytes then arrive in the ready pipe. Brindle (the core), the core (holders) and a holder (the core) start roles through `systemd-run --user --scope` in a `brindle-<role>-<hex>.scope` (`remote-protocol/src/scope.rs`), so stopping the desktop's app scope doesn't kill them; without `$XDG_RUNTIME_DIR/systemd/private` or `systemd-run`, or with `BRINDLE_NO_SCOPE=1` (the helper's tests and e2e set it), they start directly with one log line. `systemd-run --scope` execs the program itself, so roles are run as `/proc/<own pid>/exe`, not `/proc/self/exe`.
  - **Directory, pipes and access (Windows):** `$BRINDLE_SERVER_DIR`, else `%LOCALAPPDATA%\brindle\run`, or `run-elevated` for an elevated process so elevated and unelevated never share a server (`server_dir::resolve_windows`), created with a protected DACL for the user and SYSTEM (`platform/windows/dir.rs`). It holds `core.lock`/`core.log` and `holder-<build>-<n>.{lock,log}`. The pipes aren't in it but named from it (`remote-protocol/src/{server_dir,endpoint}.rs`): `\\.\pipe\brindle-server-<h>-core` and `…-holder-<build>-<n>`, where `<h>` is the FNV-1a hash of the directory's canonical path plus the user's SID string (so the directory must exist; no length limit), and the core finds holders by their lock files. The locks are `LockFileEx` (exclusive, fail immediately), released when the process dies. Every pipe (`remote-protocol/src/{access,win}.rs`) gets the SDDL `D:P(A;;GA;;;<user SID>)(A;;GA;;;SY)` plus a no-write-up mandatory label at the creator's own integrity, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` on a name's first instance, so a squatted name fails the bind (error 5 or 231, read as `AddrInUse`). Before reading anything the server checks the client (`GetNamedPipeClientProcessId`, then that process's `TokenUser` and `TokenIntegrityLevel`; `ImpersonateNamedPipeClient` fails until a read) and closes one with another SID, a lower integrity or an unreadable token. Clients (the CLI, a holder dialling its core, and Brindle's client) check the server before writing (`GetNamedPipeServerProcessId`, `win::check_server`) and refuse another SID or any other integrity, so no process uses a server at another integrity level.
  - **Detached start (Windows, `platform/windows/daemon.rs`):** the starter runs `<helper> launch <role> --ready-handle N` (std passes the ready pipe's write end, inheritable, as handle `N`), and the `launch` trampoline `CreateProcessW`s `<role> --ready-handle N` from its own image and exits at once, like the double fork, so no role's parent is a live process and `taskkill /T` or "End process tree" on Brindle doesn't reach it. The role is created with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB | CREATE_UNICODE_ENVIRONMENT` and a `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (the ready pipe and the trampoline's stdout/stderr). A job that forbids breakaway fails that with `ERROR_ACCESS_DENIED`; the trampoline then retries without the breakaway flag and says so in one stderr line, its starter's log (a `KILL_ON_JOB_CLOSE` job then still ends the role). The role writes one ready byte once listening, then points stdout/stderr at its log (`daemonize`). `brindle-remote.exe` stays a console program for its CLI; the flags keep roles from opening a console.
  - **Per-build copies (Windows):** Windows locks a running image, and a holder runs for days, so roles never run from the installed helper: `win::ensure_helper_copy` (for Brindle's client, group 7) copies it to `<copies>\<build id>\brindle-remote.exe` (`server_dir::helper_copies`: `bin` in `BRINDLE_SERVER_DIR` when set, else `%LOCALAPPDATA%\brindle\server`), through a temporary name and a rename, keeping the last-write time; a rename another process won is used once its build id checks out. Cores and holders start roles from their own image (`win::own_image_path`, `GetModuleFileNameW`), which is the copy. At its start the core removes other builds' copies (`prune_copies` → `win::prune_helper_copies`); one still running can't be deleted and stays.
  - **Platform layer (`server/platform/{unix,windows}`):** the core and the holder name no platform type. What they need from the system is in one set of modules per platform with the same items: `event_loop` (`Loop`, `Source`, `Waker`), `conn` (the `Stream` under the shared framed `Conn`), `listen` (`Listener` with the peer check, `connect`; on Windows its paths are pipe names), `lock`, `daemon` (`ready_from_args`, `start_role`, `ReadyPipe`), `pty` (`Pty`, `Program`, `Group`), `piped` (`Piped`, its three streams' sources, `PipeCommand`, `spawn_piped`, sharing `pty`'s `Program` and `Group`. Linux: three `pipe2(O_CLOEXEC)` pairs, the holder's ends non-blocking, the program `setsid` with default signals (`pty::default_signals`) in `pty::start_directory` and exactly the request's environment. Windows: three pipes from `pty::pipe` (`server_dir::pty_pipe` names), the program's ends inheritable and the whole `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, its job given with `PROC_THREAD_ATTRIBUTE_JOB_LIST` (`Job`, `KILL_ON_JOB_CLOSE`), so a pipe session's `Program` and `Group` hold `Ends::Job` where a PTY session's hold `Ends::Console`; the module is private in each seam and its items are re-exported at `platform::`'s top, since `platform::piped` is the neutral module: `CREATION_FLAGS` (`CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT`), `STARTUP_FLAGS`, `JOB_LIMITS` (`KILL_ON_JOB_CLOSE`), `ChildEnds::handle_list`, `launch` (the spawn's exact environment, the program resolved in its `PATH` by `conpty::cmdline::resolve_program`, `launch_line`), `batch_hint` ("npx is a batch file (C:\…\npx.cmd); run it as `cmd /c npx …`", the first `.bat`/`.cmd` in `PATH` order, with the arguments quoted) and `HangUp` (`CloseInput` at once, `EndGroup` after `pty::GRACEFUL_SHUTDOWN`, `KillRemaining` after another)), `dir` and `sys`. Handlers read and write through a source's owner, never through what the `Source` wraps, so the Windows loop can do the I/O itself. The decisions sit in neutral modules beside the seams, pure and tested on every platform, which the seams gather for, call and apply: `server/platform/{ready_arg,ensure_dir,pipe_state,wait,piped}.rs`, `conpty/{cmdline,choice,hosts}.rs`, `pty/{program,stat}.rs`, and in `brindle-remote-protocol` `access` (`admit_client`, `Dacl`), `server_dir` (pipe names, holder sockets, helper copies) and `hresult`.
    - **Windows loop (`event_loop.rs`, `pipe.rs`):** one IOCP with a readiness facade. Each pipe source keeps one overlapped read in flight into a buffer it owns and is readable while that holds bytes or hit the end; writes copy into an owned buffer and go out overlapped, writable while under `WRITE_MARK` (1 MiB); a listener keeps one overlapped `ConnectNamedPipe` pending and is readable once a client connected. A wait takes queued packets, then checks every source, and blocks only when none is ready, so readiness stays level-triggered as with poll(2). `Conn::input_waiting` is the buffered count plus `PeekNamedPipe`. The waker posts a packet (`PostQueuedCompletionStatus`); there is no `SIGCHLD`, so the holder watches each program with `Waker::wake_on_exit` (`RegisterWaitForSingleObject`). Deregistering and dropping cancel I/O with `CancelIoEx` and take the packets before buffers are freed. A pipe has no half-close: `shutdown_write` closes the handle once the pipe has taken everything written.
  - **Holder (`hold`, `holder.rs`):** one thread on the platform's `Loop` (Linux: `PollLoop`, poll(2) plus a `SIGCHLD` self-pipe; Windows: the IOCP loop). It owns many sessions' PTYs (Linux: `remote-agent/src/pty/unix.rs`; Windows: ConPTY, below), is the programs' parent, and parses nothing. Per session it stores, uninterpreted, the core's last checkpoint and the raw tail since (1 MiB cap, then `truncated`). It exits when it has no sessions (10 s after start if it never had one). On Linux its `Hangup` sends SIGHUP to the process group before it closes the PTY (closing first let a program blocked reading the terminal exit on the failed read), then SIGKILL while the group has members, and its programs start with every signal's default action and an empty signal mask (`pre_exec` in `pty/unix.rs`), whatever the holder inherited (under `nohup`, an ignored SIGHUP). When a write to its core fails, it still handles what that core had sent (up to 16 MiB) before it drops the core. It stops reading PTYs once 8 MiB is queued to its core (`CORE_QUEUE_HIGH`) and resumes under 2 MiB (`CORE_QUEUE_LOW`), through the pure `core_backlog` and `read_limit`; input past 4 MiB waiting for one session is dropped with an `ERROR` (lossy by design, behind Brindle's input budget of the same size). Each message from its core is handled under `catch_unwind` (`Holder::guarded`): a failure is answered for its unit (`unit_of`), `SPAWN_FAILED` for a `SPAWN` (hanging up a session it had made), an `ERROR` for that session (abandoning a checkpoint it was assembling) or for the holder, and the sessions and connection carry on; `BRINDLE_TEST_HOLDER_PANIC` (debug builds, `server/fault.rs`) injects one through a marker in a `SPAWN`'s arguments or an `INPUT`'s bytes. A connection whose first message isn't `HELLO`, or whose `HELLO` shares no version, gets an `ERROR` and a graceful close (`Conn::close_for`, within `REFUSAL_CLOSE_LIMIT`, 1 s), as the core does for a client, so the peer reads the error and then the end, not a reset. With no core for 3 s (`CORE_GRACE`) it starts its own binary's `serve`, backing off 3 s to 60 s (`BRINDLE_TEST_HOLDER_CORE_ARGS` overrides the args in tests). On Linux it sets `IUTF8` on every PTY. Pipe sessions (H1 version 3's `SPAWN_PIPES`, `platform::spawn_piped`; a session's streams are `Io::{Pty, Pipes}`): stdout is the session's output exactly as a PTY's is (tail, `OUTPUT`, `PAUSE`, `covers`), stdin takes `INPUT` under the same cap on a token of its own (`Source::Stdin`), and stderr (`Source::Stderr`) is read always into a 16 KiB ring (`StderrRing`), sent once as `STDERR_TAIL` just before `EXITED`, or right after the session's `TAIL_END` in an adoption when it ended with no core (logged as "ended with no core to tell; kept for the next one"); the session ends once stdout and stderr have both ended or been quiet (`streams`, then `policy::drained`). A hang-up is `platform::piped::HangUp`'s steps (`hang_ups`): stdin closes at once while stdout and stderr are still read, the group (Linux `SIGHUP`) or job (Windows `TerminateJobObject`) ends a grace later, and what remains is killed after another. `RESIZE` and `REPARENT` for one get an `ERROR` ("session N is on pipes and has no size" / "… no console window"). A core that negotiated H1 below 3 isn't shown them (`policy::shown`): not in `WELCOME`, no `OUTPUT` (their output only grows the tail), no `EXITED`, so a finished one waits for a core that speaks 3. A failed spawn is `SPAWN_FAILED` "cannot run <command>: <error>" (on Windows, a bare name that is a batch file gets `batch_hint`'s text). `tests/holder.rs` covers them on both platforms (`a_pipe_*`, `an_older_core_isnt_shown_a_pipe_session…`).
  - **ConPTY in the holder (Windows, `remote-agent/src/conpty/`, `platform/windows/pty.rs`):** the `Api` resolution, `Pseudoconsole` and the launch-line quoting (`cmdline::launch_line`) live in the agent, and `remote-agent/build.rs` embeds the packaged ConPTY (`scripts/fetch-conpty.ps1` fetches it; Brindle's own exe embeds none). `conpty.dll` is loaded by absolute path from beside the helper, else from a copy extracted to `%LOCALAPPDATA%\brindle\conpty\<version>`, and only when the bytes there match the embedded ones; otherwise the inbox kernel32 functions are used, with one log line. `SPAWN`'s command is never empty on Windows (Brindle resolves a profile without one itself: `cmdline::windows_default_program`); the holder quotes it with `launch_line` and passes the environment as given. `BRINDLE_CONPTY=inbox` is read from the session's `SPAWN` environment, not the holder's, and each `Api` is resolved lazily and cached. Each session has two one-way pipes, input then output (`server_dir::pty_pipe`: `\\.\pipe\brindle-pty-<holder pid>-<n>`, consecutive `n`, first instance, the server pipes' security); the host gets synchronous ends, the holder's overlapped ends make one `Source`. Pseudoconsoles are created with `PSEUDOCONSOLE_GLYPH_WIDTH_WCSWIDTH` (0x10), which matches the grid's per-code-point widths; the host's grapheme default makes ❤️ two cells.
    - **Exit:** the exit wait wakes the loop; the holder releases (`ReleasePseudoConsole` when exported) and closes the pseudoconsole on a short-lived thread, since `ClosePseudoConsole` can block until output drains, keeps reading output to EOF, and sends `EXITED` after the last output with `GetExitCodeProcess`'s code.
    - **Hangup (`CLOSE`, `KILL`, `STOP`, a `kill` session's owner gone):** the host sends `CTRL_CLOSE_EVENT` once, only to processes connected then, so the close thread first waits up to `CONNECT_LIMIT` (`pty::GRACEFUL_SHUTDOWN`, 1 s) for the root to be on the console, keeping a copy of the input end open until then (the input ending is a close too), then closes. After the same grace `Group::kill_remaining` calls `TerminateProcess` on the root if alive and on every process still on the session's console host (`conpty::console_host`, through the undocumented `NtQueryInformationProcess` class 49; if that fails, only the root). Programs that left the console (a GUI app) keep running; there is no per-session job object.
    - **`REPARENT`:** the Windows core forwards a client's `REPARENT { session, hwnd }` (protocol 1 message 13) to the session's holder (H1 message 11), which calls `ConptyReparentPseudoConsole` so the console window, and programs' dialogs, are owned by that window; it is advisory (no reply). The inbox ConPTY has no such export, which is logged once. A Linux core refuses it with an error. The owner is never cleared, and the core doesn't keep the HWND across restarts: a client re-sends it after reconnecting. Brindle sends it from `Terminal::parent_console_to` (when a terminal's view is made in the window): `Session::reparent` holds the HWND until the session has started or attached, and `Connection` keeps it per session (in its `State.sessions` entry) and sends it again after every later `REPLAY_END`, which is a reconnect's.
  - **Core (`serve`, `core.rs`, `core/{agents,clients,holders,sessions,manage,policy,process,screen}.rs`):** one thread on the same loop; takes `core.lock` for its life (`flock`; `LockFileEx` on Windows; the loser of a start race waits for the winner, then exits 0), serves clients on `core.sock` (Windows: the core pipe), drives holders and runs an `Emulator` per session whether or not a client is attached. Its decisions are pure, in `core/policy.rs`: the `Lifecycle` (when it accepts clients, the reconnect grace, the idle exit) and the session, client and holder policies the handlers call. For agent sessions (`agents-sessions`) it also holds `agent_checkpoint_due` (every reducer `Moment`, a step-down, a detach, else past `CHECKPOINT_AFTER`), `placement`'s `SpawnMode` (pipe spawns go only to a holder of the core's build that negotiated H1 3, `PIPES_PROTOCOL`), and what a client below protocol 4 (`AGENT_PROTOCOL`) meets: `shown` by `SessionKind`, `attach_refusal` ("session N is an agent session, which needs client protocol 4", before anything else about the session), `returning` without agent sessions, `agent_request_refusal` ("AGENT_PROMPT needs client protocol 4") for the agent messages, `LIST` leaving agent sessions out, and `agent_spawn_refusal` ("an agent session needs a command"). A session's `Content` is a terminal's `Screen` or an agent's `Agent` (`core/agents.rs`, the shell around `acp::reduce`): `SPAWN_AGENT` resolves the absolute directory (`platform::agent_directory`, deciding through `platform::piped::agent_dir`: the request's, `~` expanded, else the home, else the core's), which is the `SPAWN_PIPES` `cwd`, the meta's `cwd` and `session/new`'s, and queues a `SpawnRequest::Agent` (placed with `SpawnMode::Pipes`). Every input (`SPAWNED`, stdout, the stderr tail kept for `EXITED`, a lost holder, the attached client's `AGENT_*` commands, a due `Output::wake` from `tick`) is stepped under `catch_unwind` (a panic becomes `Input::Fault`, the command answered "session N: the terminal server's ACP handling failed"; `BRINDLE_TEST_ACP_PANIC` injects one), and its `Output` applied in order: the events as `TRANSCRIPT` to the attached client unless its replay waits, a checkpoint when `agent_checkpoint_due` says (`covers` from `Lines::covers`), the stdin as `INPUT` while the program is live, the hang-up; then the reply (`OK`, or `ERROR` "session N: …"; none for a taken cancel). An agent session is listed at 0×0 with `SessionInfo.agent` (the log's `Activity` mapped one to one, and the name from `initialize`), its `ATTACH` replays `Transcript::replay()` as `TRANSCRIPT` between `REPLAY_START` and `REPLAY_END` with the size ignored, and `RESIZE`, `DATA` and `REPARENT` are refused naming it. On adoption its holder's checkpoint is kept until the tail, then `acp::checkpoint::adopt` rebuilds it and the tail is fed as stdout. Agent sessions are left out of the `PROCESS` look. **The queue of one:** each agent session has one prompt slot, `Transcript::slot()` (`Slot::{Empty, Waiting, Held}`), set by the reducer and sent as `Queue { slot }` (live, and in every replay while not empty), so it lives in the log, the checkpoint and the replay, never only in a client. An `AGENT_PROMPT` during a turn waits, and is sent only after the turn ends `Ended { EndTurn }`; any other ending, a cancel, `-32000`, the agent failing or exiting, or lost output holds it with its `HoldReason`. `AGENT_RESEND` sends a held prompt (queued again while a turn runs, refused while the agent isn't ready) and `AGENT_UNQUEUE` discards a waiting or held one; a prompt while the slot is taken and a turn runs is refused ("a prompt is already queued"), and with no turn running a new prompt is sent with a held one left as it is. The slot never changes the listed activity. A session's state is a `Life` (starting, running, hung up, or exited with the exit kept for its owner) and an `Ownership` (attached, lingering, awaiting its owner after an adoption, or detached, each with since when), with its owner an `Option<ClientToken>`. It accepts clients only after adopting the startup holders (≤ 5 s). Close policies: `kill` ends on `CLOSE`/`KILL`/`STOP` and when the owner (a `client_token`) is gone, after `RECONNECT_GRACE` (10 s) for sessions adopted by a new core; `detach` ends only on `KILL`/`STOP`/exit. A client may ask in its `HELLO` for `linger_secs` (capped at `MAX_LINGER`, 600 s): its `kill` sessions then outlive its connection that long (`Ownership::Lingering`, kept only in this core; an exit meanwhile is kept for it, as for an adopted session) and are hung up only when it hasn't come back by then; `replay` clears it. A `HELLO` with the token of a client that is still connected replaces it (`take_over`): the stale connection (a link that died silently) is closed without `client_gone`, its sessions lose their client but keep their owner and go to the new one with replays, its spawns not yet sent to a holder fail and its sessions still starting are hung up (`reattach` never gives back one still starting). `ATTACH` makes the client the owner; `DETACH` clears the owner and switches `kill` to `detach`, so a reconnecting client gets back only the sessions it still owns. A `DETACH`'s or `SET_LAYOUT`'s `layout` (Brindle's record of the session's tab, opaque to the core; `SET_LAYOUT` stores only a change) goes into the session's meta, unless its JSON is over `MAX_LAYOUT` (64 KiB; logged and dropped, the detach still applies), so it survives core restarts and upgrades through `SET_META`; `LIST` reports it while the session is detached, and `ATTACH` clears it (OpenSpec change `session-layout-in-server`). Each session's `SessionMeta` (owner, policy, a random 128-bit hex `key`, `profile`, `started`, `layout`) lives in its holder; the core sends `SET_META` on every owner or policy change to H1 v2 holders (logged and skipped for v1), so the next core sees it. A stored meta the next core can't read whole (`SessionMeta::from_value`'s `MetaFault`: a field of the wrong type, or not an object; a missing field is just its default) is adopted detached with no owner, keeping what was well formed and getting a fresh key if its key was malformed (`adopt_meta`); `core.log` names the session and the fields, and the repaired meta is stored back with `SET_META`. A replay waits until the session's last `SET_META` is in its holder's connection (`Session::storing`, a count of bytes written to it; each turn flushes holders before clients, then sends those replays), so a client that has its `REPLAY_START` gets the session back even from a core killed right then. Session ids restart at 1 in a fresh core; the key tells sessions apart across cores. `LIST`'s `SessionInfo` carries key, title (the emulator's), `started`, profile, `owned` (an owner is set and no client attached: it may come back) and `detached_secs` (since its last client left; from the adoption for an adopted session). Clients that negotiated protocol 2 and set `HELLO`'s `process_info` get `PROCESS` (`process.rs`): the foreground program's `comm` and `cwd` (Linux: `tpgid` from `/proc/<pid>/stat`, through `platform::pty::foreground`; a Windows core sends none), once after a spawn or attach, then on change. The core looks once a second (`PROCESS_LOOK`) and only at sessions with output or input since its last look; activity younger than 250 ms at a look keeps the flag for the next, since a keystroke's echo comes before the shell makes the program it starts the foreground. It exits 5 s after the last session and client (`UNUSED_LIMIT`). Backpressure is per session: `PAUSE`/`RESUME` once a client's queue passes 1 MiB / falls under 256 KiB. A client found gone by a failed write is dropped only once the frames it had sent are handled (up to `DEAD_CLIENT_READ_LIMIT`, 16 MiB, as a holder does for its core; nothing is sent back), so the `DETACH`es Brindle sends as it quits count even when the core has output queued for it. Each `Term` feed runs under `catch_unwind` (`screen.rs`): a panic marks that emulator broken (replays are then `ESC c`) and the session keeps forwarding output; `BRINDLE_TEST_FEED_PANIC` (debug builds) injects it.
  - **Protocols (`remote-protocol/src/{client,holder,wire,version}.rs`):** client protocols 1–4 (`PROTOCOLS`) and core↔holder H1 share the frame header (`type: u8, len: u32 BE, payload`) with their own message numbers and version ranges, negotiated per connection by `HELLO`/`WELCOME`. JSON fields are additive with defaults; a new message type needs a new version; transcript tests pin both. Client protocol 2 adds only `PROCESS` (message 41), sent only on connections that negotiated 2 and asked, so a 1–2 client and a 1-only core agree on 1. Client protocol 3 adds only `SET_LAYOUT` (message 14, client → core: the layout of a session the client has attached, refused with an `ERROR` below 3 or from a client without it attached; transcript `client-set-layout`), so a 1–3 client and a 1–2 core agree on 2 and Brindle sends its layouts only on quit. `HELLO`'s `linger_secs` and `process_info`, `SessionInfo`'s `owned`, `detached_secs` and `layout`, and `DETACH`'s `layout` (`client::Detach`, no longer a `SessionRef`) are additive fields; `client-layout` and `holder-set-meta-layout` are their transcripts, and the older fixtures stay byte for byte. H1's `meta` is an opaque JSON blob the core owns. H1 version 2 adds `SET_META` (message 14, replaces a session's stored meta). Client protocol 4 adds agent sessions: `SPAWN_AGENT`, `AGENT_PROMPT`, `AGENT_CANCEL`, `AGENT_PERMISSION`, `AGENT_UNQUEUE` and `AGENT_RESEND` (messages 15–20), `TRANSCRIPT` (message 42: `brindle-transcript` events as JSON objects the codec checks are objects and doesn't read; `pack_transcript` splits a batch into frames of whole events) and `SessionInfo.agent` (`AgentInfo { activity, name }`, omitted for a terminal session); transcripts `client-agent-session`, `client-agent-attach` and `client-agent-old-client`, whose `TRANSCRIPT` events `transcript/tests/events.rs` checks decode and fold. Brindle still offers 1–3 (`BRINDLE_PROTOCOLS` in `src/remote/local.rs`, its `ToClient::Transcript` arm logged and dropped), so it never meets an agent session; `agents-profiles` raises it. The core sends a connection only the events of the version it negotiated: event kinds and enum values are frozen for protocol 4, which may only gain optional fields (`brindle-transcript`'s `v4/` fixtures), and a client below 4 is never listed or attached an agent session and has the agent messages refused by name. H1 version 3 adds sessions on plain pipes: `SPAWN_PIPES` (message 15), `STDERR_TAIL` (message 41, binary, at most `MAX_STDERR_TAIL`, 16 KiB, a longer one refused both ways) and `HeldSession.mode` (`SpawnMode`, omitted for a PTY); transcripts `holder-spawn-pipes`, `holder-pipes-adopt` and `holder-pipes-old-core`. The holder runs them (see the holder's entry), and the core spawns them for agent sessions, only on holders of its own build (which speak 3); a core below H1 3 adopting a newer holder isn't shown them, and they come back to the next core that speaks 3. Large checkpoints/tails are chunked (`*_BEGIN`, 64 KiB `*_CHUNK`s, `*_END`); a receiver keeps at most `MAX_OPEN_BLOBS` (16) of one kind open per connection and refuses a `*_BEGIN` past it.
  - **`brindle-term-core` (`term-core/`):** the GPUI-free state shared by Brindle and the core: `shell_integration` (`Parser`, `Marks`), `status` (`Records`), `osc` (the scanner), `progress` (the pure OSC 9;4 model: `parse`, `apply`, `most_pressing`), `pointer` (the pure OSC 22 model: `Shape`, `parse`, `Stacks`; the client's alone, never replayed), `kitty` (one OSC 99 chunk: `KittyId`, `Payload`, `Data`, `Meta`, `Chunk`; the client's alone), `replay` (`render(&mut Term, &Marks, &Records, Option<Progress>, &Contexts, title) -> Vec<u8>`, which writes the progress as one `9;4` report and then one `3008;start=…` per open context, outermost first and re-escaped, after the marks a replayed `A` would otherwise drop it with; with its fidelity limits listed in the file; it writes each command's reported line as `633;E` after its `B` (or its `A` when it has none, through `encode_vscode`), so lines survive an attach and a core restart while older clients see only the 133 marks) and `emulator` (`Emulator`: `Term` + `Parser` + `Marks` + `Records` + the progress + the `Contexts` (cleared only by `process_exited`, which the core calls in `session_exited`) + the kept title; its listener drops every event but title changes, so the server never answers queries — the attached client does). An `Emulator` is built with the path style of its programs' platform (`Emulator::new(cols, rows, scrollback, style)`; the core passes `platform::pty::PATH_STYLE`), so a Windows session's OSC 9;9 `C:\src` is kept and replayed as `ESC ] 7 ; file:///C:/src`. It re-exports `alacritty_terminal`. Keep the core's tracking identical to the client's, or replay drifts.
  - **`brindle-transcript` (`transcript/`; OpenSpec change `agents-sessions`):** the agent transcript's events and their fold, which Brindle and the core share. Client protocol 4 carries the events as JSON values that `brindle-remote-protocol` doesn't interpret, each side encoding and decoding them through this crate, so neither shared crate names the other's types. Pure as a crate (`fcis R4`: no IO, clock, threads or environment; `transcript_does_no_io_and_reads_no_clock`), with `serde` and `serde_json` as its closed list (`ports R3`) and the wildcard, `unwrap_used` and `expect_used` lints at its root. Brindle and the helper depend on it. `src/lib.rs` holds the types: `EntryId` (from 1, never reused, never an index), `Entry` (user, agent, thought, tool, permission with its options and outcome, notice), `Event` (`Added`, `Appended`, `ToolChanged`, `Answered`, `Queue { slot }`, `Turn`, `Agent`, `Trimmed`), the queue's `Slot` (`Empty`, `Waiting`, `Held` with its `HoldReason`), `TurnState`, `StopReason` (`Other { name }` for a reason it doesn't know), `AgentState`, and `Activity` (program status's names). `Transcript::apply` is the one fold: an event it can't apply is a `FoldError` (out of order, an unknown or trimmed entry, an append to an entry with no text, a tool change or answer on the wrong kind, a second answer, a trim past the end or behind the last) and leaves the log unchanged; `Queue` sets the whole slot and never fails. `replay()` gives the events that rebuild the log (`Trimmed`, each entry's `Added` with its text in `Appended`s of at most `TEXT_CHUNK`, 64 KiB, cut at character boundaries, a permission's `Answered`, `Queue` when the slot isn't empty, `Turn`, `Agent`), and a property test pins `fold(replay(t)) == t`. `activity()` is design decision 15's table (the slot never changes it). `trim_to(limit)` drops the oldest entries whole, always keeping the newest, and returns the `Trimmed` it applied; the log keeps each entry's exact encoded length (an append adds its text's escaped length) so the bound costs no re-encoding. The encoding: each enum with data is an object tagged by a field of its own (`event`, `type` for an entry, `turn`, `agent`, `slot`, `hold`, `reason`, `outcome`), each fieldless enum (`ToolKind`, `ToolStatus`, `NoticeLevel`, `PermissionKind`) a `snake_case` string, and unset optional fields are left out. `Event::from_value` refuses a non-object, an unknown kind or value and a missing field (`DecodeError`), and ignores unknown fields. `tests/events.rs` pins every kind and value against `tests/fixtures/v4/` (one event per file, compact JSON with sorted keys so the bytes don't depend on serde_json's `preserve_order`; written only when missing with `BRINDLE_REGEN_FIXTURES=1`, never edited), with an unknown field added to every object and an unknown string put in every enum field; `src/fuzz.rs` runs the decoder and the fold over random and mutated input. ACP itself stays out of it: the helper alone names `agent-client-protocol-schema`, and only in `remote-agent/src/acp/` (`only_the_acp_modules_name_the_schema_crate`), so ACP's types never enter Brindle's build.
  - **The core's ACP client (`remote-agent/src/acp/`; OpenSpec change `agents-sessions`):** pure modules (`PURE_MODULES`), the only code that names `agent-client-protocol-schema` (`=1.22.0`, no default features; `only_the_acp_modules_name_the_schema_crate`). The core's agent sessions (`core/agents.rs`) call them through `reduce::step` and `checkpoint::{encode, adopt}`. `wire.rs` decodes a line in two steps. `decode` reads the JSON-RPC envelope by hand into `Message::{Request, Notification, Response, Error}`, with `params`/`result` as `Value` and invalid UTF-8 replaced; a line that isn't one is a `Malformed` (blank, not JSON, a batch, not an object, no `"jsonrpc": "2.0"`, `InvalidRequest` for a request whose id is over `MAX_ID_LEN` (1 KiB) or not a number or string, which the reducer answers `-32600` with a null id, and `BadShape`). An `Id` keeps the number or string the agent sent and `encode`s it back verbatim (Antigravity's permission ids are strings, others start at `0`). Then each method the reducer reads is decoded into Brindle's types, through the schema crate's where it is lenient: `session_update` dispatches on `sessionUpdate` by hand (never the crate's `SessionUpdate` enum, which costs the static helper over a megabyte) into `Update::{UserChunk, AgentChunk, ThoughtChunk, ToolCall, ToolChanged, Ignored}`, mapping the crate's `non_exhaustive` `ToolKind`, `ToolCallStatus` and `ContentBlock` onto `brindle_transcript`'s closed `ToolKind` and `ToolStatus` and `wire::Content`; `prompt_result` reads `stopReason` itself (`StopReason::Other { name }` for one it doesn't know, since the crate's has no catch-all); `permission_request` is decoded by hand, keeping an unknown option kind as `OptionKind::Unknown { name }` (the crate rejects the whole request); `initialize_result`, `supported_versions` (a `-32022`'s `data.supported`, `None` when missing or malformed), `new_session_result` and `cancel_request` (`$/cancel_request`'s `requestId`). `request_kind` and `notification_kind` close the methods it knows (everything else is `Unoffered`, answered `-32601`, or `Other`, ignored). Its tests decode every line of `remote-agent/tests/fixtures/acp/` (the real agents' captures, Gemini's login prompt on stdout, the hand-written unknown values, and the `.jsonl` answers no agent gave: `initialize-32022`, `initialize-v2-reply`, `prompt-auth-required`), plus a fuzz run over mutated captured lines. `lines.rs`'s `Lines` splits stdout into `Piece::Line`s (without `\n` or `\r\n`; chunks may cut anywhere), keeping the line in progress as a `Partial`: `Collecting` (at most `MAX_LINE`, 8 MiB, plus a `\r`), `TooLong` (a longer line, dropped as it comes and reported as `Piece::TooLong` at its newline, never buffered) or `Resyncing` (after `cut_front`, for a truncated tail: the held partial line and the bytes up to the next newline are reported as `Piece::Lost`). `covers` counts every byte fed, the partial line's included; `restore(partial, covers)` rebuilds one from a checkpoint. `rpc.rs`'s `Rpc` holds the next outgoing id (from 1), the core's requests awaiting a response by id with their `Purpose` (`Initialize`, `NewSession`, `Prompt`; `answered` takes one, `forget` drops a purpose's), and the agent's waiting permission requests by `EntryId` with their wire `Id` (`hold_permission` refuses the 17th with `Full`, `MAX_PENDING_PERMISSIONS`; `answer_permission`, `cancel_permissions` after a cancel, `withdraw` for `$/cancel_request`); `from_parts` rebuilds one from a checkpoint. It writes its own lines rather than the schema crate's (which encodes `clientCapabilities` with explicit `false`s, against decision 4's `{}`): `initialize`, `new_session` and `prompt` (which also record the request), and `cancel`, `permission_answer` and `error` (`Refusal::{MethodNotFound, InvalidRequest}`, `-32601`/`-32600`), each one line ending in `\n`, strings escaped by `serde_json`, ids echoed verbatim; the tests pin them against the captures' client lines. `reduce.rs` is the reducer: `step(&mut AgentSession, Input, now) -> Output`. An `AgentSession` holds the `Transcript`, `Rpc`, `Lines`, a `Phase` (`Spawning`, `Initializing`, `Creating` with the agent's name and version, `Ready { session }`, `LoginRequired`, `Refused` for a failed start, `Broken` for a handling fault, `Exited`), the directory and Brindle's version for the start requests, the chunk `Run`, the tool entries by call id and a pending `BadRun`. `Input` is `Spawned`, `Stdout(bytes)` (fed through the session's own `Lines`), `OutputLost` (a truncated tail: `cut_front`, a notice, a forgotten prompt's turn `Failed` and a waiting prompt `Held { OutputLost }`), `Exited { code, stderr }`, `Command` (`Prompt`, `Unqueue`, `Resend`, `Cancel`, `Answer { entry, option }`), `Fault { reason }` (the core's `catch_unwind`) and `Tick`. `Output` is the events (already applied to the session's log), the stdin bytes, the command's reply (`Result<(), Refused>`, whose `Display` is the refusal text), a checkpoint `Moment` (`BeforeRequest` wins, so a prompt's entry and id reach the holder before its bytes), `hang_up` (a failed start) and `wake` (when to `Tick`, so a run of bad lines becomes one notice with its count once a second passes without another, unless a message or another input comes first). It applies decision 10's slot table (a waiting prompt is sent only after `end_turn`; a `cancelled` stop with no cancel from the user holds it as `Stopped { Cancelled }`, not `Cancelled`), answers unoffered requests `-32601` and unreadable ones `-32600`, ignores unknown notifications and update kinds, leaves out a permission option of a kind outside the four with a notice (answering `cancelled` when none is left), cleans control characters to U+FFFD (keeping `\n`, `\t` and the `\r` of `\r\n`), bounds text fields at 64 KiB, and trims the log past `LOG_LIMIT` (16 MiB), answering `cancelled` a waiting permission request whose entry it drops. A `FoldError` from its own events becomes the `Broken` phase. Its tests fold a client copy of every event and check it equals the session's log after each step, and replay the captures through it (ids renumbered, answers chosen by kind and checked byte for byte against the captured ones). `checkpoint.rs` encodes an `AgentSession` for its holder (`encode`, refusing past `MAX_CHECKPOINT_LEN` with `TooLarge`): the magic `BACP`, format `1` (big-endian `u16`) and the JSON state's length (`u32`), then the state (the log as `Transcript::replay`'s events, `acp: 1`, the directory and version, the `Phase`, `Rpc`'s parts with the permission ids as sent, the chunk run, the tool entries, the count of a bad-line run not yet written, and `Lines`' partial kind and `covers`), then the partial line's raw bytes. `decode` checks every reference (the run, the tools and the waiting permissions name entries the log holds, of their kind) and never panics; `adopt(checkpoint, truncated, cwd, version, now)` is the core's one call on adoption: a checkpoint that reads comes back as it was (`OutputLost` stepped after a truncated tail, so a pending prompt's turn fails and a waiting prompt is held, a held one kept); an empty one (the core checkpoints before its first write, so the agent got nothing) is a new session, started with `Spawned`; any other is `not_restored`, a log of one notice ("the conversation could not be restored: …"), the agent `Failed`, phase `Broken`. A restored bad-line run's notice waits a quiet second from the adoption (`Output::wake`). Its tests round-trip every phase, a session mid-turn with a waiting permission and prompt and half a line, a trimmed log, a held prompt (then resent with the next id), a 16 MiB log with an 8 MiB partial line and a 256 KiB prompt (well within 64 MiB), each way a checkpoint fails to read, and a fuzz run over random and mutated checkpoints. The fake ACP agent the tests play agents with is the package's second binary, `brindle-fake-acp-agent` (`src/fake_acp/main.rs`): every `cargo build` puts it in `target/<profile>/` beside `brindle-remote` and the tests find it through `CARGO_BIN_EXE_brindle-fake-acp-agent`, while nothing packages it (the packaging scripts name their files, and `build-linux.yml`'s "Release archive contents" and `build-windows.yml`'s "Release zip contents" fail on any file outside each archive's list); its script parser `fake_acp/script.rs` is pure (`PURE_MODULES`; its tests run with `cargo test -p brindle-remote-agent --bin brindle-fake-acp-agent`): `parse` turns a script into `Step`s (`record <path>`, `expect <method>`, `expect-response <id>` (the response to the agent's own request with that JSON id), `send <json>` kept as written, `send-raw <text>`, `respond <json>`, `respond-error <code> <message> [<data>]` with a one-word or JSON-string message, `stderr <text>`, `wait-file <path>`, `exit <code>`; `#` comments and blank lines skipped) or a `BadScript` naming the line and its `Problem` (an unknown step, a missing argument, JSON that doesn't parse, a bad code, a response before any `expect`), and `Received::{parse, answers}`, `result_line` and `error_line` are what the player reads and writes. The binary (`brindle-fake-acp-agent SCRIPT`) checks the script whole, then plays it: `expect` reads stdin lines until one with that method, `expect-response` until the response with that id (each appending what it matched to the `record` file), responses answer the last request an `expect` matched (a notification matched since doesn't change which), a `wait-file` looks for its file every 10 ms with no limit, and a script that runs out without `exit` idles until stdin closes, then exits 0; it exits 2 for a usage error or a bad script and 3 for a step it can't play (stdin closed before the method or response came, a response when every `expect` so far matched a notification, an IO error). The real-process tests of agent sessions are `remote-agent/tests/agents.rs` (one per scenario of the `agent-sessions` spec, the core restarts included), the agent cases of `upgrade.rs` (a held prompt and a pending permission across an upgrade, an H1 2 core not shown the session), `manage.rs` (`list`, `kill`, `stop`) and `relay.rs` (frames 15–20 and 42 through a relay), with the holder's pipe sessions in `holder.rs`; the test client keeps each session's events in order (`TestClient::events`) and checks that each encodes back to the JSON it came as, and `support/fake_agent.rs` builds scripts (`started`, `said`, `ask`, `stop`, `update`, gates, and `reached` marks a test waits for). On Windows `build.rs` links the helper's version resource into `brindle-remote` only (`embed_resource::compile_for`).
  - **Checkpoints and replay:** the replay stream (`ESC c`, scrollback and screen with SGR, OSC 133 marks, the alternate screen, modes, cursor, title, OSC 7501 reports, OSC 9;4 progress, OSC 3008 contexts) serves attach/reconnect (`REPLAY_START`…`REPLAY_END`) and is sent to the holder as a checkpoint after 512 KiB of output (`CHECKPOINT_AFTER`, checked after each read of the holder's output, and only past 4 MiB while more of it is waiting, because rendering costs about as much as feeding), before a step-down and on detach. `CHECKPOINT_END` carries `covers`, the tail bytes the core had fed when it rendered; the holder drops only that many from the front, since output may still be in flight. A new core feeds a fresh `Emulator` the checkpoint then the tail, and replays requested meanwhile wait for it. An agent session's checkpoint is `acp::checkpoint`'s encoding of its whole `AgentSession` (the log with its slot, `Rpc`'s ids, the partial line), taken whenever the reducer returns a `Moment` (the start, right before every request it writes, so a prompt's entry and id reach the holder ahead of its bytes on the same connection, a turn's end, a slot change, a permission request and its answer, a stop), past 512 KiB of stdout, before a step-down and on detach (`policy::agent_checkpoint_due`); its `covers` is `Lines::covers()` since the last one. On adoption the checkpoint and the tail go through `checkpoint::adopt` and the reducer, so a turn in flight, waiting permissions and the slot carry over; a tail cut short fails a pending turn and holds a waiting prompt (`OutputLost`), and a checkpoint that doesn't read leaves a conversation that could not be restored, its agent running.
  - **Upgrade, drain, supervision:** after `WELCOME`, `remote::local::upgrade::offer` decides whether Brindle's helper is newer (higher semver, or equal version with a different build id and a later mtime than `/proc/<core pid>/exe`; on Windows the check reads the core's image with `win::image_path_of` (`QueryFullProcessImageNameW`) instead, once Brindle's client lands in group 7, and since `CopyFileW` keeps the last-write time a per-build copy still compares build times); if so it runs `<helper> check --holder-protocols …` and, on success, sends `STEP_DOWN`. The core checkpoints every session, sends `GOODBYE { handover }` to each holder and exits; the upgrading client starts the next `serve`, which adopts the holders and `DRAIN`s any of another build (they take no new sessions and exit when empty). A holder never gets replaced while it has sessions. Other clients reconnect, waiting `START_AFTER` (5 s) before starting a core themselves.
  - **Management (`cli.rs`, `check.rs`):** `brindle-remote list | kill | status | stop | check` are clients that never start a core (`status --json` prints `{"running":false}` with no server). They offer the whole client range, so a protocol 4 core lists them agent sessions: `list_line` (pure, unit-tested) puts `agent: <activity>` in the title column, and `--json` prints `SessionInfo` as the core sent it, its `agent` object included; `kill` and `stop` need nothing of their own for agent sessions.
  - **Relay (`relay`, `relay.rs`; Linux only (`target_os = "linux"`); other platforms, macOS included, refuse it):** a client of its host's core that pipes the client protocol to its stdio for a Brindle on another machine (over `ssh` or `docker exec`). It writes the frame marker, resolves and creates the server directory, connects or starts the core from `/proc/<own pid>/exe` (stdout to `/dev/null`, since its own carries frames; ready pipe through `start_role_as`/`ReadyPipe::wait`), then sends `RELAY_HOST` (version, build, its environment, shell from `SHELL` else passwd, home, server dir, core pid) or `RELAY_ERROR` (the problem and `core.log`'s path) and exits. The client's core connection is open once `HOST` is sent, so its `HELLO` must follow within the core's 5 s. Then whole frames are copied both ways by header; the client's relay frames are dropped, so no core sees a `RELAY_HEARTBEAT`. Scope: a scope only when `/var/lib/systemd/linger/<passwd name>` exists and `scope::current_outcome()` finds a user manager (`decide_scope`); otherwise plain, with `BRINDLE_NO_SCOPE=1` in the core's environment (its holders too) and one `core.log` line saying why. That line warns that the sessions "may not outlive the login" only when a user manager is reachable (`scope::Outcome::user_manager`: the user doesn't linger, or `systemd-run` is missing); with no user manager (a container) or `BRINDLE_NO_SCOPE=1` it is the plain "without a scope" line. Liveness (`liveness.rs`): the stdin reader thread stamps every frame, heartbeats included, and is busy while writing one to the core; the main thread ends the relay after 60 s without a stamp; a heartbeat thread sends `RELAY_HEARTBEAT` after 10 s without a write, under the writer mutex the core→stdout copier holds per frame, so a client that stops reading blocks only those two. `BRINDLE_TEST_RELAY_IDLE_MS`/`…_HEARTBEAT_MS` shorten both for tests. It ends when either side closes. Upgrade: on its own connection (token `relay-<pid>-upgrade`) it reads `WELCOME`, compares `upgrade::is_newer` (its own exe's mtime against `/proc/<core pid>/exe`'s), checks the holders' H1 versions in-process (`check::refusal`), sends `STEP_DOWN`, waits for the old core to exit (a `serve` that loses the lock counts the exiting one as the winner), starts `serve` and connects again (up to 15 s, taking the holders' own core if its won't start); a refusal relays to the running core. Tests: `tests/relay.rs` and the relay cases in `tests/upgrade.rs` (Linux) run it on a socket pair (`tests/support/relay.rs`).
- **Brindle's client (`src/remote/local.rs`, `local/{connection,session,upgrade}.rs`):** `shared()` keeps one `Connection` per endpoint (`Host`) with a reader thread (demultiplexes by session, parses into each `SessionSink`; during a replay it drops bells, notifications and status notices) and a writer thread (queues messages, holds them while disconnected). `Session::start` (`SPAWN`) and `Session::attach` (`ATTACH`, answered by a `REPLAY_START` carrying its `req`) return at once and do the connecting, start, upgrade and request on their own thread, so the UI thread never blocks; each request waits in `State.requests` for its answer. Input waits under the session's input budget (`remote/budget.rs`, `InputBudget`, owned by the `Session` across its phases and handed to its `Running`): held while the session starts and while the link is down or slow, counted until the writer has written or skipped its `DATA` (`Outgoing`'s backlog), a call taken whole while less than 4 MiB waits and refused past it until less than 1 MiB waits; `Session::input` returns a `Delivery`, and `Terminal::write` sends `ChannelEvent::InputRefused` on a crossing's first refusal, which writes one dim "input not sent" line in the tab. Control messages (resize, close, detach, layout) are never refused. Every call into a sink goes through `Connection::deliver` under `catch_unwind` (`process R3`): when Brindle's emulator panics on a session's output, that session stops being shown and is sent `DETACH` (it keeps running), its sink is told `broken` (the terminal replaces its `Term`, parser and marks, and the tab says in red that it can't show the session any more and to attach it again from Attach Session…), and the reader carries on for the endpoint's other sessions. Debug builds take `BRINDLE_TEST_SINK_PANIC=<marker>`, read once: the sink panics on output holding the marker (the e2e suite's fault switch). `brindle --list-fault-switches` lists it and `BRINDLE_TEST_LAUNCH_LISTING`, and a release build lists none. `State.sessions` holds each shown session's `Shown` entry by id: its sink, its key (`SessionKey`, decoded once from the wire's string; `None` from a core that predates keys), its window (for `REPARENT`) and its last `PROCESS`, which all go with it. A `Running` (a started session's handle) acts only while its connection shows that session by id and key (`State::shows`, `State::forget`), so a lost or exited tab's input, resizes, window, layout, detach and close never reach a session that later got its id. Closing a zone or tab ends its program, and quitting keeps it: `Closing::Keeps` (profile tabs) spawns with the `detach` policy, so a crash keeps them too, and `Closing::Ends` (`-e`) with `kill`. `Terminal::close` (an explicit close) sends `CLOSE`; quitting has every terminal leave explicitly (`Workspace::quit` → `ZoneTreeView::quit_all` → `Terminal::quit_with`, from the app's quit handler and from the window's close: the `CloseWindow` action or a close the platform asks for), a `Keeps` one with `DETACH` and an `Ends` one with `CLOSE`, recording the window first, since a zone that left no longer knows its session. Each tab's `DETACH`es carry its layout (`layout::record`: the split tree by session key, the active zone, the manual title, the tab's index and the process's id (`layout::origin_id`, made once in `main.rs` and passed to `Workspace::new`); zones without a running session are left out, and a session still starting detaches without one). While Brindle runs, `main.rs`'s once-a-second `record_session` tick also calls `Workspace::send_layouts` → `ZoneTreeView::send_layout` → `Terminal::set_layout` → `Running::set_layout`, which sends `SET_LAYOUT` only when the link negotiated protocol 3 (`State.protocol`, from each `WELCOME` in `Connection::up`) and the layout differs from the one it last sent, so a killed Brindle leaves its splits (e2e `local-server-layout-live`). A drop does the same, and a session leaves only once, but drops can't be relied on (see the Windows pitfalls). Nothing asks first, and quit waits at most `QUIT_FLUSH` (500 ms) for the connections to write the tabs' `DETACH`es and `CLOSE`s (`local::flush`, after GPUI's shutdown; a connection that is down isn't waited for): they are only queued for the writer threads, which the exit ends (on Windows at once), and a lost `DETACH` leaves the session its owner, so the next launch doesn't open it as a tab. On a lost connection the reader reconnects with the same `client_token` (a core is started after `START_AFTER`), a `LIST` after `WELCOME` finds the sessions the core no longer has with their keys (`State::keep_listed` over `ListedSession`s: a fresh core restarts ids at 1, so a session whose id it lists under another key is one it no longer has, and an attach cut off by the drop is sent again only to a session listed with its key), and those, or all after `RECONNECT_LIMIT` (15 s), get the red "session lost" line (`EXIT` with `lost`) while the tab stays open. A relay link's reason for ending (the log line, `LinkState::Offline` and the failed requests share it) names its cause (`relay_link_ended`): `nothing read from <name> for <limit>` when the watchdog ended it (it marks the link's `Stamp` expired first, so a killed process's status isn't mistaken for the cause), else the relay process's own account (`Wire::why`: `ssh exited with 255: <cause>`, the cause the last line it wrote to stderr), else `the relay closed the connection`; only the local core's socket or pipe says `the terminal server closed the connection`. A failed launch's first line names its cause the same way (`client::split_cause`: the last non-empty stderr line, the other lines below it). `SPAWN` carries the complete environment (Brindle's with `child_env(profile)`; non-UTF-8 variables are dropped; on Windows names are merged case-insensitively with the profile's entry winning, `cmdline::merge_environment`). A relay connection stays in use (`State::in_use`) while a request, a session, a listing hook or an unwritten `CLOSE` needs it, but a `CLOSE` only for `Timings::close_limit` (5 min) after the oldest was queued: with no link up by then, the closes are given up, never written, and their programs left running (logged as `not ending session <ids> on <endpoint>: …`, which is also the end's reason if nothing else uses it). A core that refuses this Brindle (`Refused`) ends a connection that isn't eager; an eager one reports the endpoint offline with the refusal, fails new tabs' requests with it and retries at most `Timings::eager_cap` apart.
  - **Reattach (`src/reattach.rs`):** the instance's launch (unless `--no-restore`) lists the core's sessions once, and reads the state file, on a `launch-list` thread started in `main` before GPUI (`start_launch_reads` → `read_launch`; `running_sessions`, which never starts a core), so neither wait is on the UI thread. A foreground task awaits that and opens the window once the listing has answered or failed, applying the pure `startup_launch`'s result (the `Detached` global, the restored window without lost zones, the asked tab). The window still opens only after the listing, which now overlaps GPUI's startup; `BRINDLE_TEST_LAUNCH_LISTING` (debug builds: `fail`, or a delay in milliseconds) makes it fail or slow for the e2e cases (`local-server-reattach-slow-listing`, `local-server-reattach-failed-listing`). A failed listing (`reattach::Listing::Failed`) keeps every recorded zone and sweeps nothing, and `--attach` then says the server couldn't be listed (`Listing::attach_target`). Each listing connection says `HELLO` with a token of its own (`list_token`), so the launch's and a forwarded `--attach`'s never close each other. The state file's windows are merged into one (`session::merge_windows`), and zones whose recorded `{ id, key }` isn't detached any more are dropped (`session::drop_lost_zones`: the sibling takes the split, an empty tab goes; skipped when listing failed). Restored zones take theirs by id and key, the rest open as tabs grouped by the layouts they were detached with (`layout::group`: sessions naming one tab rebuild it, pruned to those present, the first zone active when the recorded one is missing; one Brindle's tabs keep their order where its oldest session sorts; the others one per tab, in start order; `session.toml` zones take theirs first), each with the profile `reattach::session_profile` gives it (this machine's: the one it started with, else the default; a remote endpoint's: the one it started with when that targets the endpoint, else the first profile that does, else the first tab's profile on the endpoint, else the default; it runs on the endpoint whatever its profile targets; a remote endpoint's first-listing sweep is `reattach::swept_tabs`, grouped the same way and opened by `Workspace::insert_layout_tab`, and the sessions palette uses the same rule), then the launch's own request (`brindle terminal`'s tab or `--attach`'s session, `Args::opening`) opens as the active tab (`Workspace::open`); `--attach ID`'s session is kept out of `Detached`. An attached terminal starts at the session's listed size (`ListedSession::of` reads a size outside the grid limits as none, as an old core's 0x0, and the tab then starts at the default grid: `GridSize::listed`), and its `SessionSink` holds the first replay until `REPLAY_END`, then feeds it at that size under the term lock: a replay fed at another size misplaces the cursor. A restored remote zone (`Attaching::Recorded`) starts at the default 80x24 and learns its size from the endpoint's listing (`SessionSink::replay_size`). What the term does after the replay is the pure `server::replay_fit`: a terminal a layout has sized (`Backend::Server`'s `laid_out`, which `Terminal::resize` sets under the term lock and the sink reads under it) resizes back to its own grid, and the queued `RESIZE` takes the session there; one nothing has laid out (a background tab: an inactive tab is never laid out) keeps the session's size, so what the program draws before the tab is shown lands as drawn, not clamped to 80 columns, which the program would never redraw, since showing the tab then resizes its PTY to the size it already had. `Terminal::resize` resizes when the layout's grid is new or the term's grid differs from it (`resize_due`), since a kept replay size leaves the term at a size the terminal didn't choose. The "Attach Session…" palette (`PaletteKind::Sessions`) lists this machine and every remote endpoint in the `Hosts` global (`remote/hosts.rs`) concurrently, each answer applied as it arrives and the palette opened once all have answered or after `OPEN_GRACE` (250 ms), a remote one listed only on the connection the process has (`local::existing`, never dialling) and within `LIST_LIMIT` (2 s); `picker::session_palette` groups the rows (local first, then remote endpoints in profile order, headed by name only when a remote one lists sessions) and gives each pending, connecting or offline endpoint a disabled row; enter attaches and `picker_kill` sends `KILL` on the row's endpoint (rows are keyed by endpoint and id, since ids restart per core). `Hosts` is fed by the connections' own reports (`Report`, `local::watch_hosts`, set before the window opens), never by polling. Profiles with `connect_at_launch` make their endpoints eager on every launch, `--no-restore` included (`local::keep_connected`, re-run on a config reload); only the sweep of a host's detached sessions into tabs (`sweep_launch_hosts`, through `local::when_listed`) waits on a restoring launch. When the window's last tab on an endpoint that isn't eager goes (`Workspace::remove_tab`, `reattach::endpoints_without_tabs`), `local::stop_listing` withdraws that listing hook, so the endpoint's connection ends once unused instead of dialling on for the sweep.
  - **Tests:** `remote-agent/tests/{holder,core,upgrade,manage}.rs` run a real holder and core in a temp `BRINDLE_SERVER_DIR` with test clients, on Linux and Windows with each platform's own programs (Linux-only where they need a Unix shell, exact PTY bytes, signals or `/proc`, with Windows counterparts beside them) (roles and start race, spawn and I/O, policies, reconnect, replay fidelity, checkpoints and truncation, upgrade/drain/refused check, management commands), and `launch.rs` (Windows) the detached start. `core.rs`'s scopes test (`holders_and_restarted_cores_run_in_scopes_of_their_own`) runs only with `BRINDLE_SCOPE_TEST=1`, which CI's `test` job sets, since it starts scopes in the user's own systemd manager; without it, it skips. Their waits go through `remote-agent/tests/support/wait.rs` (`eventually`, `until`, `Quiet`), and the unit tests' through each crate's `test_support` (`src/test_support/`, `remote-agent/src/test_support.rs`, `remote-protocol/src/test_support.rs`), whose limits `BRINDLE_TEST_SLOW` (a positive factor, default 1) scales; a passing run never reaches a limit, so only failing runs take longer. A test that can't run for want of a capability calls `skip(Capability, reason)`, which appends `<test>\t<capability>\t<reason>` to `target/tmp/skipped.log` and stderr and returns, unless `BRINDLE_TEST_REQUIRE` (comma-separated: `scopes`, `packaged-conpty`, `fault-switches`, `elevated`) names the capability, which fails the test instead; CI's `test` and Windows jobs empty the log before `cargo test` and print it after, and set `BRINDLE_TEST_REQUIRE=fault-switches`; `brindle-remote --list-fault-switches` says which switches the helper has. `remote-protocol/src/fuzz.rs` fuzzes the decoders, and `term-core/src/fuzz.rs` (with the parser tests in `shell_integration.rs`) the OSC scanner, the status parser and the emulator. The e2e `local-server-*` cases (`tests/e2e/cases/local_server.rs`) run Brindle against a private server directory and `brindle-remote stop` afterwards. `scripts/with-xvfb` runs them without a desktop.
- **`terminal_view.rs` / `terminal_element.rs`**
  - Key handling: GPUI resolves keybindings *before* `on_key_down`. `key_down` encodes special keys and modifier combos and calls `stop_propagation`. Plain text (no modifiers or shift only) instead arrives through the `EntityInputHandler` path, which is what makes IME work. That's why app shortcuts are ctrl-shift-*.
  - Painting: the element batches each row into same-style runs, shapes each batch once, and places it at its exact column. Non-ASCII glyphs and the cursor cell get their own batch. Box drawing (U+2500–U+259F) is painted as rectangles, not glyphs.
  - Pointer: `prepaint` reads the program's shape for the screen it draws (`Terminal::pointer().top(…)`, from the mode it reads under the term lock) and stores `pointer::choose(link hovered, TerminalView::is_selecting, program shape, mouse mode)` in the frame: the hand over a ctrl-hovered link, the text beam during a selection drag, then the program's OSC 22 shape, then the arrow while the program reports the mouse, else the text beam. `paint` sets it with `set_cursor_style(…, &frame.hitbox)`, so it applies over the grid only. A press or release that starts or ends a selection drag draws a frame (`TerminalView::set_selecting` notifies), and `paint` records each frame's pointer in the view (`pointer_painted`, the pure `pointer::Shown`): one that changed while the mouse is over the grid goes to `cursor::show_now` (the seam), because GPUI on Windows only shows a new pointer at the window's next `WM_SETCURSOR` (a mouse move, and never while a press holds the mouse captured), so the seam posts one; on Wayland and X11 the frame's end shows it and the seam does nothing. The dump's `--- grid-pointer NAME` (CSS name) is the last painted frame's pointer, and `--press`/`--release` hold and release the left button for a drag.
  - Mouse: listeners are registered in `paint` with hitbox checks, and move/up are tracked globally while dragging. A right press that isn't reported (`mouse::reports`; shift always bypasses) pastes the clipboard when `right_click = "paste"`, over a selection too, and the paste clears the selection; with no text on the clipboard nothing is pasted and the selection stays. `mouse::right_press(reports, setting)` is the pure choice: `Report`, `Paste` or `Nothing`. The feedback it sets is described under `terminal/` above. `copy_on_select` and `right_click` are read from `Settings` at the event, so a reload reaches open tabs. `--right-click` is the right button's `--click`.
- **Grid geometry** — `cell_metrics()` and `fit_grid()` are the single source of cell size; anything that positions cells must use them. No grid is narrower than `MIN_COLS` (10 columns, `brindle_term_core::emulator::MIN_COLS`): `fit_grid`, `Terminal::resize` and the server emulators clamp to it, because `alacritty_terminal` panics on a double-width character in a 1-column grid. Nor is one larger than `MAX_COLS` × `MAX_ROWS` (2048 × 1024), since a grid allocates every cell and its size comes from outside: `emulator::clamped` is the one clamp, which `GridSize::clamped` (`Terminal::resize`, an attach, the replay resize), every `Emulator` and the server core (a `SPAWN`'s, a `RESIZE`'s and an adopted session's size, for the emulator, the PTY and the listing alike) go through.
- **`workspace.rs`** — each tab is a local zone tree (`Tab::zones`, an `Entity<ZoneTreeView>`).
  - **Models (`workspace/`, pure):** `tabs.rs`'s `Tabs` keeps the active tab by its `TabId` (`Tab::id`) over the one order in `Workspace::tabs`: where a new tab goes (`insert_at`), which tab is active after a removal (`removed`), a switch (`pick`, with `ActivateTab`'s `TabTarget { Nth, Last }`) or a move (`shift`, then `reorder`); the strip's events name tabs by place and are turned into ids at once. `launch.rs`'s `new_tab_cwd` says where a new tab starts (`NewTabCwd`), `overlays.rs`'s `toggle` what asking for an overlay does while another shows (`OverlayKind`, `Opens`), and `previews.rs`'s `Previews` which theme and profile a tab shows while the settings dialog previews them. The shell keeps one `overlay: Overlay` (closed, a sessions palette still opening, a palette with its `PaletteKind`, the settings dialog, the profile menu, or a context menu with what it is for, `MenuFor`). The profile picker and menu resolve the chosen row by `ProfileKey` (`Config::profile_key`, `find_profile`), else by its place, and `Settings::zoomed` steps the zoom.
  - **`zone_view.rs`** — `ZoneTreeView` owns a local tab's binary split tree (`ZoneTree`) of `Zone`s (`ZoneContent::Terminal(Entity<TerminalView>)`), normalized `[0, 1] x [0, 1]` geometry (`UnitRect`) for `FocusZone*` and `--dump-screen-after`. Every zone is a `brindle_ui::Card` in its terminal's colours (`Theme::card_colors`), on the tab theme's background, which the root paints and which shows in the `ZONE_GAP` (6px) round and between the cards: 1-zone tabs render a headerless card, and 2+ zones render a header per card (status dot, title, split/close buttons, and its terminal's progress bar along its bottom edge, and its context badge after the title) with the gaps in place of dividers. The header sits on the terminal's background, its title in `foreground` on the active zone and muted on the others, its buttons muted, and status dots come from `Settings::chrome_theme`. The active zone of a 2+ zone tab gets a focus ring, drawn in the gap, only when focus came from the keyboard (`shows_ring`). The title is `trigger_label`, the buttons are ghost `IconXs` buttons with tooltips, and a right-click on a header (`open_menu`) focuses its zone and emits `ZoneMenuRequest` for the workspace's context menu.
  - The tab strip is the client-side-decorated title bar: a `brindle_ui::TabList`, shadcn's pill (`render_tab_bar`; `tab_bar_height()` is the list's 36px, `TAB_LIST_HEIGHT` through `rems_at_default`, plus the `ZONE_GAP` above it), drawn in the chrome tokens (`cx.ui_theme()`) whatever the tabs' themes, except each tab's face, active or not, which takes its terminal's background and foreground, its icons and close button too (`TabTrigger::surface`, `text_color`); no line marks the active face, which is raised with a shadow. Beside it are the new-tab button and the `⌄` profile menu (the third overlay; the tab and zone header context menu is the fourth, see `picker.rs`), and nothing that acts on the active tab: split and find are on their keys, the tab menu and the palette. The strip's buttons (`strip_button`) and the caption buttons are `IconSm` with 16px icons stroked at least `LEGIBLE_ICON_STROKE` (2px) wide, as is a tab's close X. The strip is one keyboard stop (`strip_focus`), reached only through `FocusTabStrip`: arrows, home and end switch tabs, enter or escape return focus to the terminal, and a press on a tab leaves focus in its terminal.
  - Tab titles are cached and refreshed on `TitleChanged` plus a 1 s title tick (`_title_refresh`, in `Workspace::new`). Where a tab's foreground process is found in a look at all processes (Windows' local sessions), the tick does that look off the UI thread: it gathers each local terminal's root pid on the UI thread, runs `process::detect` on the background executor (one Toolhelp snapshot, with the token reads `ElevationCache` doesn't hold, pruned to the snapshot's pids), then applies each root's name and elevation with `Terminal::set_detected` on the UI thread, and notifies only when a title changed. `record_session` runs after it, as before. `--dump-screen-after` prints the tab badge lines, then the zone badges, then the mouse feedback line (`--- feedback kind=…`, after the badges and before the zone lines).
  - Brindle has one window: nothing opens another after launch. Removing the last tab closes it, and closing it quits.
- **`instance.rs`** — one Brindle per state directory (`session::state_dir`: `BRINDLE_STATE_DIR`, else `$XDG_STATE_HOME/brindle` or `~/.local/state/brindle`, on Windows `%LOCALAPPDATA%\brindle`, the variable before the known folder). An elevated Brindle's default on Windows is `%LOCALAPPDATA%\brindle\state-elevated` (`StateEnv::elevated`, which `main` reads once through `win::elevated`), so elevated and unelevated Brindles are separate instances, each with its own `session.toml`. `main` (`launch_state_dir`) makes and holds that directory with `win::protected_dir(…, Contents::Executables)` (`win::protect_state_dir`) before it takes the lock in it; a failure there, or an elevation it can't read, takes the no-state-directory path, with the window's notice saying why. `main` takes `session.lock` before GPUI starts; the holder is the instance and listens on `$XDG_RUNTIME_DIR/brindle-instance-<FNV-1a of the state dir>.sock` (0600, `SO_PEERCRED` same uid; a named pipe `\\.\pipe\brindle-instance-<hash>-<user>` on Windows). A later launch without debug options sends one JSON line (`instance::Request`: the subcommand's `kind` (`terminal`, omitted by a bare launch), its profile, absolute `-d` and `-e`, `--attach`, its working directory, its `XDG_ACTIVATION_TOKEN`/`DESKTOP_STARTUP_ID`), checked first against the 1 MiB the instance reads (`instance::fits`; `read_request` answers a line cut off there as over the limit), retrying the connection for 5 s. The line is never versioned or negotiated (the `process R4` exception): fields are only added, and the instance decodes it into a closed `Forward` (`Request::asked`: `attach` wins, the `terminal` kind or an older launch's profile, directory or command is a terminal tab, nothing raises, any other kind is refused by name). It checks a terminal launch's profile against its own config (`forwarded_launch` → `profile_for`). The answer is `ok`, `error: TEXT` or `usage: TEXT` (`instance::Answer`); the launch exits 0, 1 with the error, or 2 with the usage error (an unknown profile), which it prints; on Windows a launch with no console whose stderr goes nowhere (a Start Menu launch) also shows it in a message box (`win::show_unprinted`). Before it sends anything, the launch checks who serves the socket, as the instance checks who connects: on Unix `SO_PEERCRED` against its own effective uid (`same_user`, pure), and a socket another user serves gets nothing, only the refusal `not_sent` words (`not sending the launch to <socket>: …`). The listener thread lists sessions for `--attach`, hands the request to the UI thread (`take_launches`) and waits for its answer; the instance opens it with `Workspace::open` and raises the window with `activation::raise` and the forwarded token. On Windows the launcher calls `AllowSetForegroundWindow` for the pipe server's pid first.
- **`settings.rs`** — a GPUI global holding the `Config`, the resolved terminal font and UI family (built once, from `all_font_names`, which it keeps for the Fonts section; GPUI lists its fallback stack's names (Cantarell, Segoe UI, …) on every machine, so `installed_families` keeps those, `GPUI_ADDED_NAMES`, only when the platform has them: DirectWrite's `FindFamilyName` on Windows, the resolved font's own family on Linux), the zoom level and the settings dialog's font preview (`set_font_preview`, a `FontPreview` read before the config by `font()`, `font_size()`, `line_height()` and `ui_font_family()`; nothing else reads `config.font` or `config.ui_font` for drawing). Live reload rebuilds it, which also ends a preview, rebinds keys, and calls `Workspace::apply_config`: `main.rs` polls the file's mtime and reads it on the background executor, and one task applies reloads in request order (`ConfigReloads`, fed by the watch, `ReloadConfig` and the settings dialog's writes through `request_config_reload`; renames queued meanwhile are merged in order by `merge_renames`). The first read is in `main`, before GPUI starts. **The config line:** `Config::load_or_default` returns `(Config, ConfigReport)`: a config error, plus the `ConfigFinding`s of a file that did load, which are values Brindle used in place of the file's (a clamped `font.size` or `font.line_height`, an unknown global or profile theme, a failed `write_default`) and the removed keys it ignores (`Config::parse` returns them in `Loaded` instead of logging). `actions::bind_keys` returns the keybindings it couldn't bind (an unknown action, keys that don't parse; `user_bindings` is the pure part), which `Settings::add_binding_findings` adds once it has run. `Settings` keeps the findings and the precomputed `config_line` (`config_line(error, findings, notices)`, pure; `notices` are window notices that aren't config: the launch's, then the transient ones), rebuilt with the settings on every reload; `Workspace::render` only reads it, and the config's part goes when the file is fixed. **Transient notices:** what the user asked for and Brindle didn't do (a link it didn't open, `LinkFailed`) is a transient notice, kept by the pure `workspace/notices.rs` (`Notices`: `push(text, now)` replaces an equal text and keeps at most 3, `expire(now)` drops those past `NOTICE_LIFETIME` (10 s) and returns the next deadline, `dismiss_all`, `texts`). `Workspace` pushes each, hands the texts to `Settings::set_transient_notices` (again after a reload, which makes settings without them) and keeps one timer task for the next deadline. While one shows, the config line has a ghost `IconXs` dismiss button (tooltip "Dismiss") and the workspace handles `dismiss_notices` (in the palette only then); both drop the transient notices only. The dump's `--- config` line carries them. `set_ui_theme` makes a theme (the global one, or the settings dialog's preview) the active `brindle_ui::UiTheme` tokens and records it as `Settings::chrome_theme`, whose ANSI colours the strip and zone headers use for status dots (`Theme::status_color`); `apply_ui_font` sets `brindle_ui::UiFont` (`[ui_font]`'s first installed family, else `BUILTIN_UI_FAMILIES`'s, else `.SystemUIFont`), which the workspace root and brindle-ui's own roots (tooltips, the dragged tab) apply.
  - **Settings dialog models (`settings_dialog.rs`, `settings_dialog/{themes,profiles,fonts,clipboard}.rs`):** `Model` (`{ section, themes, profiles, fonts, clipboard, error }`, plus the config path messages name) holds one GPUI-free model per section, `ThemesState`, `ProfilesState`, `FontsState` and `ClipboardState`, each with its own mode (`ListMode`, or Fonts' form). None of them touches the file: they are given its text (`config_edit::FileText`, read by the view with `read_text`; a missing file is `None`), and an operation returns a `Step` (`Nothing`, `Write(ConfigEdit)`, `Close`). The view writes the `ConfigEdit` with `config_edit::save` and `ConfigEdit::apply` (which calls the `config_edit` functions and returns `Applied`), rereads the file and reports it with `Model::written`, which returns the `Outcome` for the workspace. Lists keep their selection by identity (theme name, `ProfileKey`; the profile editor's `Target { New, Saved }`), and a `ProfileRef` is built only for the write that checks it. The view's decisions are the models' too: `Model::enabled`, `active_row`, `list_key`, the pure `focus_target`, `ProfilesState::rows`, the profile editor's `title`, `default_note` and `theme_labels`, and `FontsState::choice_for`.
  - **Fonts section (`settings_dialog/fonts.rs`):** `FontsState` is the GPUI-free model (the four fields read from the file's text past errors elsewhere, validation, `preview()`, `apply()` returning `ConfigEdit::SetFonts` with the changed fields, written through `config_edit::set_font_family`/`set_font_number`); the view's family fields are `brindle_ui::Combobox`es over `family_names`, the terminal font's regrouped (`family_groups`) once the `MonospaceProbe` global, run once per process on the background executor, has measured `i` against `M` in every family. Choices are kept by family name, never by index: a family list's items are keyed by `family_key` and found again with `FontsState::choice_for`.
  - **Clipboard section (`settings_dialog/clipboard.rs`):** `ClipboardState` is the GPUI-free model (the two values read from the file's text past errors elsewhere, `toggle`, `apply()` returning `ConfigEdit::SetClipboard` with only the changed keys); the view's two `brindle_ui::Switch`es are its stops.
- **`theme.rs`** — terminal colour themes. `Theme::ui_tokens` maps one to `brindle-ui` tokens (legible pairs, checked for every built-in theme by `ui_tokens_are_legible_for_every_builtin`). The tokens are the only source of chrome colours (strip, find bar, window border, overlays); `chrome_background`, `card_border` and `muted_foreground` are private inputs to `ui_tokens`. Zone cards take the terminal theme's colours instead, through `card_colors` (`card_border`, and the muted text `card_muted_foreground`). `accent()` stays public: a config field, also used by `config_edit`.
- **`find_bar.rs`** — the scrollback find bar, one per `TerminalView`, at its top right and inside its focus subtree. It is drawn in the chrome tokens on `brindle-ui`: an `Input` over a `TextInput`, the count, case and regex `Toggle`s, a `Separator` and ghost `IconXs` buttons, each with a `Tooltip` naming its key. Its controls take no focus, so the query keeps it. The matches in view are found (`search::visible_matches`) when the query, the options, the output or the view changes (`research`, `step_match`, `recount`, `find_terminal_changed` on every terminal notify) and cached with the view they were found in (`FindBar::visible`, a `search::VisibleMatches` keyed by `ViewKey`); `prepaint` only reads that cache, and when `search::cached` says it is for another view (a resize, or output that moved a scrolled-back view first) it draws no matches that frame and has the view refresh and redraw (`find_view_moved`, deferred).
- **`notify/`** — desktop notifications.
  - `osc.rs` scans output for the OSCs Brindle acts on beside alacritty, which drops OSCs it doesn't know: 9/777 notifications, kitty's `99` notification chunks (`Found::Kitty`, `kitty::parse`; up to 1024 bytes of metadata beside a 4096-byte payload; the server ignores them), 7501 program status, ConEmu's `9;4` progress (`Found::Progress`, tried before a `9` is read as a message), UAPI.15's `3008` context starts and ends (`Found::Context`, `context::parse`; `ESC c` and `A` don't end contexts), `22` pointer shapes (`Found::Pointer`, `pointer::parse`; the client tags each with its screen, the server ignores it), 133 `A` prompt starts and `ESC c` (for the status and progress lifetimes). It keeps state across reads and returns `Found` values. ConEmu's other `9;1`–`9;12` commands are not messages, and `9;4` never notifies. The number must be written as is (`0009` isn't 9).
  - Every session, local or remote, is scanned on its server connection's reader thread (`SessionSink`). What it finds travels on the terminal's event channel (`ChannelEvent::Osc`). The scanner itself is `brindle-term-core`'s `osc`, which `notify/osc.rs` re-exports.
  - `Workspace::on_attention` handles bells and notifications from local tabs (bell dot, focus rule, settings; `policy::wanted` also takes an OSC 99 occasion and whether the tab is its window's active one).
  - `Notifier` (a GPUI global) rate-limits (`policy.rs`), then sends to a zbus worker on the background executor, or to the `BRINDLE_NOTIFY_LOG` file (appended by a `notify-log` writer thread, `LogWriter`, which quitting waits for through an `on_app_quit` flush, so a line sent just before `--dump-screen-after` or a closing window quits is in the file). It maps notification ids to window and tab for clicks. Sinks get `Command::Notify` (with `Hints`: urgency, expiry, silence, and button labels) and `Command::Close`, and answer `Reply::{Shown, Action, Token, Closed, Capabilities}`; the toast XML (`toast::xml`) and the reading of a toast's activation arguments (`toast::action_key`) are neutral and tested on Linux, the worker is `cfg(windows)`.
  - **kitty's OSC 99 (`kitty.rs`, pure; `brindle-term-core`'s `kitty.rs` parses one chunk):** each `Terminal` keeps a `kitty::Assembly` (at most 8 incomplete notifications, oldest dropped; 2048 bytes each of title, body and button labels; base64 decoded as a stream, an unfinished quad carried to the next chunk; metadata merged, a later chunk's value winning; no title means the body is the title). `Terminal::handle_kitty` drops chunks during a replay and with `notifications.osc99` off, answers `p=?` at once with `reply_query` (from `Notifier::caps`: the platform sink's `Caps`, `dbus::CAPS` or `toast::CAPS`, the log sink answering as its platform's, D-Bus's `buttons` updated by `Reply::Capabilities`), and emits shows, closes and alives as one event kind (`TerminalEvent::Notify99`, `Request99`), so they reach `Notifier` in stream order through `Workspace`. `Notifier` keeps a `kitty::Open<EntityId>` table: `(terminal, id)` to a sent key or a sink id, oldest first, for replacement (an update before its first is shown is sent as new and the first closed once shown, as kitty does), `p=close` (`close_program`, which writes the close report itself when `c=1`) and `p=alive` (`answer_alive`). A `Target` carries the `ProgramNotice` (a `WeakEntity<Terminal>` and the `Program`), so a click goes through `kitty::activation` (body: raise unless `-focus`, report with `report`; buttons `1`–`4`: report with `report`, never raise) and a close through `kitty::on_close`; reports to a closed terminal are skipped. The log sink writes OSC 99 lines with flags (`i=`, `replaces`, `buttons=`, `silent`, `urgency=`, `expiry=`) and `close<TAB>osc99<TAB>i=ID` for a program's close.
  - A click activates the tab and raises the window. On Wayland, `activation.rs` uses the server's `ActivationToken` on GPUI's own `wl_surface` (foreign display, own event queue), because GPUI's own activation request is refused when unfocused. A later launch's forwarded token is used the same way. The attachment to GPUI's display (the registry round trip and the `xdg_activation_v1` bind) is made once, on the background executor, as soon as the window opens (`activation::prepare`, called by the launch task after `open_window`); a raise with a token that arrives before then waits for it in a task (`Attachment::Pending`, `policy::raise_plan`), and one after a failed attachment raises plainly.
- **`desktop.rs`** — `--install-desktop` / `--uninstall-desktop` register Brindle with freedesktop launchers. They write `brindle.desktop` (its `Exec` is the running binary's absolute path) and the embedded `assets/brindle.svg` icon, and they run in `main` before GPUI starts, so no display is needed. `scripts/install.sh` delegates to them. Linux icons come only from the desktop entry and the icon theme, matched through the `brindle` app_id. The icon cache is refreshed only where one already exists.
- **`actions.rs`** — one `ACTIONS` table drives config-name lookup, `--list-actions` and the command palette (an entry's label puts it in the palette). Default bindings use the key contexts `Workspace`, `ZoneTree`, `Terminal`, `Palette`, `SettingsDialog`, `SettingsSections`, `SettingsList` and `TextInput`, plus `UiLayer`, `UiFocusScope`, `UiList` and `UiCommand` (the last five from `brindle_ui::default_bindings()`, chained in). User bindings go in the `Terminal` context, so they win over the defaults.
  - Config names can stand for `brindle_ui` actions: `picker_up/down/confirm/cancel` are `ListUp/ListDown/ListConfirm/Dismiss` (as `settings_cancel` is `Dismiss`), so old configs and `--action` steps keep working; `palette_keys_and_picker_aliases` pins each to its key's action.
- **`picker.rs`** — `Palette`, the view behind every palette (new tab from a profile, commands, sessions) and the one-line prompt (OpenSpec change `ui-command-palette`). List mode is a `brindle_ui::Command` in `Dialog` chrome (shadcn's `CommandDialog`: no padding, no visible header, no close `X`); prompt mode is an `Input` under the prompt's label, which is the dialog title, with a pointer-only close `X`.
  - `Workspace` shows it in a modal `brindle_ui::Overlay` slot (`palette`; the workspace's `overlay` records which overlay shows, a palette with its `PaletteKind`); the settings dialog has the other slot and the strip's `⌄` profile menu (a `brindle_ui::DropdownMenu`, `profile_menu`) is the third overlay, and the tab and zone header menus (one `brindle_ui::ContextMenu`, `context_menu`) the fourth; opening one closes the others first (`has_overlay`, `close_overlay`), so the focus each records is the tab's. A right press on a tab face (`TabList::on_context_menu`) opens that tab's menu without activating it (`Overlay::ContextMenu` keeps its id as `MenuFor::Tab`, and `context_menu_selected` runs Rename, Move and Close on it through `TabMenuItem`; e2e `windows-tab-menu-background`), and one on a zone header (`ZoneTreeView::open_menu`, emitting `ZoneMenuRequest`) focuses that zone, before the menu opens at the pointer; `OpenTabMenu`/`OpenZoneMenu` open the active one's below its face or header. Items are `actions::ActionMenu` rows (labels from `ACTIONS`, keys from the keymap for the tab's contexts, each item keyed by its action's name); a chosen zone item refocuses the tab and runs its action with `window.dispatch_action`, as the command palette does. The profile menu's items are the picker's rows (`profile_rows`: name, description, ctrl-alt-N from the keymap), rebuilt each time it opens (the `⌄` wrapper's capture-phase press handler, or `OpenProfileMenu`), each keyed by its `ProfileKey`, then a separator and a Settings item keyed `settings`. `profile_menu_choice` decodes the chosen key into a `ProfileMenuChoice`: a profile opens as the picker opens it, and Settings runs `open_settings`. The palette has its own tracked focus handle, and its one `FocusStops` stop is the active mode's input, so Tab stays on it; `--- focus` reports `palette`.
  - Every way of closing reaches `Workspace` as `PaletteEvent::Dismissed` (the command list's `Cancelled`, or the palette's own `Dismiss` handler in prompt mode); the palette never emits `DismissEvent`, so `palette_dismissed` always runs.
  - The command palette lists the labelled actions available from the tab that had focus, snapshotted before the palette opens. It needs both `available_actions` (for global listeners) and `is_action_available` (for `no_json` actions). Running a command closes the palette, refocuses the tab and calls `window.dispatch_action` (deferred, and following focus), so it takes the keybinding's path.
  - Prompted commands (`RenameTab`) are ordinary actions. Their handlers emit a prompt request that `Workspace` opens, so a keybinding and the palette behave the same. A prompt asked for by a command run from the palette opens a palette of its own, since the palette closed to run it.
  - Keys: a list's are its command list's (`UiList`, `UiCommand`); the `Palette` context adds only ctrl-shift-delete (`PickerKill`, the sessions palette, on `Command::highlighted()`) and enter (`ListConfirm`, which submits a prompt). A sessions palette refreshed after a kill or an answer takes the new rows through `Command::set_groups`, keeping the filter text and, by `keep`, the highlighted row.
  - **Sessions palette state (`picker::SessionsModel`):** pure, in `PaletteKind::Sessions { model }`. It holds each endpoint's `Listing` (`Pending` until it answers) with its round, the killed sessions, each endpoint's failed kill and the highlighted row's `RowKey` (a session's endpoint, id and key, an endpoint, an endpoint's failed kill, or the note). This machine's failure to list is `Listing::Unlisted` (a remote endpoint's is `Offline`, `listing sessions on <name>: …`), a disabled `this machine  could not list sessions: <why>` row. `answer` applies one endpoint's listing as it arrives, with the outcome of the kill made before it (`list_sessions` returns `Listed { sessions, kill }`), and drops one from an earlier round, except a failed kill: that brings the session's row back and adds a disabled `<name>  could not end session N: <why>` row after the endpoint's, kept until the endpoint's next answer. `view` builds the groups and the index to keep: the highlighted row if it is still listed, else the row now at its place (a kill), else the last, skipping rows that do nothing. `Workspace::refresh_sessions_palette` spawns one listing per endpoint (`palette_endpoints`: this machine, then `Hosts`; `listing_from` decides what each gives) and applies each answer through `sessions_answered`, with no `join_all`. The palette opens when every endpoint has answered or after `OPEN_GRACE` (250 ms), whichever comes first, so a slow one is a disabled `<name>  listing sessions…` row until it answers or gives up (`LIST_LIMIT`). The "No detached sessions" note is a row after every endpoint's, shown only once nothing is pending or unlisted (e2e `local-server-palette-unlisted`).
- **`brindle-ui` (`ui/`; OpenSpec change `add-brindle-ui`)** — the shared UI crate, modelled on shadcn/ui: tokens (`UiTheme`) and the chrome's font family (`UiFont`, read through `ActiveFont::ui_font`), overlay primitives (layers, focus scope, placement, list navigation, focus-visible); `Anchored::within(area)` keeps a box inside an area (`place_within`), as the mouse feedback label keeps itself inside the grid, components and `TextInput`.
  - **Boundary:** it depends on `gpui` only, never on `brindle`, `brindle-term-core` or `alacritty_terminal`, so it knows nothing of terminals, config or the `ACTIONS` table. Mapping the terminal theme to tokens is the app's job.
  - Its actions are `brindle_ui::*`. `brindle_ui::default_bindings()` returns its default keys, and Brindle chains them into its own `default_bindings()`, so a config reload restores them; the crate binds no keys itself.
  - Controls activate on the enter or space **key-down** and ignore gpui's keyboard click, which fires on the key-up for whatever has focus then (an overlay confirmed with enter would otherwise reopen from its opener on the release).
  - **Items by key (OpenSpec change `extract-decisions-into-models`, group 1):** `CommandItem`, `SelectOption` and `MenuItem` carry an `ItemKey`, the owner's opaque identity for the item (its label unless set with `.key(..)`, which an owner whose labels repeat gives). Components keep items by key across a refresh and name the chosen one by it: `SelectEvent::Changed(ItemKey)`, `ComboboxEvent::Changed(ItemKey)`, `MenuEvent::Selected(ItemKey)`, `Command::set_groups(.., keep: Option<ItemKey>)`; a `TabMove` names the dragged trigger by its `ElementId`. The owner finds a key among its items as they are then (`option_keyed`, `item_keyed`, `entry_keyed`); an index is valid only within the call that computed it (`CommandEvent::Confirmed(usize)` is read in the same update). Brindle's palettes, profile menu and profile selects key their items by position for now, mapping the key back to the index they used before, and the fonts combobox and the action menus by label.
  - **Components** (listed in `ui/README.md`): `Button` (with the small icon sizes `IconSm` and `IconXs`), `Input`, `Checkbox`, `Switch`, `Toggle`, `Kbd` (keycaps from a keymap string), `Separator`, `Badge` (shadcn's outline badge in one colour, which can be cut with an ellipsis, unlike shadcn's, or `Badge::icon`, an icon alone that isn't cut; either can carry a tooltip), `Tooltip` (a label and optional shortcut keycaps, put on an element through `TooltipFor`), `Dialog`, `Popover`, `Select`, `Command`, `Combobox` (shadcn's Popover holding a Command, behind a select-style trigger; the owner reads the open list's search and highlight through `command()`), `Menu` and its two openers `ContextMenu` and `DropdownMenu`, and `TabList`/`TabTrigger` (shadcn's Tabs plus what a tab strip needs: close buttons, leading elements (status and bell dots) and trailing adornments, a `TabWidth`, drag to move, a context menu, per-trigger surface and text colours, an `EdgeBar` along a trigger's bottom edge, and a `Badge` after its label; the list is always shadcn's pill, with no other variant). `Card` and `CardHeader` are the bordered surfaces that zones are drawn in: an optional 28px header row over content with no padding, colours from the owner's `CardColors`, a `ring` prop for the focus ring, an optional `EdgeBar` along the header's bottom edge and `Badge` after its title (the title cut first, down to 8 characters, then the badge; the actions then sit at the end through an auto margin), and corners cut out in the `surround` colour (gpui can't round the content itself). `Icon` draws lucide's strokes itself (no SVG assets), sized in rems, and includes `ClipboardPaste` and `Ban` (lucide's `clipboard-paste` and `ban`, beside `Copy`) for the mouse feedback label; `IconElement::min_stroke` (`Button::icon_min_stroke`) keeps chrome icons' strokes at least 2px wide, and `IconElement::turn` (`Button::icon_turn`) turns one for a spinner.
  - **AI elements (OpenSpec change `agents-profiles`, section 3):** `Textarea` (`Input`'s frame around a `TextArea`), `MessageScroller` (an entity over gpui's `list` with `ListAlignment::Bottom`; the owner keeps the items and splices; the pure `Follow { AtEnd, Away }` comes from the list's scroll events, and an outline `arrow-down` button shows while away), `Message`/`Bubble` (the person's at the end on `muted`, the other side's at the start on the card; `BubblePart` draws a message split over list items as one bubble; actions drawn only on hover), `PromptInput` (an entity owning its `TextArea`: the owner's `PromptStatus` picks the submit button, a queue row shows a `Queued::{Waiting, Held}` text with buttons that ask the owner and never touch the draft; it emits `PromptInputEvent::{Submit, Stop, RemoveQueued, ResendQueued}`; enter and escape are `PromptSubmit`/`PromptStop` in the `PromptInput` context, which wraps the text area alone), `Reasoning` (a pointer-only trigger over content, `open` held by the owner), `Tool` (one unfocusable row with a status badge), `Confirmation` (keyed action buttons while requested, the outcome once answered) and `Alert`. They know nothing of agents. Their tests run in gpui's `TestAppContext` (`test-support` is a dev-dependency only; `ui/src/test_support.rs`).
  - **Ellipsis pitfall:** gpui 0.2.2's `truncate()`/`text_ellipsis` on a flex item cuts nothing (the text keeps its first, natural-width measure). A one-line label that must give way in a flex row uses `trigger_label` (a line clamp of 1 laid over an invisible unwrapped copy), as tab triggers and zone header titles do.
  - The gallery (`cargo run -p brindle-ui --example gallery`, see `ui/README.md`) shows every component; `-- --check` drives the `ui-components` spec's scenarios from inside the app (keys through `Window::dispatch_keystroke`; key releases and pointer presses as messages posted to its own window, Windows only, skipped elsewhere) and prints `ok`/`FAIL`/`SKIP` per check. Both open a window: ask first, as for any GUI run.
- **`text_input.rs`** (in `brindle-ui`, `ui/src/text_input.rs`) — the single-line `TextInput` used by every overlay text field. `EditState` (text, selection, IME composition, UTF-16 offsets) is pure and unit-tested; the entity adds focus, the `TextInput` key context, mouse, clipboard and `EntityInputHandler`, so typed text and IME arrive through the platform input handler as in terminals. `EditState` has a `Lines` mode: `One` for `TextInput`, `Many` (`EditState::multiline`) keeping `\n` and tab for **`TextArea`** (`ui/src/text_area.rs`), the multi-line entity, which wraps with `shape_text`, hands the pure `WrapMap` of each layout back for vertical motion (`motion_vertical`, keeping a goal x) and home/end on the shown row, grows to `max_lines` then scrolls to the cursor (`first_row_for_cursor`), and binds its line keys and shift-enter in the `TextArea` context. It binds no escape, tab or shift-tab, passes enter on (`TextAreaEnter`) unless composing and passes up and down at its edges, so the owner's bindings get them; unbound enter or tab text from gpui's input-handler fallback is dropped.
  - The `TextInput` context binds no enter, escape, tab, up/down or ctrl-p/ctrl-n, so those reach the contexts around it: enter, up/down and ctrl-p/ctrl-n a command list's `UiList` (a palette's filter), the `Palette` (enter in a prompt) or the settings dialog's contexts, tab `UiFocusScope` (inside an overlay) and escape `UiCommand` (a palette's list) or else `UiLayer`.
  - Owners keep plain strings: they subscribe to `TextInputEvent::Changed` and call `set_text` (which emits nothing) for their own changes. The settings dialog lists its controls as `FocusStops` per section and mode, and the overlay's focus scope walks them on tab; the dump's `field=` is derived from which stop has focus.
