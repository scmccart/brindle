## Summary

2. Clamp listed session sizes from remote endpoints.

## Attack surface

1. **Program output** in any tab: OSC 7, 8, 9;9, 52 and 7501, titles, and mode switches such as bracketed paste. This includes everything a host prints when `ssh` runs inside a local tab.
2. **Remote endpoints** reached through SSH or Docker profiles: the relay link, `LIST` session info, `PROCESS` reports, and error text.
3. **Other local principals:** other users, and unelevated processes against an elevated Brindle on Windows. They can reach the server directories and pipes, the instance pipe or socket, the session bus, and the helper-copy and ConPTY folders.
4. **The user's own files:** the config and the state files.

## Findings

### High

**1. Program output makes Brindle send the user's NTLM credentials to any host, with no click** (`term-core/src/shell_integration.rs:299`, and the OSC 7 branch at `:279–288`)
- **Cause:** in the Windows path style, `reported_dir` accepts any path starting with `\\`. That includes UNC, `\\?\UNC\…` and WebDAV forms such as `\\host@80\x`.
- **Path:** every second, `Workspace::new`'s timer (`src/workspace.rs:555`) calls `record_session` (`:733`), then `zone_records` (`src/zone_view.rs:588`), then `Terminal::working_directory`. That runs `is_dir()` on the reported path for local Windows tabs (`src/terminal/mod.rs:1102`), on the UI thread. This chain was verified by hand.
- **Impact:**
  - Each check opens SMB or WebDAV to the attacker's host, which sends the user's NTLM credentials.
  - It also blocks the window for the connection timeout.
- **How long it lasts:** cmd, and PowerShell without Brindle's integration, never report a new directory, so the leak repeats until a new path replaces it.
- **Spread:** splits, new tabs and restore (`src/session.rs:506`) start the new shell in that directory through `CreateProcessW`.
- **Fix:** in the Windows style, accept only drive-letter paths in `reported_dir`, and move the `is_dir` check off the UI thread. The off-thread check also stops the freezes when a real network drive drops.

### Medium

**2. An elevated Brindle runs and deletes code in folders unelevated processes can write** (`remote-protocol/src/win.rs:475`; refutation lowered it from high)
- **Cause:** the helper copies (`%LOCALAPPDATA%\brindle\server`) and the ConPTY files (`…\conpty`) are shared between elevated and unelevated runs.
- **How an unelevated process gets code run elevated:**
  - It forges a copy, which is checked only by an FNV-1a build id, or swaps it between the check and the launch.
  - It replaces the running copy, which the holder relaunches from its own path.
  - It replaces `OpenConsole.exe` after its one-time check.
  - It plants `pwsh.exe` or `cmd.exe` in the copy's folder, which is searched first for bare program names (`remote-agent/src/server/platform/windows/pty.rs:510`).
  - It turns the copies folder into a junction, so `prune_copies` (`remote-agent/src/server/core.rs:206`) deletes directories elsewhere as administrator.
- **Precondition:** attacker code already running as the user without elevation. Microsoft doesn't treat UAC as a boundary, but Brindle's own threat model does.
- **Fix:** when elevated, use folders with a DACL of Administrators and SYSTEM only, plus a High integrity label, and refuse reparse points.

**3. Ctrl-clicking a link opens any target, and the target is never shown** (`src/terminal/links.rs:154`; merges `:101` and `src/terminal_view.rs:573`)
- **Cause:** `has_scheme` is the only check before `ShellExecuteW` or `xdg-open`.
- **What gets through:**
  - a drive path such as `C:\…\x.exe`, which Windows runs as a program;
  - a `file://host/share` UNC path;
  - any protocol handler (`ms-*:`, `search-ms:`, …).
- **On Windows:** a quote or space in the link can add arguments to the program a protocol handler starts. A plain-text `file://` URL also reaches the Windows shell.
- **Fix:** allow only http, https and mailto by default. Reject one-letter schemes. Show the target, and confirm when an OSC 8 link's text differs from its URI.

**4. A malicious remote endpoint can abort Brindle on every launch** (`src/terminal/mod.rs:548`; root at `src/remote/identity.rs:59`)
- **Cause:** listed session sizes have no upper cap.
- **Path:** the launch sweep turns detached sessions into tabs and builds each grid with `Term::new` on the UI thread. At 65535×65535 that is about 200 GB, and the failed allocation aborts the whole process, local tabs included.
- **Trigger:** none needed from the user, for endpoints with `connect_at_launch` or a restored tab.
- **Fix:** clamp the size in `ListedSession::of`, and on every path into `Term::new` and resize.

**5. Another local account can squat the Windows instance pipe** (`src/instance.rs:351`)
- **Cause:** a later launch opens the pipe with std's default QoS (impersonation) and never checks who serves it. The terminal-server clients do both.
- **Impact:**
  - A process of another account that creates the name first receives every launch's request: its `-e` command, cwd and activation token.
  - A service account with `SeImpersonatePrivilege` can also act as the user.
- **What it can't do:** the default DACL and label stop anyone sending commands the other way into the user's Brindle.
- **Fix:** open with `SECURITY_IDENTIFICATION`, call `win::check_server` before writing, and put the SID and elevation in the pipe name.

### Low (lowered during refutation)

- **`run-elevated` folder:** its DACL includes the user's SID, so unelevated processes can take its locks and read its logs. Redirecting a log needs a race, and a junctioned parent isn't checked (`remote-agent/src/server/platform/windows/dir.rs:41`).
- **OSC 52 clipboard writes:** any program overwrites the clipboard and primary selection silently, with no size cap (`src/terminal/mod.rs:782`). Combined with that, background output printing `CSI ?2004 l` makes the next paste go unbracketed, so it runs (`:903`). This is standard xterm behaviour.
- **Linux client and CLI:** they don't check the server directory's owner or the socket peer. This matters when Brindle runs as root with the user's environment (`sudo -E`, `su` without `-`), or with a shared `BRINDLE_SERVER_DIR`; root's `core.log` can then be redirected through a symlink (`src/remote/local/unix.rs:30`, `remote-agent/src/server/cli.rs:289`, `check.rs:94`).
- **Config permissions:** a settings-dialog save resets a 0600 config to the default 0644 (`src/config_edit.rs:32` → `src/config.rs:687`).
- **Relay folder check:** the relay checks only the leaf server directory, once, and never the core's peer (`remote-agent/src/server/relay.rs:284`).

### Low (not refuted; the method refutes only critical, high and medium)

- **Text shown raw:**
  - remote error text written raw into that endpoint's own tabs (`src/remote/local/relay.rs:205`, `src/remote/local/connection.rs:2463`, `src/terminal/server.rs:160`);
  - `brindle-remote list` printing titles with C1 controls (`remote-agent/src/server/cli.rs:146`).
- **Instance socket and pipe:**
  - no read timeout on the Windows instance pipe (`src/instance.rs:333`);
  - the `/tmp/brindle/run` fallback has no owner check (`src/instance.rs:161`).
- **Config:** loaded with no owner check, and saved through a predictable temp name (`src/config.rs:477`).
- **Windows pipes:**
  - predictable pipe names allow a denial of service only (`remote-agent/src/server/platform/windows/listen.rs:449`, `pty.rs:472`);
  - `check_server` identifies the server by pid, which can be reused (`remote-protocol/src/win.rs:208`).
- **Container `/tmp`:** assumed sticky (`src/remote/client.rs:361`).
- **Notifications:**
  - `Notifier`'s pending map grows without limit (`src/notify/mod.rs:319`);
  - the D-Bus summary isn't markup-escaped (`src/notify/dbus.rs:114`);
  - signals aren't filtered by sender, so a forged click steals focus (`:84`).
- **Profile sent to the wrong endpoint:** after a config edit or a state-file restore, a split can send a profile's env and command to an endpoint the profile doesn't target. An endpoint can't cause this (`src/remote/local/relay.rs:481`).

## Ruled out

- **Local environment:** remote spawns never carry Brindle's own environment.
- **Remote directories:** never reach local tabs or local disk checks.
- **Paste:**
  - the reported "C1 paste bypass" isn't real;
  - bracketed paste strips ESC.
- **Find bar:** regexes are linear-time and size-limited.
- **Remote listing size:**
  - the 1 MiB `LIST` frame cap holds;
  - layout JSON is bounded.
- **Remote endpoint controls:**
  - an endpoint can't select a local profile;
  - relay frames after setup are dropped;
  - kills stay on their endpoint.
- **Windows server pipes:** they check client and server identity soundly.
- **Panic text:** can't re-trigger the panic on the UI thread.
- **CI workflows:** benign.

## Suggested rules

There is no repository security policy yet. These would close the classes above:
1. Paths, URIs and sizes from program output or a remote endpoint are untrusted, and are validated where they are parsed.
2. An elevated process never runs, loads or deletes anything in a location a Medium-integrity process can write.
3. Every local IPC client authenticates its server before writing: peer uid on Unix; SID, integrity and `SECURITY_IDENTIFICATION` on Windows.
4. Files Brindle rewrites keep their mode, and new ones are created 0600.
5. No filesystem or network I/O runs on the UI thread for data the user didn't choose.

## Remediation order

1. **#1:** drive-letter-only paths, plus an off-thread check.
2. **#4:** clamp listed session sizes.
3. **#3:** link scheme allowlist, and show the target.
4. **#5:** instance pipe QoS and `check_server`.
5. **#2:** separate elevated folders, with an integrity label and reparse-point checks.
6. **The lows:** config mode, the Linux peer check, an OSC 52 setting, then the rest.
